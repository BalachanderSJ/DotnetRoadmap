How to use this guide with the roadmap

The roadmap is the script you speak. This guide is the mechanism behind each line of that script: what the runtime actually does, what the code looks like when it is right, what it looks like when it pages someone at 02:00, and what the choice costs in allocations, latency, and operational load. Every block is built so that you can answer the first question in ninety seconds and survive the third follow-up.

  1. Read the short answer, then the Under the hood box. Trace the recommended code with a pen.
  2. Cover the code and write the five lines that matter from memory. If you cannot, you do not own the topic yet.
  3. Read the pitfall code and say out loud why it fails, who notices, and how you would detect it in production.
  4. Speak the Say this in the room box in under ninety seconds. Add the trade-off only when they push.
  5. On Day 10, use the rapid-fire miniatures as a check and return to the full block when one feels thin.

1.1Class, struct, and record

QWhat is the difference between a class, a struct, and a record? Where does each actually live in memory, and which would you use for an EF Core entity, an integration event, and a money value?

Short answerA class is a reference type with identity: variables hold a pointer to one heap object. A struct is a value type: the bytes are copied on assignment and stored inline wherever the struct is declared. A record is compiler-generated value equality, immutability by default, and a with clone, applied to either a class (record) or a struct (record struct). Entity: class. Event or DTO: sealed record. Small immutable value: readonly record struct.

How it works

On 64-bit .NET every heap object carries two hidden words before its fields: an 8-byte object header (sync-block index, thin-lock bits, or the cached identity hash code) and an 8-byte MethodTable pointer that identifies the type and its virtual-method table. A reference points at the MethodTable word; the header sits at a negative offset. The minimum object size is 24 bytes even for an empty class. Every object is also something the GC must mark and possibly move.

A struct has no header and no MethodTable pointer when it is stored unboxed. Where its bytes live depends on where it is declared: a local can live on the stack or entirely in registers (the JIT can "promote" struct fields to registers); a struct field of a class lives inside that object on the heap; a struct element of an array is laid out contiguously inside the array. That last point is why Money[] of a thousand items is one allocation while a thousand class instances are a thousand and one.

Under the hood
  • Copy semantics: assignment, parameter passing, and returning a struct copy every byte. The framework design guideline of "about 16 bytes or less" for frequently copied structs is about this copy cost, not a hard limit.
  • default bypasses invariants: default(Money) and every element of new Money[10] are all-zero bits. A struct constructor never runs for them, so a struct cannot guarantee that Currency is non-null.
  • What a record generates: an EqualityContract property, Equals(R? other) comparing every field through EqualityComparer<T>.Default, a matching GetHashCode, == and !=, a ToString that prints members, Deconstruct for positional records, and a protected copy constructor used by with. with is a shallow copy.
  • Positional record struct properties are mutable (get; set;) unless you declare readonly record struct. Positional record (class) properties are init-only.
  • Default struct equality is slow: ValueType.Equals compares bits only when the struct has no reference fields and no padding; otherwise it uses reflection over fields, and the call itself boxes. Records and IEquatable<T> avoid both.

Example

Shape (x64)Bytes per item1,000 items
sealed class Money { decimal; string; }8 header + 8 MethodTable + 24 fields = 401,001 allocations, about 48 KB, 1,000 objects for the GC to trace
readonly record struct Money(decimal, string)24, inline1 allocation, about 24 KB, contiguous and cache friendly
Performance and trade-offs
  • Allocations: small structs remove an allocation per value and the GC work that goes with it. Large structs trade allocation for copy cost on every call and assignment.
  • CPU: contiguous struct arrays are cache friendly; arrays of references chase pointers. Structs that implement interfaces box when used through the interface (see the boxing block).
  • Thread safety: immutable records and readonly structs are thread-safe by construction. A mutable struct stored in a readonly field is silently copied before every member call (a defensive copy), so mutations vanish.
  • Latency: irrelevant for a CRUD endpoint dominated by SQL; relevant in parsers, pricing loops, and anything allocating per element.
Architectural context
In a Clean Architecture solution the Domain project holds entities as classes with private setters and behavior, and value objects as readonly record struct or sealed records. EF Core maps value objects as owned types or, on EF Core 8+, as complex types, so Money becomes two columns on the Orders table without a separate identity. Contracts that cross a process boundary (MassTransit messages, Service Bus payloads, MediatR requests) are sealed records in a contracts package: immutable, value-equal, and safe to serialize, retry, and compare in tests.
What breaks in production
A large mutable struct copied into a method and mutated leaves the caller's copy unchanged, with no compiler warning. A record used as an EF entity breaks change tracking and dictionary lookups once its fields change, because its hash code moves with them. A record holding a List<T> is not value-equal, which surprises the test that compares two events. And the sentence "structs live on the stack" is wrong often enough to lose the point: a struct field of a class lives on the heap with the object.
Say this in the room
Class when identity matters, record when the values are the identity, readonly struct when the value is small and immutable. A class instance costs a 16-byte header plus GC tracking; a struct costs a copy on every pass. I reject a large mutable struct in the API layer and a record used as an EF entity.

1.2ref, out, in, and params

QExplain ref, out, in, and params. When does in actually help, when does it hurt, and why do these rarely appear on a public Web API surface?

Short answerref, out, and in pass a managed pointer to the caller's storage instead of a copy. ref is read-write and must be initialized by the caller; out must be assigned by the callee; in is read-only and avoids copying a large struct. params packs arguments into an array, or on C# 13 into a span. HTTP has no references, so these belong in parsers and hot paths, not in API contracts.

How it works

All three compile to a managed pointer (a byref, T& in IL). The GC understands byrefs, including interior pointers into the middle of an object or array, and updates them when it compacts the heap. Because a byref can point at a stack slot, the runtime forbids storing one on the heap. That one rule is the origin of every ref struct restriction you will see in the next block.

Under the hood
  • in and defensive copies: if the struct is not readonly, the compiler cannot prove a method call will not mutate it, so it copies the struct into a hidden temporary before every member call on an in parameter or a readonly field. You pay the copy you were trying to avoid. Mark the struct readonly, or mark the members readonly.
  • Passing an rvalue to in makes the compiler create a temporary. C# 12 added ref readonly parameters for APIs that must receive a real variable, with a warning when you pass a value.
  • ref returns and ref locals let you write into storage owned by someone else. CollectionsMarshal.GetValueRefOrAddDefault returns a ref into a dictionary entry, removing the second hash lookup of a read-then-write.
  • params: a params object[] call allocates an array and boxes every value-type argument. C# 13 allows params ReadOnlySpan<T>, which the compiler can back with a stack buffer.

Example

Performance and trade-offs
  • Allocations: ref and in allocate nothing. params object[] allocates an array plus a box per value type on every call, even when the callee returns early.
  • CPU: in pays off from about 32 to 64 bytes upward and only on readonly structs. On a small struct it adds an indirection for nothing.
  • Thread safety: a ref into a Dictionary or List is invalidated by any concurrent or subsequent mutation of the collection.
Architectural context
Inside the Application layer, prefer returning a result type (Result<OrderDto>, a discriminated record hierarchy, or a tuple) over out parameters: the shape survives being moved behind MediatR, a queue, or an HTTP boundary. Keep ref, in, and ref returns inside Infrastructure hot paths: parsers, serializers, pricing loops.
What breaks in production
A public out parameter makes ownership unclear and cannot cross HTTP. An in parameter on a non-readonly struct is a silent performance regression. A ref into a dictionary held across an Add writes into freed storage. params object[] on a logging helper boxes every integer on the hot path.
Say this in the room
ref reads and writes the caller's variable, out must be assigned by the callee, in is a readonly pointer that avoids copying a large readonly struct. The trap is a defensive copy when the struct is not readonly. On a Web API I return a result type; I keep refs in parsers and hot loops.

1.3Span<T>, Memory<T>, ref struct, and ArrayPool<T>

QWhat is Span<T>, why can it not be used in an async method or stored in a field, and how do Memory<T> and ArrayPool<T> fit with it? Show me a parser that does not allocate per line.

Short answerSpan<T> is a ref struct holding a managed pointer and a length. It is a window over contiguous memory, whether that is an array, a string, a stackalloc buffer, or native memory, and slicing it never copies. Because it may point at the stack, it is stack-only: no boxing, no heap fields, no capture in lambdas, and no use across await. Memory<T> is the heap-storable equivalent. ArrayPool<T> rents and returns buffers so a hot path stops allocating them.

How it works

Internally Span<T> is { ref T _reference; int _length; }. Since C# 11 that ref field is a public language feature, and Span<T> is just a ref struct that uses it. The JIT treats span indexing like array indexing, including eliminating bounds checks in simple loops. ReadOnlySpan<char> over a string points at the string's characters, so text.AsSpan(4, 6) is a view, not a Substring allocation.

Under the hood
  • Why stack-only: a span can point at a stackalloc buffer that disappears when the method returns. If the span could be boxed, stored in a class field, captured by a lambda, or survive an await (where locals are hoisted into a heap-allocated state machine), it could outlive the memory it points at. The compiler enforces the lifetime rules (scoped, ref-safety contexts) at compile time.
  • C# 13 relaxations: ref struct locals are allowed in async methods and iterators as long as they are not live across an await or yield. Generic methods can opt in with the allows ref struct anti-constraint.
  • Memory<T> is a normal struct { object _object; int _index; int _length; } that can live on the heap and cross await. You call .Span at the point of use, in a synchronous section.
  • ArrayPool<T>.Shared keeps per-core caches of arrays bucketed by power-of-two sizes. Rent(n) returns an array of at least n elements that may contain data from its previous user. Return puts it back; using it afterwards is a use-after-free bug that can leak one request's data into another.

Example

Performance and trade-offs
  • Allocations: the parser above allocates one string per row instead of four objects per row. On a million-row nightly import that is millions fewer Gen0 objects, and far fewer promotions to Gen1 and Gen2.
  • CPU: span slicing is a pointer add. ArrayPool rent and return cost tens of nanoseconds, cheaper than allocating and zeroing a large array, and dramatically cheaper than a Large Object Heap allocation (85,000 bytes and up) that triggers Gen2 work.
  • Thread safety: a span is not shared by construction, because it cannot escape the stack. A rented array is owned by exactly one caller between Rent and Return.
  • Trade-off: span code is harder to read and review. Use it where a profiler shows allocations, not across the domain model.
Architectural context
Kestrel, System.Text.Json, and System.IO.Pipelines are built on spans, IBufferWriter<byte>, and pooled memory, so ASP.NET Core already gives you a low-allocation request path. Your job is not to undo it: do not read the body into a string, then Split it. Keep span-based code in Infrastructure (parsers, file importers, webhook signature checks) and expose ordinary types (OrderLineRow) to the Application layer. For streams of unknown size, prefer Microsoft.IO.RecyclableMemoryStream or a PipeReader over MemoryStream.ToArray().
What breaks in production
Returning a rented array and then reading it, or returning it twice, corrupts another request's data, and it only shows up under load. Forgetting that Rent(100) may return 128 elements writes garbage past the logical end unless you slice. A large stackalloc in a recursive method overflows the stack and kills the process with no catchable exception. ToString() on a span inside a loop reintroduces every allocation you removed.
Say this in the room
Span is a stack-only view over memory: an array, a string, or a stackalloc buffer, sliced without copying. It cannot cross await or live in a field because it might point at the stack; Memory is the heap version. In hot parsers I use spans plus ArrayPool with a try/finally return, and I measure the allocation drop with BenchmarkDotNet before I ask the team to read harder code.

1.4Pattern matching and switch expressions

QHow do you use modern pattern matching in production code? What does the compiler generate, and where does it hide a bug?

Short answerPatterns test shape and value in one expression: type, property, positional, relational (>= 100), logical (and, or, not), and list patterns. A switch expression is an expression with exhaustiveness checking, which makes it ideal for state transitions and for mapping results to HTTP. The bug it hides is a discard arm that silently absorbs a new enum value or subtype.

How it works

The compiler lowers a switch expression into a decision DAG: it orders the tests so that each input is examined at most once, shares common sub-tests between arms, and reports an error when an arm can never be reached (it is subsumed by an earlier arm). Type patterns become isinst checks; property patterns call the getters; list patterns use Length or Count, the indexer, and slicing. The compiler warns (CS8509) when inputs are not covered, but only if you do not add a _ arm.

Example

Performance and trade-offs
  • Allocations: none for type, relational, and property patterns. Tuple patterns over (current, command) build a ValueTuple on the stack, not the heap.
  • CPU: the decision DAG is at least as good as hand-written if chains. Switching on strings compiles to length checks and character comparisons, or to a hash, depending on the cases. For a very large type hierarchy, a virtual method can be faster than a long chain of type tests.
Architectural context
Pattern matching is how C# expresses the "closed set of outcomes" that functional languages call discriminated unions. Use it in the Domain for state machines and in the API layer for mapping application results to TypedResults. A closed record hierarchy plus a switch expression replaces the if (result.IsSuccess) ... else if (result.Error == "conflict") string matching that drifts over time.
What breaks in production
A _ arm silences the exhaustiveness warning, so a new enum member compiles and falls into the default branch. Add a unit test that iterates Enum.GetValues<OrderStatus>() through every switch that matters, or throw in the default arm. Patterns run top to bottom: a broad arm placed early shadows a specific one, and the compiler only catches the fully subsumed case.
Say this in the room
I use switch expressions for state transitions and for mapping results to HTTP, because they are expressions with exhaustiveness checking. The compiler builds a decision tree, so it costs nothing extra. The bug is the discard arm that swallows a new state, so the default throws and a test walks every enum value.

1.5Deferred LINQ, IEnumerable, and IQueryable

QWhat is deferred execution? What is the real difference between IEnumerable<T> and IQueryable<T>, and what goes wrong when a service returns IQueryable?

Short answerLINQ to Objects builds a chain of iterator objects that run when you enumerate, and run again on every enumeration. IQueryable<T> holds an expression tree that a provider such as EF Core translates to SQL when you enumerate. The moment a query is typed as IEnumerable<T>, every later operator runs in your process on rows SQL already returned. Keep IQueryable inside the data method, project, and materialize once.

How it works

Where on an IEnumerable<T> takes a Func<T, bool> (compiled IL) and returns an iterator object. Where on an IQueryable<T> takes an Expression<Func<T, bool>>, a data structure describing the lambda, and returns a new query whose expression tree has one more node. Nothing touches the database until enumeration: foreach, ToListAsync, CountAsync, FirstOrDefaultAsync.

Under the hood
  • LINQ to Objects: each operator allocates an iterator plus a delegate, plus a closure object if the lambda captures a local. The runtime specializes common chains (for example, a Where followed by a Select over a List<T>), and in .NET 8 and 9 aggregates such as Sum and Max over arrays are vectorized. Enumerating a List<T> through IEnumerable<T> boxes its struct enumerator.
  • EF Core pipeline: on enumeration EF computes a cache key from the expression tree's shape, looks up a compiled query, and on a miss translates the tree to SQL and compiles a materializer delegate. Captured variables (tenantId) become SQL parameters, so one cached plan serves every tenant. Building expression trees dynamically, with a different shape per request, defeats both the EF query cache and the SQL plan cache.
  • Client evaluation: since EF Core 3, an untranslatable predicate throws. Only the final Select may contain client code, which runs on materialized rows.

Example

Performance and trade-offs
  • Allocations: a Where().Select().ToList() chain over a small in-memory list costs a few objects. That is irrelevant per request and relevant in a loop over a million rows, where a plain foreach is clearer and allocation-free.
  • Latency: the cost of an early IEnumerable is the SQL transfer and the change tracking of every row you then discard. It grows with the tenant, so it passes in development and times out for the largest customer.
  • Analyzers: CA1851 flags multiple enumeration of an IEnumerable. Turn it on.
Architectural context
In CQRS terms, the query side owns IQueryable and returns DTOs; it never leaks a query to the API layer. The command side loads an aggregate by key. A generic repository that returns IQueryable<T> erases that boundary and is the reason Day 2 refuses it as a house style.
What breaks in production
A second enumeration of a deferred query repeats the SQL. An AsEnumerable() in the middle of a chain silently moves every later filter into memory. Returning IQueryable from a service enumerates after the request scope has disposed the DbContext, which throws ObjectDisposedException in the serializer, and only on that code path.
Say this in the room
IQueryable is an expression tree that EF translates to SQL when I enumerate. After it becomes IEnumerable, everything runs in memory on rows already fetched. I keep the query inside the data method, project to a DTO, and materialize once with ToListAsync. I do not return IQueryable from a service.

1.6async, await, and the ways production gets it wrong

QWalk me through what the compiler does with an async method. Then tell me the three async bugs you have seen take an API down.

Short answerThe compiler rewrites an async method into a state machine. It runs synchronously until the first await on an incomplete operation, then registers a continuation and returns the thread to the pool. When the I/O completes, a pool thread resumes the method at the saved state. The outages come from blocking on tasks (.Result, .Wait()), which starves the thread pool; from async void and fire-and-forget work that escapes the request scope; and from unbounded fan-out without cancellation.

How it works

For async Task<T> the compiler emits a struct implementing IAsyncStateMachine (a class in Debug builds). Parameters and any locals that live across an await become fields. An AsyncTaskMethodBuilder<T> drives it. The caller's thread runs MoveNext directly. At each await the generated code calls GetAwaiter() and checks IsCompleted. If the operation already finished (a cache hit, a buffered read), execution continues with no allocation and no thread switch.

If it has not finished, the builder boxes the state machine onto the heap the first time. That box is an AsyncStateMachineBox<TStateMachine>, which is also the Task<T> returned to the caller. The builder captures the ExecutionContext (which carries AsyncLocal values such as the current Activity) and hands a continuation to the awaited task. The method returns, and the thread goes back to the pool. When the socket or SQL read completes, the I/O completion thread completes the inner task, the continuation is queued to the thread pool (or run inline when that is safe), and MoveNext resumes at the saved state. Exceptions are captured into the task and rethrown at the await through ExceptionDispatchInfo, so the original stack trace survives.

Example

Performance and trade-offs
  • Allocations: a method that completes synchronously allocates nothing for the state machine. If it returns a result that is not cached, it still allocates the Task<T>; the runtime caches tasks for bool, null, and a few small integers. A method that actually suspends allocates one box, sized by its hoisted locals (often 100 to 200 bytes), plus whatever the awaited operation allocates.
  • CPU: each suspension costs a continuation dispatch to the pool, typically around a microsecond. That is irrelevant next to a millisecond of SQL and meaningful in a tight loop of tiny awaits. Batch them, or make the hot path synchronous when the data is in memory.
  • Threads: an awaiting request holds no thread. A blocked request holds one for the full I/O latency, which is why sync-over-async turns 50 ms of SQL latency into thread-pool starvation at a few hundred requests per second.
Architectural context
Async is end to end: controller or endpoint, MediatR handler, repository, EF Core, HttpClient. One synchronous adapter in the middle, typically a legacy SDK, blocks the chain. Wrap it on a dedicated thread or behind a queue rather than calling .Result. Background work that must outlive the request goes to a durable queue (the outbox, Service Bus) or at least to a Channel drained by a BackgroundService that creates its own scope. It never goes to _ = Task.Run(...).
What breaks in production
ConfigureAwait(false) in a controller does not fix a blocked .Result. async void outside UI event handlers drops exceptions on the thread pool, where an unhandled one terminates the process. Awaiting a ValueTask twice is undefined behavior. A fire-and-forget task that touches a scoped service fails with ObjectDisposedException minutes later, in a log line nobody correlates with the request.
Say this in the room
The compiler turns the method into a state machine. At the first incomplete await it boxes that state to the heap, registers a continuation, and gives the thread back. I pass the request's CancellationToken into EF and HttpClient, I reject .Result and async void in review, and I cap fan-out with Parallel.ForEachAsync, a scope per item, and a degree of parallelism I can justify against the SQL pool.

1.7ValueTask, SynchronizationContext, and ConfigureAwait

QWhen would you return ValueTask instead of Task? What is a SynchronizationContext, why did classic ASP.NET deadlock on .Result, and do you still need ConfigureAwait(false) in ASP.NET Core?

Short answerValueTask<T> avoids allocating a Task when the result is usually available synchronously, as with a cache hit or a buffered read, but it can be awaited only once. Use it on measured hot paths and on interfaces such as IAsyncDisposable; default to Task. A SynchronizationContext decides where a continuation runs. UI frameworks and classic ASP.NET had one bound to a single thread, so blocking that thread on .Result deadlocked. ASP.NET Core has none, so ConfigureAwait(false) matters in libraries, not in application code.

How it works

Under the hood
  • ValueTask<T> is a struct that wraps one of three things: a T (synchronous result, no allocation), a Task<T>, or an IValueTaskSource<T> plus a 16-bit token. The last mode lets a producer reuse one pooled object for many operations; sockets, PipeReader, and channels do this. Reuse is exactly why you may not await twice, await concurrently, or read .Result before completion: by then the source may already belong to the next operation.
  • PoolingAsyncValueTaskMethodBuilder (.NET 6+), applied with [AsyncMethodBuilder], pools the state-machine boxes of an async ValueTask method. It is a specialist tool: measure before you use it.
  • SynchronizationContext capture: by default await captures SynchronizationContext.Current (or a non-default TaskScheduler) and posts the continuation back to it. WinForms, WPF, and MAUI post to the UI thread. Classic ASP.NET's AspNetSynchronizationContext allowed one thread at a time per request. Blocking that thread with .Result while the continuation waits to get back onto it is the classic deadlock.
  • ASP.NET Core installs no context. Continuations run on any pool thread, so the deadlock cannot happen. Blocking still starves the pool, though, which is the modern version of the same mistake.
  • .NET 8 ConfigureAwaitOptions on Task: SuppressThrowing (await completion without rethrowing) and ForceYielding (always yield, even if already complete).

Example

Performance and trade-offs
  • Allocations: on a 95 percent cache-hit path, ValueTask removes a 70-byte-plus Task allocation per call. On a path that usually goes to I/O it saves nothing, and the struct is wider to copy.
  • Consumer cost: every caller must follow the single-await rule, and a ValueTask stored in a collection or passed to WhenAll must be converted with AsTask() first.
  • ConfigureAwait(false): in ASP.NET Core it saves a context check per await, which you will never measure. In a library it prevents deadlocks for callers you do not control.
Architectural context
Shared libraries in an enterprise (an internal SDK for the payments service, a common HTTP client package) use ConfigureAwait(false) consistently, enforced by analyzer CA2007, because some consumer will be a WPF tool or a legacy System.Web site. Application code in ASP.NET Core, Functions, and Worker Services omits it for readability. Public interfaces return Task unless implementations commonly complete synchronously; then ValueTask, as IAsyncDisposable.DisposeAsync and IAsyncEnumerator.MoveNextAsync do.
What breaks in production
Changing a public Task to ValueTask is a breaking change for callers who await twice or cache the task. Code that once ran under a context and was "fixed" with ConfigureAwait(false) can resume on a pool thread and touch UI controls or HttpContext.Current, which is null there. Blocking on a ValueTask backed by a pooled source is not supported at all.
Say this in the room
Task is the default. ValueTask is for a hot path that usually completes synchronously, and it is awaited exactly once. The old .Result deadlock came from a single-threaded SynchronizationContext; ASP.NET Core has none, so ConfigureAwait(false) belongs in libraries. What still hurts in ASP.NET Core is blocking, because it starves the pool.

1.8The thread pool and task scheduling

QHow does the .NET thread pool decide how many threads to run? What does thread-pool starvation look like in production, and how do you prove it?

Short answerThe pool keeps a small set of worker threads, starting at the processor count. A global queue plus per-thread local queues with work stealing feed those threads, and a hill-climbing algorithm tunes the thread count for throughput. When work blocks, the pool injects extra threads only gradually. Starvation looks like low CPU, rising latency, a growing queue length, and a thread count that climbs slowly. You prove it with dotnet-counters and a dump full of threads parked in .Result or Wait().

How it works

Under the hood
  • Queues: work queued from a non-pool thread goes to the global FIFO queue. Work queued from a pool thread (Task.Run inside a request, or a continuation) goes to that thread's local queue. The owning thread takes its newest item first, which is cache friendly; idle threads steal the oldest items from other threads' local queues. TaskCreationOptions.PreferFairness forces the global queue.
  • Thread count: the minimum defaults to the processor count, which in a container means the CPU limit the runtime detects. Above the minimum, the hill-climbing controller adds or removes threads based on measured throughput. When queued work makes no progress, a starvation detector injects threads, but slowly (historically on the order of one or two a second). Since .NET 6 the pool compensates faster when a thread blocks inside Task.Wait or .Result, which mitigates starvation but does not cure it.
  • I/O completions: on Windows they arrive through I/O completion ports, on Linux through epoll threads in the socket engine. Either way, the continuation that resumes your method runs on a worker thread.
  • Dedicated threads: TaskCreationOptions.LongRunning creates a new thread outside the pool. Use it for a loop that blocks for its whole life, such as a legacy SDK's receive loop, not for short work.
  • Inline continuations: by default, completing a TaskCompletionSource can run awaiting continuations synchronously on the completing thread. Pass TaskCreationOptions.RunContinuationsAsynchronously so a producer does not unexpectedly execute its consumers' code while holding a lock.

Example

Performance and trade-offs
  • Latency: every queued work item waits for a free worker. Under starvation, p99 grows by seconds while CPU stays idle, a signature that separates starvation from a CPU-bound slowdown.
  • Memory: each extra thread reserves a stack (1 MB by default on Windows, often 1.5 MB or more on Linux) and adds context-switch cost. Raising the minimum threads trades a starvation incident for a memory one.
  • CPU-bound work: on a server, Task.Run inside a request only moves work from one pool thread to another and adds a hop. It helps in UI apps, where it frees the UI thread.
Architectural context
The thread pool is shared by Kestrel, your endpoints, HttpClient continuations, EF Core, timers, and every BackgroundService in the process. That is why a hosted job that blocks can degrade the API sitting next to it. It is also the argument for moving heavy or blocking work into a separate Azure Function or worker process, where it scales and fails independently. SetMinThreads is a short-lived mitigation with a ticket attached, not a fix.
What breaks in production
A single synchronous call in a hot path (a sync Redis client, a blocking File.ReadAllText on a network share, a lock held across slow work) can starve the pool at load. The symptom is timeouts everywhere, including health checks, which then restart instances and make it worse. Teams often misread it as "SQL is slow" because every dependency's latency goes up at once.
Say this in the room
The pool has a global queue, per-thread local queues, and work stealing, and hill climbing tunes the thread count; it adds threads slowly when work blocks. Starvation shows up as low CPU, rising queue length, and slowly climbing threads. I confirm it with dotnet-counters and a dump full of .Result frames, then remove the blocking call rather than raise the minimum threads.

1.9IAsyncEnumerable<T> and streaming

QWhen do you return IAsyncEnumerable<T> instead of a list? How does cancellation flow into an async iterator, and what does streaming do to your database connection?

Short answerIAsyncEnumerable<T> is a pull-based stream in which each MoveNextAsync can await I/O. Use it to export or process large result sets with constant memory, and to page through an external API lazily. ASP.NET Core serializes it as a JSON array while it streams. Cancellation flows through WithCancellation into the parameter marked [EnumeratorCancellation]. The cost is that an EF Core stream holds its connection open for the whole enumeration.

How it works

An async iterator (async IAsyncEnumerable<T> with yield return) compiles to a class that implements the enumerable, the enumerator, and IValueTaskSource<bool>, so one object serves the whole enumeration and MoveNextAsync returns a ValueTask<bool> without allocating per item. await foreach calls DisposeAsync at the end, which runs the iterator's finally blocks and disposes the readers and connections opened inside it. EF Core's AsAsyncEnumerable() streams rows from a DbDataReader as they arrive.

Example

Performance and trade-offs
  • Memory: constant, bounded by one row or one page, instead of the whole result set. For a 500,000-row export that is the difference between a few kilobytes and hundreds of megabytes on the Large Object Heap.
  • CPU: per-item overhead is small but real: a MoveNextAsync per element. For a page of 50 DTOs, a List<T> is simpler and faster.
  • Connections and locks: an EF stream keeps a pooled connection and an open reader for its whole duration. Under locking READ COMMITTED, slow consumption can hold shared locks. Never do slow per-row I/O inside the loop: buffer a batch, or stage to a table first.
Architectural context
Use streaming at the edges: exports, ETL from partner APIs, gRPC server streaming, and a ChannelReader<T>.ReadAllAsync() feeding a worker. In a CQRS read side, normal queries return pages. A streaming export is a separate endpoint with its own timeout, rate limit, and a read-replica connection if you have one. On .NET 10 the base library includes LINQ operators for IAsyncEnumerable; on .NET 8 they come from the System.Linq.Async package.
What breaks in production
Forgetting [EnumeratorCancellation] means a cancelled export keeps reading until the end. A stream returned from a service after its DbContext scope has ended throws when the serializer starts enumerating. Streaming through a proxy or gateway that buffers responses removes the memory benefit and can time out the request.
Say this in the room
IAsyncEnumerable is a pull stream in which each item can await. I use it for exports and paged partner reads, so memory stays flat. Cancellation needs EnumeratorCancellation, and an EF stream holds a connection for the whole enumeration, so I never do slow per-row I/O inside it. For a normal page I return a list.

1.10Equality, hash codes, and records

QWhat must be true about Equals and GetHashCode? What breaks when you use a mutable object as a dictionary key, and should an EF entity override Equals?

Short answerEqual objects must return equal hash codes, and a key's hash must not change while it sits in a hash-based collection. Records generate correct value equality for contracts. Keys should be immutable: a record, a readonly record struct, or a value tuple. Entities keep reference identity, or compare by key only when the key is already assigned.

How it works

Under the hood
  • Dictionary internals: Dictionary<TKey,TValue> computes GetHashCode once, on insert, picks a bucket from it, and stores the hash alongside the entry. A lookup recomputes the hash, walks that bucket's chain, and calls Equals. If the key was mutated after insertion, the lookup goes to a different bucket: the entry is still in the dictionary but can never be found, and it can never be removed by key.
  • Defaults: object.Equals is reference equality. ValueType.Equals compares bits when it can and otherwise uses reflection with boxing. ValueType.GetHashCode may hash only part of the struct, so many distinct values collide.
  • Randomized hashing: string hash codes and HashCode.Combine are randomized per process. Never persist or share a hash code across processes or machines.
  • Comparers: pass StringComparer.Ordinal or OrdinalIgnoreCase to dictionaries keyed by identifiers. The default comparer is ordinal and case-sensitive; culture-aware comparers are slower and can be surprising.

Example

Performance and trade-offs
  • Allocations: a readonly record struct key allocates nothing. A struct key without IEquatable<T> boxes on every Equals call in a dictionary built on older patterns or non-generic collections.
  • CPU: a poor hash, such as one that hashes only TenantId, degrades lookups from constant time toward linear. Records hash every field, so keep keys small.
  • Thread safety: immutable keys are safe to share across threads. A mutated key in a ConcurrentDictionary fails in exactly the same way.
Architectural context
Domain-Driven Design value objects get value equality, which records give you. Entities get identity equality, which a reference or a stable key gives you. EF Core's change tracker uses its own identity map keyed by the primary key, so it does not need you to override Equals on entities. Overriding it is mostly a source of the transient-entity bug above. Message deduplication in a consumer uses a stable message id persisted in SQL, never a GetHashCode.
What breaks in production
Equal objects with different hash codes corrupt dictionaries and sets without any exception. A hash that changes after insertion is a permanent miss and a slow memory leak. A with expression creates a new record; it does not mutate the original, which is what you want for an event and a surprise for someone who thought they were updating an entity.
Say this in the room
Equal objects share a hash code, and the hash must stay stable while the object is in the collection. Records give me that for contracts. Keys are immutable record structs or tuples, with an explicit string comparer. Entities keep identity, and EF's identity map does not need me to override Equals.

1.11The garbage collector: generations, LOH, POH, and GC modes

QExplain how the .NET GC works: generations, what happens during a collection, the Large and Pinned Object Heaps, and Server versus Workstation GC. Our API's memory grows in Kubernetes and p99 spikes every few seconds. Where do you look?

Short answerAllocation is a pointer bump into Gen0. Most objects die young, so frequent, cheap Gen0 collections reclaim them, and survivors are promoted to Gen1 and then Gen2. Objects of 85,000 bytes or more go to the Large Object Heap, which is collected only with Gen2 and not compacted by default. Pinned buffers go to the Pinned Object Heap. ASP.NET Core defaults to Server GC, with one heap per core. For memory growth and p99 spikes, measure allocation rate, percent time in GC, Gen2 and LOH counts, and container limits before you tune anything.

How it works

Each thread has an allocation context, a small range of Gen0 memory. new moves a pointer forward in that range, which costs a few nanoseconds. When the range is exhausted the thread gets another one, and when the Gen0 budget is used up, a collection is triggered. A collection suspends managed threads at safe points and marks everything reachable from roots: stack slots and registers (the JIT records which slots hold references), statics, GC handles (including pinned handles), and the finalization queue. It then plans, and either compacts (relocates survivors and updates every reference) or sweeps (builds free lists). Survivors move to the next generation.

Under the hood
  • Card table and write barrier: a Gen0 collection must not scan all of Gen2. Every reference store goes through a write barrier that marks a "card" when an older object starts pointing at a younger one. Gen0 collections scan only marked cards.
  • Background GC: Gen2 collections are normally background. Marking runs concurrently with your threads, with short pauses at the start and end. Gen0 and Gen1 collections can still run during a background Gen2. Blocking Gen2 collections (memory pressure, induced, or compacting) are the long pauses.
  • Large Object Heap: objects of 85,000 bytes or more, in practice arrays and strings longer than about 42,500 characters, are allocated directly in the LOH. The LOH is logically Gen2, so it is collected only by Gen2 collections. It is swept rather than compacted by default, so fragmentation grows. LOH allocations also clear their memory and count toward a budget that triggers Gen2 collections.
  • Pinned Object Heap (.NET 5+): GC.AllocateArray<byte>(n, pinned: true) places long-lived pinned buffers where they cannot fragment the compacting generations. Kestrel's and the socket layer's memory pools use it.
  • Regions (.NET 7+, 64-bit): the heap is managed as many small regions instead of a few large segments, which lets the GC return memory and rebalance generations more flexibly.
  • Workstation vs Server: Workstation GC has one heap and collects on the thread that triggered the collection. It is lower memory and the default for console and desktop apps. Server GC has one heap and one dedicated, high-priority GC thread per logical core (bounded by container CPU limits). It has higher throughput, much larger budgets, and higher memory use, and it is the default for ASP.NET Core.
  • DATAS (Dynamic Adaptation To Application Sizes) lets Server GC grow and shrink its heap count with load. It is opt-in on .NET 8 and on by default with Server GC on .NET 9+, and it is the main fix for "Server GC uses too much memory in a small pod".
  • Containers: when a memory limit is set, the GC's default heap hard limit is 75 percent of it. Without a limit, Server GC sizes itself to the node.

Example

Performance and trade-offs
  • GC pressure is a function of allocation rate and object lifetime. Short-lived garbage is cheap. Objects that survive just long enough to be promoted (buffered bodies, per-request caches, large DTO graphs held across awaits) are expensive, because they make Gen1 and Gen2 do the work.
  • What to watch: allocation rate (MB/s), percent time in GC (sustained above about 10 percent deserves attention), Gen0/1/2 counts per minute, LOH size, heap size against the container limit, and pause durations from a dotnet-trace GC profile.
  • Server vs Workstation: Server GC gives better throughput and fewer collections at the cost of more memory. In a pod limited to 1 CPU and 512 MB, Workstation GC or DATAS can be the right call. Measure both under load.
  • Thread safety: allocation contexts are per thread, so allocation scales across cores without locks. Collections, however, suspend all managed threads.
Architectural context
GC tuning is almost always allocation reduction in disguise. In an enterprise API the big wins are streaming bodies instead of buffering them, projecting EF queries to small DTOs instead of tracking full graphs, pooling buffers with ArrayPool or RecyclableMemoryStream, bounding caches (MemoryCache with SizeLimit, or HybridCache on .NET 9+), and using the logging source generator. For Kubernetes, set memory requests and limits, let the GC read the limit, enable DATAS, and alert on the gap between GC heap size and container working set, which separates native leaks from managed ones.
What breaks in production
Calling GC.Collect to "fix" memory graphs moves objects into Gen2 early and adds blocking pauses. A 1 MB buffer allocated per request quietly turns every few seconds of traffic into a Gen2 collection, which surfaces as periodic p99 spikes. Server GC in a small pod without DATAS or a hard limit can look like a leak because the GC simply has not needed to collect yet. OOMKilled pods with a modest managed heap point at native memory: unmanaged libraries, unbounded HttpClient handlers, or thread stacks.
Say this in the room
Allocation is a pointer bump into Gen0. The GC marks from roots, compacts survivors, and promotes them, and the card table keeps Gen0 collections from scanning Gen2. Objects of 85K and up go to the LOH, which is collected with Gen2 and not compacted, so per-request large buffers cause Gen2 churn. ASP.NET Core runs Server GC, with DATAS on .NET 9 for containers. I measure allocation rate and time in GC first, and the fix is usually streaming or pooling, not a GC setting.

1.12Disposal and ownership in ASP.NET Core

QWhat is the difference between a finalizer, IDisposable, and IAsyncDisposable? Who disposes what in ASP.NET Core DI, and how do you leak with a transient disposable?

Short answerIDisposable and IAsyncDisposable release resources deterministically: sockets, file handles, connections, pooled buffers. A finalizer is a last-resort safety net the GC runs at an unknown time on one finalizer thread, and it makes the object more expensive to allocate and collect. The rule is that the creator disposes. The DI container disposes what it created, at the end of the scope or at shutdown. A transient disposable resolved from the root provider lives until the app stops.

How it works

Under the hood
  • Finalization: an object whose type overrides Finalize is registered on the finalization queue when it is allocated, which is slower than a normal allocation. When it becomes unreachable, the GC moves it to the f-reachable queue instead of freeing it, so the object and everything it references survive one more collection and usually get promoted. The single finalizer thread runs finalizers in no guaranteed order. A blocking finalizer stalls all finalization, and memory grows. .NET Core and later do not run finalizers at process exit.
  • GC.SuppressFinalize(this) in Dispose removes the object from the finalization queue, so a disposed object is collected like any other.
  • SafeHandle wraps a native handle with a critical finalizer, reference counting, and protection against handle recycling. If you own a native handle, wrap it in a SafeHandle and do not write a finalizer yourself.
  • DI tracking: a scope records every IDisposable or IAsyncDisposable instance it creates, including transients, and disposes them in reverse order when the scope ends. Transients resolved from the root provider are tracked by the root until shutdown. Instances you register yourself with AddSingleton(instance) are not disposed by the container.
  • HttpClient: IHttpClientFactory pools HttpMessageHandler instances and rotates them every 2 minutes by default (HandlerLifetime). Disposing the HttpClient it gives you is harmless. Creating new HttpClient() per call exhausts sockets in TIME_WAIT. A single static client never sees DNS changes unless you set SocketsHttpHandler.PooledConnectionLifetime.

Example

Performance and trade-offs
  • Allocations and GC: a finalizable object costs more to allocate, survives at least one extra collection, and drags its object graph into Gen1 or Gen2. Thousands of finalizable objects per second (undisposed streams, for example) visibly raise GC cost.
  • Latency: an undisposed SqlConnection holds a pool slot until the GC finalizes it. Under load the pool empties, and requests wait for up to the 15-second connect timeout before failing with "timeout expired prior to obtaining a connection from the pool".
  • Thread safety: make Dispose idempotent and safe to call twice. Do not make it thread-safe against concurrent use: using an object while another thread disposes it is a bug in ownership, not a locking problem.
Architectural context
Ownership is an architectural rule: Infrastructure creates connections, streams, and SDK clients, and it either disposes them or registers them with a lifetime in the composition root. Application and Domain code receive dependencies and never dispose them. IAsyncDisposable matters for anything that flushes on close (writers, message producers, ServiceBusClient). The host's shutdown timeout bounds how long that flush may take, so configure HostOptions.ShutdownTimeout to fit it.
What breaks in production
Disposing a DbContext you were injected with breaks the next caller in the same request. Not disposing a connection you opened yourself drains the pool. A using around a stream you were handed closes it for the code that owns it. A transient IDisposable resolved from the root provider, or from app.Services at runtime, is a slow leak that only shows in a heap dump after days.
Say this in the room
The creator disposes. DI disposes what it created at the end of the scope or at shutdown, so I never dispose an injected DbContext, and a singleton creates a scope per unit of work. Finalizers are a safety net for native handles; I use SafeHandle instead and never write a finalizer for managed resources, because it makes every instance survive an extra GC. HttpClient comes from the factory.

1.13Memory leaks in a managed runtime: events, singletons, and caches

QThe GC frees unreachable memory, so how does a .NET service leak? Give me the leaks you have actually seen and how you found them.

Short answerA managed leak is unintended reachability: something long-lived keeps a reference to something that should have died. The usual culprits are a singleton or static event holding subscribers, a captive scoped dependency, an unbounded cache keyed by user input, an undisposed timer or CancellationTokenRegistration on a long-lived token, and closures that capture more than intended. You find them by comparing two heap snapshots and walking gcroot from the growing type.

How it works

A delegate holds a reference to its Target, the subscriber instance. An event is a multicast delegate stored in the publisher. When a long-lived publisher (a singleton, a static, the application lifetime) holds a short-lived subscriber (a scoped handler, a page, a per-request object), the subscriber, and everything it references, lives as long as the publisher. The same mechanism applies to CancellationToken.Register: the callback is stored in the token source until the registration is disposed or the source is cancelled or disposed.

Example

Performance and trade-offs
  • Memory: leaks surface first as GC cost, with more Gen2 collections and longer marks as the live heap grows, and only later as OOM. Rising percent time in GC with flat traffic is an early signal.
  • Snapshot cost: dotnet-gcdump triggers a Gen2 collection and pauses the process for its duration; on a multi-GB heap that is seconds. Take it from one instance, out of rotation if you can.
Architectural context
In DI terms, most leaks are lifetime mismatches: a singleton referencing a scoped object through an event, a callback, or a captured closure. Make lifetimes explicit in the composition root. Turn on ValidateScopes and ValidateOnBuild. Prefer channels or a message bus (in-process MediatR notifications, or MassTransit consumers with their own scope) over .NET events between components with different lifetimes. Caches are a product decision with a size, a TTL, and a key normalization rule.
What breaks in production
Leaks are invisible in short tests and in development, where processes restart constantly. They appear after days in production as a sawtooth that never returns to baseline. Restarting pods on a schedule hides them until traffic grows. Static ConcurrentDictionary "caches" with no eviction are the most common leak in enterprise codebases.
Say this in the room
A managed leak is something long-lived still referencing something short-lived: a singleton event holding scoped subscribers, a registration on the app-lifetime token, or an unbounded cache keyed by user input. I compare two gcdumps under load and run gcroot from the type that grows. The fix is usually a lifetime fix, plus a size limit on every cache.

1.14Boxing, and when it matters on a Web API

QWhat is boxing, where does it hide in modern C#, and how do you decide whether it is worth fixing?

Short answerBoxing copies a value type into a new heap object so it can be treated as object or as an interface. Unboxing checks the type and copies the value back out. One box is noise. A box per call on a hot path, such as logging arguments, non-generic collections, or interface calls on structs, shows up as allocation rate. Fix it when a profile says so, usually with generics, typed logging, or IEquatable<T>.

How it works

A box is a full heap object: header, MethodTable pointer, and a copy of the value, so 24 bytes for a boxed int on x64. Mutating the box does not change the original, and the original does not change the box. Generics avoid boxing because the JIT generates specialized code for each value-type instantiation; List<int> stores raw ints. Calls on a generic T constrained to an interface compile to a constrained. call that dispatches directly without boxing.

Under the hood
  • Hidden boxing sources: params object[] APIs (classic logging calls, string.Format), non-generic collections (ArrayList, Hashtable), casting a struct to an interface (IComparable c = 42), struct Equals(object) in a collection when the struct does not implement IEquatable<T>, foreach over a List<T> typed as IEnumerable<T> (the struct enumerator is boxed), and Enum operations on older runtimes.
  • No longer boxing: string interpolation since C# 10 (DefaultInterpolatedStringHandler formats value types directly into a pooled buffer), and Enum.HasFlag, which the JIT treats as an intrinsic.

Example

Performance and trade-offs
  • Allocations: about 24 bytes per boxed int or long and 32 per boxed decimal. At 2,000 requests a second with five log lines of three value arguments each, the classic logging API allocates around 30,000 short-lived objects a second for nothing.
  • CPU: boxing and unboxing are cheap individually. The cost is GC pressure, plus the lost inlining when a call goes through an interface instead of a constrained generic.
  • Priority: a CRUD endpoint spends milliseconds in SQL and microseconds on boxing. Fix boxing in parsers, serializers, logging on hot paths, and tight loops, after a profile shows it.
Architectural context
Make the logging source generator the team standard for anything at Information level or below on request paths. It also gives event ids that operations can alert on. In shared libraries, prefer generic APIs with interface constraints over object parameters. In domain code, do not contort the design to avoid a box: clarity wins until the profiler disagrees.
What breaks in production
Casting a boxed int to long throws InvalidCastException; unboxing must name the exact type. A mutable struct boxed into an interface and mutated through it changes the box, not the original. Micro-optimizing boxing while a list query scans a million rows does not move p95.
Say this in the room
Boxing wraps a value type in a heap object. Generics and constrained calls avoid it. The modern hiding places are params object arrays, which is why I standardize on the LoggerMessage source generator, plus non-generic collections and struct-to-interface casts. I fix boxing when a trace shows allocation pressure, not on principle.

1.15Shared state, lock, and why lock cannot cross await

QHow do you protect shared state in a service? Why can you not await inside a lock, what do you use instead, and what changes when you scale to two instances?

Short answerPrefer no shared mutable state: immutable data, request-scoped objects, or state in SQL. Inside one process, use Interlocked for counters, ConcurrentDictionary for independent keys, lock (or .NET 9's System.Threading.Lock) for short synchronous critical sections, and SemaphoreSlim.WaitAsync when the critical section awaits. A lock is per process: two App Service instances have two locks, so cross-instance uniqueness and ordering belong in the database.

How it works

Under the hood
  • lock / Monitor: the first, uncontended acquire stores the owning thread id in the object header (a thin lock). On contention, the lock inflates into a sync block with a wait queue; waiters spin briefly, then block. The lock is reentrant and thread-affine: only the thread that entered may exit. That is why the compiler forbids await inside lock, since the continuation may resume on a different thread. lock also emits memory barriers, so writes inside it are visible to the next owner.
  • System.Threading.Lock (.NET 9, C# 13): a dedicated lock type. When you lock on it, the compiler uses its faster EnterScope API instead of Monitor.
  • SemaphoreSlim: a count plus a queue of waiters. WaitAsync returns a task, so no thread blocks while waiting. It is not reentrant and not thread-affine, and it does not guarantee FIFO order. Release it in finally, exactly once per successful wait.
  • Interlocked: single CPU atomic instructions (compare-and-swap, add). They are lock-free, but cover one memory location at a time.

Example

Performance and trade-offs
  • CPU: an uncontended lock costs about 20 nanoseconds. A contended one costs a context switch, measured in microseconds. Keep critical sections short, with no I/O, logging, or allocation-heavy work inside.
  • Threads: a waiter on lock blocks a pool thread. A waiter on SemaphoreSlim.WaitAsync holds no thread. Under contention that difference is starvation or no starvation.
  • Scale-out: any in-process lock or static counter is wrong on the second instance. The fix is a database constraint, a sequence, an atomic UPDATE ... OUTPUT, sp_getapplock, or a blob lease, each with its own latency cost.
Architectural context
The concurrency model of an enterprise service is usually: stateless instances, a request-scoped DbContext, optimistic concurrency (rowversion) for aggregates, unique constraints for business identity, and idempotency keys for retries. In-process synchronization is reserved for caches, token refresh, and rate limiting inside one instance. For cross-instance single-flight caching, .NET 9's HybridCache adds stampede protection per instance on top of a distributed L2.
What breaks in production
A static mutable field looks fine on a single-instance dev box and splits the brain when the platform scales out. A SemaphoreSlim released more times than it was acquired throws SemaphoreFullException. A release outside finally leaks the gate on the first exception, and every later caller waits forever. Taking a lock and then calling code that blocks on a task deadlocks under load.
Say this in the room
No shared mutable state if I can avoid it. In one process: Interlocked for counters, lock on a private object for short synchronous sections, and SemaphoreSlim.WaitAsync when the section awaits, because Monitor is thread-affine and the continuation may resume on another thread. None of that coordinates two instances. Uniqueness and ordering go to SQL.

1.16Channels, concurrent collections, and CPU-bound versus IO-bound work

QWhen do you use System.Threading.Channels versus ConcurrentQueue or ConcurrentBag? How do you handle CPU-bound work in an ASP.NET Core service, and what is wrong with Parallel.ForEach with an async lambda?

Short answerA bounded Channel<T> is the async producer/consumer primitive: writers await when it is full, which is backpressure, and readers await when it is empty, without blocking threads. ConcurrentQueue is a lock-free FIFO with no waiting. ConcurrentBag is optimized for threads that add and take their own items, so it is a poor work queue. I/O-bound work is async end to end. CPU-bound work runs on threads with a bounded degree of parallelism, ideally off the request path. Parallel.ForEach with an async lambda creates async void delegates and returns before the work finishes.

How it works

Under the hood
  • Channels: Channel.CreateBounded with BoundedChannelFullMode.Wait makes WriteAsync wait for space; DropOldest, DropNewest, and DropWrite shed load instead. SingleReader and SingleWriter enable cheaper internal synchronization. ReadAllAsync exposes the channel as IAsyncEnumerable<T>. Reads and writes return ValueTask backed by pooled sources.
  • ConcurrentDictionary: reads are lock-free; writes take one of a set of striped locks. GetOrAdd(key, factory) can run the factory more than once under a race, and only one result is stored. Count and ToArray acquire all locks, so calling them on a hot path serializes the dictionary.
  • ConcurrentBag: keeps a list per thread and steals from other threads when its own is empty. It is fast when the same thread both adds and takes (an object pool) and slow and unordered as a cross-thread queue.
  • BlockingCollection: blocks threads on Take. It predates async, and in a server it ties up pool threads.

Example

Performance and trade-offs
  • Allocations: channel operations are mostly allocation-free thanks to pooled ValueTask sources. A bounded channel caps memory at capacity times item size.
  • Throughput vs latency: CPU-bound work inside requests competes with request processing for the same cores and threads, which drives p99 up. Moving it to a bounded background worker trades the latency of that job for the latency of everything else.
  • Thread safety: channels and concurrent collections make each operation atomic, not the sequence. Check-then-act across two calls is still a race.
Architectural context
An in-process channel is a buffer, not a queue: it vanishes on restart, deployment, or crash. Use it for best-effort, rebuildable work such as thumbnails, cache warming, or telemetry batching. For business work, such as an email that must be sent or a payment that must be captured, use the transactional outbox and Service Bus, with MassTransit or the SDK, so the work is durable, retried, and dead-lettered. CPU-heavy work that scales differently from the API (PDF rendering, image processing) belongs in its own Function or worker deployment.
What breaks in production
An unbounded channel or queue under a burst grows until the pod is OOMKilled. A DropOldest mode used for business events silently loses data. A worker loop without a try/catch per item ends the BackgroundService, and since .NET 6 an unhandled exception there stops the host by default. Work queued in memory at shutdown is lost unless you drain it within the host's shutdown timeout.
Say this in the room
For async producer/consumer I use a bounded channel, so producers wait when it is full and nothing blocks a thread. ConcurrentBag is for same-thread pooling, not queues. I/O is async end to end; CPU-heavy work goes to a bounded background worker or its own service, never Task.Run inside the request. And anything that must survive a restart goes through the outbox, not a channel.

1.17String immutability

QWhy are strings immutable in .NET, what does that cost in a loop, and what are the modern zero-copy options?

Short answerA string is an immutable, length-prefixed UTF-16 array. Immutability makes strings safe to share across threads, to intern, and to use as dictionary keys, but every change allocates a new string. Concatenation in a loop is quadratic. Use StringBuilder for loops, interpolation for a few pieces, string.Create or span formatting for hot paths, and write large outputs straight to a stream instead of building a string.

How it works

Under the hood
  • Layout: header, MethodTable pointer, an int length, the UTF-16 characters, and a null terminator for interop. That is 2 bytes per character, so a string longer than about 42,500 characters lands on the Large Object Heap.
  • Interning: literals are interned per process; string.Intern interns at runtime, and interned strings are never collected. Do not intern user input.
  • StringBuilder keeps a linked list of character chunks and copies once in ToString(). Give it a capacity when you know the rough size.
  • Interpolation (C# 10+) lowers to DefaultInterpolatedStringHandler, which formats directly into a pooled buffer, with no string.Format parse and no boxing. string.Create(provider, stackalloc char[n], $"...") formats into a stack buffer and allocates only the result.
  • Comparison: == is ordinal. ToLower() and ToUpper() allocate and are culture-sensitive (the Turkish dotless i). Use StringComparison.OrdinalIgnoreCase for identifiers.

Example

Performance and trade-offs
  • Allocations: += in a loop of n items copies O(n²) characters. With 50,000 lines that is gigabytes of copying, and strings past 85 KB land on the LOH every iteration.
  • CPU: ordinal comparison is a vectorized memory compare. Culture-aware comparison goes through ICU on Linux and is far slower.
  • Thread safety: strings are immutable, so they are always safe to share. A StringBuilder is not thread-safe.
Architectural context
Make CultureInfo.InvariantCulture and ordinal comparison the defaults for machine-readable data (files, keys, logs, identifiers), enforced by analyzers CA1305, CA1307, CA1309, and CA1310. Keep culture-aware formatting at the UI edge. For high-volume text in Infrastructure (exports, webhooks), write UTF-8 directly to a stream or PipeWriter.
What breaks in production
Building a million-row export with += allocates its way into a timeout. Formatting decimals with the server's culture breaks partner files after a region migration. Concatenating SQL with user input is an injection vulnerability, however clean the string building is.
Say this in the room
Strings are immutable UTF-16 arrays: safe to share, but every change allocates. In loops I use StringBuilder; for hot formatting, string.Create or interpolation into a stack buffer; for big exports, a stream writer. Identifiers compare ordinal ignore-case, machine formats use invariant culture, and SQL is always parameterized.

1.18JIT compilation: tiered compilation, Dynamic PGO, ReadyToRun, and Native AOT

QHow does .NET turn IL into machine code? Explain tiered compilation and Dynamic PGO, and when you would choose ReadyToRun or Native AOT for a service.

Short answerMethods are compiled on first call. Tier 0 compiles quickly with minimal optimization. Methods called often (30 calls by default) are recompiled in the background at Tier 1 with full optimization. Since .NET 8, Dynamic PGO instruments Tier 0 code so Tier 1 can devirtualize and inline using real types and branch frequencies. ReadyToRun ships precompiled code for faster startup and still tiers up. Native AOT compiles everything ahead of time: fastest startup and smallest memory, no JIT, and strict limits on reflection and dynamic code.

How it works

Under the hood
  • First call: every method starts as a stub that calls the JIT. The JIT compiles the IL, patches the stub, and later calls jump straight to native code.
  • Tier 0 skips most optimizations so startup is fast. A call-counting stub counts invocations. After the threshold, and after a short delay in which no new Tier 0 methods appear, the method is queued for Tier 1 recompilation on a background thread. Calls switch to the new code when it is ready.
  • OSR (on-stack replacement, .NET 7+): a Tier 0 method stuck in a long loop can transfer to optimized code mid-loop, so methods with loops no longer have to skip Tier 0.
  • Dynamic PGO (on by default since .NET 8): an instrumented Tier 0 records which concrete types arrive at virtual and interface calls and which branches are hot. Tier 1 emits guarded devirtualization (if the receiver is UsTaxCalculator, inline its body; otherwise do the interface call), hot/cold block layout, and better register allocation.
  • ReadyToRun (R2R): precompiled native code embedded alongside the IL. It is used at startup instead of Tier 0, hot methods are still rejitted at Tier 1 with PGO, and it makes files bigger. The framework itself ships as R2R.
  • Static readonly fields: by the time Tier 1 runs, static constructors have usually run, so the JIT can treat static readonly values as constants and fold away branches on them.
  • Native AOT: the whole app is compiled and trimmed at publish time. There is no JIT, so no Reflection.Emit and no runtime code generation, and reflection is limited to what the trimmer can see. It needs source generators (System.Text.Json, configuration binding, logging, the Minimal API Request Delegate Generator). ASP.NET Core supports it for Minimal APIs, gRPC, and worker services. It has no Dynamic PGO, so peak throughput can be lower than JIT plus PGO.

Example

Performance and trade-offs
  • Startup: JIT with Tier 0 is fast. R2R is faster. Native AOT is fastest, with the smallest working set; it is often several times better on cold start and memory.
  • Steady state: JIT with Dynamic PGO usually gives the best peak throughput, because it optimizes using the types that actually show up. AOT relies on static analysis.
  • Warm-up: the first seconds after a deploy or scale-out run Tier 0 or R2R code with cold caches. That is why p99 is high right after a slot swap, and why warm-up requests and readiness probes matter.
  • Build cost: R2R and AOT lengthen publishes and produce platform-specific output, so you need one build per runtime identifier.
Architectural context
Long-running APIs on App Service or Kubernetes: JIT plus PGO, optionally R2R to shorten scale-out warm-up. Azure Functions on Consumption, sidecars, and small webhooks: consider Native AOT when the dependency graph supports it. EF Core has only partial AOT support (precompiled queries are experimental in EF Core 9+), and MVC and many reflection-heavy libraries do not support it. Benchmarks must run through BenchmarkDotNet, which warms up so you measure Tier 1 code.
What breaks in production
Turning off tiered compilation slows startup and does not fix the real cause of slow first requests (cold caches, connection pools, lazy DI singletons). AOT publishing without fixing trim warnings ships a binary that fails at runtime on a reflection path such as a JSON type that was trimmed away. AggressiveOptimization sprinkled on hot methods disables the very PGO that would have made them fast.
Say this in the room
IL is jitted on first call at Tier 0, and hot methods are recompiled at Tier 1 in the background. Since .NET 8, Dynamic PGO feeds real types into Tier 1 for guarded devirtualization and inlining. R2R ships precompiled code for startup and still tiers up. Native AOT removes the JIT for the fastest cold start but restricts reflection. I use JIT plus PGO for APIs and consider AOT for small scale-to-zero services.

1.19Fundamentals they still ask

These are short, but each one has a mechanism and a decision behind it, not just a definition. If the panel stops at the definition, give the first sentence and stop. If they push, the second paragraph is the follow-up.

Abstract class versus interface

An abstract class shares state and implementation, and it uses up the single base-class slot. An interface is a contract a type can implement alongside many others. Since C# 8, interfaces can carry default method implementations, and since C# 11 they can declare static abstract members, the basis of generic math and of IParsable<T>.

Under the hood: a virtual call indexes into the type's vtable in its MethodTable, which is one indirection. An interface call goes through virtual stub dispatch, a call-site cache that is slightly more expensive until it settles. sealed classes let the JIT devirtualize both.

Say this in the room
Interface for a swappable dependency; abstract class only when subclasses genuinely share state and an algorithm. Sealed by default, so the JIT can devirtualize.

virtual, override, and new

override replaces a virtual method in the vtable slot, so every caller gets the derived behavior regardless of the variable's type. new adds a separate slot that hides the base member, so a call through a base reference still runs the base method. Hiding makes behavior depend on the compile-time type, which is the bug a reviewer catches.

Say this in the room
override replaces the vtable slot for every caller; new hides the method and surprises anyone holding the base type. I do not ship new on methods.

const, readonly, and static

const is a compile-time literal that the compiler copies into every calling assembly, so changing a public const breaks consumers until they recompile. readonly fields are assigned once, in the constructor. static means one per process (per AppDomain on .NET Framework), not one per server farm.

Under the hood: at Tier 1 the JIT treats an initialized static readonly primitive or reference as a constant, so if (Features.UseNewPricing) on a static readonly bool costs nothing after tier-up. That makes it a free feature switch, but it cannot be changed at runtime.

Say this in the room
const is compile-time and a versioning trap across assemblies. readonly is fixed after construction. static is per process, not per farm.

First, FirstOrDefault, Single, and SingleOrDefault

First throws on an empty sequence; FirstOrDefault returns default. Single throws unless there is exactly one match. On a primary or unique key, SingleOrDefault turns a duplicate (a data defect) into a loud failure.

Under the hood: EF Core translates First to SELECT TOP(1) and Single to SELECT TOP(2), so it can detect a second row. Both are cheap on an indexed key. Without an OrderBy, First returns an arbitrary row.

Say this in the room
First is any match and needs an OrderBy to be deterministic. Single is exactly one, using TOP(2) in SQL. On keys I use SingleOrDefault so duplicates cannot hide.

throw versus throw ex

throw; rethrows the current exception and keeps its stack trace. throw ex; resets the trace to your catch block, so the log points at the wrong code. To add context, wrap the original as the inner exception. To rethrow outside a catch block (for example after crossing threads), use ExceptionDispatchInfo.Capture(ex).Throw(), which is what await does internally.

Say this in the room
throw keeps the stack and throw ex resets it. I wrap only when I am adding context, keep the inner exception, and use exception filters so non-matching cases do not unwind.

IEnumerable, ICollection, IList, and IReadOnlyList

IEnumerable<T> may be lazy and may not know its count; ICollection<T> adds Count and mutation; IList<T> adds indexing; IReadOnlyList<T> is the honest return type for "you may index, you may not add". Accept the smallest interface, and return a materialized, read-only shape.

Under the hood: LINQ checks at runtime for ICollection<T> and IList<T> to shortcut Count() and ElementAt. TryGetNonEnumeratedCount (.NET 6+) gets the count without enumerating when it can.

Say this in the room
Accept the smallest interface; return a materialized IReadOnlyList so callers never enumerate a query twice.

Covariance and contravariance

out T marks a producer interface as covariant (IEnumerable<string> works where IEnumerable<object> is expected); in T marks a consumer as contravariant (Action<object> works where Action<string> is expected). List<T> both produces and consumes, so it is invariant.

Under the hood: variance on generic interfaces is checked at compile time and costs nothing at runtime. Array covariance, a legacy feature, is checked at runtime: every write to a reference-type array element pays a type check, and a wrong type throws ArrayTypeMismatchException.

Say this in the room
out is producer and covariant, in is consumer and contravariant, lists are invariant. Array covariance is the runtime-checked legacy trap.

Nullable reference types

string? may be null and string should not be. These are compile-time annotations and flow analysis only; the IL type is the same. Enable them, treat the warnings as errors on new projects, and reserve ! for proven invariants, with a comment.

Say this in the room
Nullable reference types are a compile-time contract. I enable them, treat warnings as errors, and require a reason next to every suppression.

Partial classes and source generators

The compiler merges partial declarations into one type. Incremental source generators (Roslyn IIncrementalGenerator) emit partial code at compile time, which is how [LoggerMessage], [JsonSerializable], [GeneratedRegex], configuration binding, and the Minimal API Request Delegate Generator remove reflection at runtime. Keep hand-written rules out of generated files.

Say this in the room
Partial merges files. Source generators move reflection to compile time, which is faster and AOT-safe. Hand-written rules live in files the generator does not own.

2.1Single responsibility

QWhat does single responsibility mean in an ASP.NET Core API? Show me a controller that violates it and the shape you would refactor it into.

Short answerA type should have one reason to change. In a Web API that usually means the endpoint translates HTTP, a handler runs the use case, the domain enforces invariants, and infrastructure talks to SQL and the bus. A class that validates the body, calculates tax, writes SQL, and sends email has four reasons to change, and testing the tax rule means booting HTTP.

Example

Performance and trade-offs
Splitting costs nothing at runtime: a scoped handler resolved from DI is one cached factory call and one allocation per request. The real cost is navigation. Each extra hop is a file the next developer opens, so split where a second caller or a second reason to change already exists.
Architectural context
This is the seam that Clean Architecture formalizes: Api depends on Application, Application on Domain, and Infrastructure implements Application's ports. It is also what lets the same CreateOrderHandler be invoked by an HTTP endpoint, a MassTransit consumer, and a nightly import without duplicating the rule.
What breaks in production
A controller that owns business rules cannot be tested without the host, and every new channel (queue consumer, retry job, admin tool) copies the rule. A handler that also formats ProblemDetails gives the error catalog two owners. Splitting a twenty-line endpoint into five projects is the opposite failure.
Say this in the room
The endpoint translates HTTP, the handler runs the use case, the domain enforces the rule, and infrastructure does I/O. I collapse those on a tiny endpoint and say so. I split them when a second caller needs the same rule.

2.2Open/closed

QHow do you apply open/closed without building a plugin system? Show me adding a carrier without touching checkout.

Short answerA new behavior should be a new class behind an interface you already have, not another branch in a growing switch. In .NET 8+ keyed services make "pick an implementation by key" a one-line registration. Two branches of an if do not deserve a registry; extract when the set actually grows.

Example

Performance and trade-offs
A keyed lookup is a dictionary hit inside the container: nanoseconds. It does make the policy less visible, because the set of carriers lives in Program.cs rather than in the method.
Architectural context
Open/closed is how payment providers, tax engines, and notification channels stay pluggable in an enterprise checkout. Each adapter lives in Infrastructure, is registered by key in the composition root, and is tested independently. Configuration selects the key; code does not change.
What breaks in production
A registry nobody can see from the handler hides the policy. A switch that is the policy, sitting in one tested method, is often the better design. Resolving keyed services through IServiceProvider everywhere is the service-locator anti-pattern; keep it in one factory or quoter.
Say this in the room
A new provider is a new class plus a registration when the set actually grows; keyed services make that one line in .NET 8. I do not invent a plugin system for two branches of an if.

2.3Liskov substitution

QGive me a Liskov violation you would catch in review on a .NET backend.

Short answerA subtype must keep the promises of the type it replaces: no stronger preconditions, no weaker postconditions, and no new exceptions for operations the base type supports. The common .NET violation is an implementation that throws NotSupportedException for a method on its interface. The fix is a smaller interface.

Example

Architectural context
In CQRS the read and write sides are separate interfaces from the start, so a read replica, a cache, or a projection can implement the read side honestly. Contract tests run against every implementation of an interface, including fakes, to prove they all behave the same way.
What breaks in production
Tests written against the base type pass with the production subtype and fail with the stub, or the reverse. Support then finds a 500 where the contract promised a result.
Say this in the room
A subtype keeps the promises of the type it replaces. If a method does not make sense for an implementation, it does not belong on that interface. NotSupportedException from an override is the smell, and splitting into read and write interfaces is the fix.

2.5Dependency inversion

QExplain dependency inversion versus dependency injection. Where should the IOrderStore interface live, and what does the DI container actually do at runtime?

Short answerDependency inversion is a design rule: high-level policy owns the abstraction, and low-level detail implements it, so the interface lives in Application and the EF implementation lives in Infrastructure. Dependency injection is the mechanism: the container builds the object graph from registrations in the composition root.

How it works

Under the hood
Microsoft.Extensions.DependencyInjection builds a call site for each service the first time it is resolved: which constructor to call, the lifetime, and the dependencies. After a few resolutions, it compiles that call site into a delegate (using Reflection.Emit where available, expression trees otherwise), so later resolutions are close to hand-written new calls. Scoped instances are cached in the scope's dictionary, singletons in the root. ValidateOnBuild builds every call site at startup, so a missing registration fails the deployment, not the first request.

Example

Performance and trade-offs
After warm-up, resolution costs are tiny: a compiled delegate, plus a dictionary lookup for scoped services. The startup cost of ValidateOnBuild is real on large graphs but buys a fail-fast deployment. Avoid resolving from IServiceProvider inside loops; inject the dependency once.
Architectural context
The compiler enforces inversion only if the project references point inward: Infrastructure references Application, never the reverse. Making adapters internal and exposing a single AddOrdersInfrastructure extension keeps the Api from reaching around the port.
What breaks in production
An abstraction that mirrors every DbSet method is a pass-through, not inversion. A handler that news up a SqlConnection welds policy to adapter, and a tax-rule test then needs a database.
Say this in the room
Inversion means the use case owns the interface and infrastructure implements it; injection is how Program.cs wires them. The container compiles a factory per service, so resolution is cheap after warm-up, and ValidateOnBuild makes a missing registration fail the deploy.

2.6Singleton, the interview implementation, and the one you ship

QWrite a thread-safe singleton. Then tell me why you would not ship that in ASP.NET Core.

Short answerThe static-readonly-field singleton is thread-safe because the CLR runs a type initializer exactly once, under a lock. Lazy<T> gives lazy creation. In ASP.NET Core you register AddSingleton instead, so the lifetime is visible and replaceable in tests. Either way, a singleton must be thread-safe, must hold no per-request data, and must not capture scoped services. And it is one per process, not one per farm.

Example

Performance and trade-offs
Reads of an immutable dictionary swapped by reference are lock-free and allocation-free, the ideal shape for a hot singleton. Refreshing allocates one new dictionary every five minutes, which is noise.
Architectural context
Singletons hold expensive, thread-safe, shareable things: HttpClient handlers (via the factory), ServiceBusClient, compiled caches, TimeProvider, and options monitors. Cross-instance uniqueness, counters, and locks belong in SQL or a distributed store.
What breaks in production
A hand-written static singleton becomes ambient state that tests cannot replace without a reset hook. A singleton DbContext is disposed after the first request, or shared across threads and corrupting the change tracker. A lock inside the singleton still does not coordinate the second instance.
Say this in the room
I can write the static or Lazy singleton; the type initializer makes it thread-safe. I ship AddSingleton for a thread-safe type with no request data. If it needs the database it creates a scope per refresh, and it swaps an immutable snapshot by reference so readers never lock.

2.7Factory versus Strategy at checkout

QWhat is the difference between a factory and a strategy? Show both in a tax calculation.

Short answerA factory decides which object to build and how to construct it. A strategy is an interchangeable algorithm behind an interface. At checkout the tax rule is the strategy; the thing that picks the rule for a country is the factory. With fixed sets, keyed DI often replaces the hand-written factory.

Example

Architectural context
IHttpClientFactory is the factory worth naming in .NET because it owns a real decision: handler pooling and lifetime. MassTransit's consumer factories and EF Core's IDbContextFactory<T> are the same idea: they own construction and lifetime so callers do not.
What breaks in production
A strategy interface with one implementation and a factory that only forwards new adds two types and no test value. A factory that contains both the tax rule and the construction rule becomes the god class the strategy was meant to prevent.
Say this in the room
A factory builds; a strategy behaves. Tax is a strategy, and picking the strategy per country is the factory. I extract them when the third country arrives or the rule needs its own tests.

2.9Repository and unit of work with EF Core

QWould you put a generic repository on top of EF Core? If not, what boundary would you use?

Short answerDbContext already is a unit of work (it tracks changes and commits them in one transaction), and DbSet already is a repository. A generic IRepository<T> hides Include shapes, projections, split queries, ExecuteUpdate, and compiled queries, and it usually leaks IQueryable anyway. A focused store per aggregate (IOrderStore.FindAsync, AddAsync) is a real boundary; in a small service, inject the DbContext into the handler.

How it works

Under the hood
SaveChanges runs DetectChanges, orders the commands by dependency, batches them (SQL Server batches up to 42 statements per round trip by default), and wraps them in one transaction unless an ambient or explicit transaction exists. Two SaveChanges calls are two transactions. A "unit of work" wrapper that calls SaveChanges inside every Add defeats the batching and the atomicity.

Example

Performance and trade-offs
The generic repository's GetAllAsync and Get(predicate) return tracked full entities, which is the most expensive EF shape. Focused query methods return projections with AsNoTracking, and can be compiled queries on hot paths.
Architectural context
In CQRS, the command side uses an aggregate store and the query side uses query objects or Dapper-style SQL that return DTOs, with no repository at all. If the team insists on a repository, constrain it to aggregates and forbid IQueryable on its surface.
What breaks in production
A generic repository that saves inside Add commits the order and loses the outbox row. Two SaveChanges calls without an explicit transaction can commit half a use case. A wrapper around one DbContext called UnitOfWork adds a type and no behavior.
Say this in the room
DbContext is the unit of work and DbSet is a repository. I defend a thin store per aggregate, or the DbContext directly in a small service. I do not defend IRepository of T as a house style, because it makes bad queries harder to see and good ones impossible to write.

2.10CQRS and Mediator on a real API

QExplain CQRS and the Mediator pattern. When does MediatR earn its place, what does it cost, and what changed about using it?

Short answerCQRS separates the write model (commands that change an aggregate) from the read model (queries that return DTOs). On most APIs that is two handlers against one database, not two databases. Mediator dispatches a request object to exactly one handler through a pipeline of behaviors (validation, transactions, logging). It costs indirection and a little allocation per call. Since mid-2025, MediatR's newer versions ship under a commercial license, so adopting it is now a cost decision too.

How it works

Under the hood
IMediator.Send looks up a cached wrapper for the request type, resolves the handler and every registered IPipelineBehavior<TRequest, TResponse> from the current scope, and composes them into a chain of delegates around the handler. Per call, that is a handful of allocations (the delegate chain and closures) and one DI resolution per behavior. That is negligible next to I/O, but it matters in tight loops, and it hides the call graph from F12.

Example

Performance and trade-offs
  • Allocations: a few small objects per Send, plus one resolution per behavior. Fine per request, wasteful inside loops.
  • Latency: microseconds. The real cost is navigation and debugging: stack traces full of behavior frames.
  • Read/write split: a separate read store (a projection table, a search index) adds eventual consistency. The read side lags the write side, and the UI must tolerate that.
Architectural context
MassTransit's mediator, Wolverine, or a twenty-line hand-written dispatcher are alternatives. Choose once per estate and write it down, including the licensing position. Whatever the tool, the team rules are what keep it healthy: commands change state and queries do not; handlers do not call handlers; cross-cutting work is a behavior; the transaction boundary is the command handler.
What breaks in production
Handlers calling handlers hide the transaction boundary and create cycles. A query handler that saves a "last viewed" stamp makes GET unsafe and uncacheable. Two databases on day one double the operational load before the domain has stabilized.
Say this in the room
CQRS is separate read and write shapes, on one database until they actually diverge. Mediator is a dispatcher I adopt when validation and transaction behaviors earn the indirection; it costs a few allocations and F12. MediatR's license changed, so it is a budget line now. Handlers never call handlers.

2.11Options: which interface you inject

QExplain IOptions, IOptionsSnapshot, and IOptionsMonitor. How do you make a bad setting fail the deployment instead of the first order?

Short answerBind a section to a typed class and validate it at startup with ValidateOnStart, so a missing or invalid value fails the slot before traffic arrives. IOptions<T> is a singleton computed once. IOptionsSnapshot<T> is scoped and recomputed per request. IOptionsMonitor<T> is a singleton that tracks reloads and raises change notifications. Inject the one that matches the consumer's lifetime.

How it works

Under the hood
Configuration providers (JSON, environment variables, Key Vault, App Configuration) produce a key-value tree. OptionsFactory<T> creates the instance, runs every Configure and PostConfigure, then runs validators. IOptionsMonitor caches per name in an OptionsCache and listens to the configuration's change token; on reload it evicts the cache and calls OnChange listeners. IOptionsSnapshot recomputes, and therefore allocates and binds, on every scope, which is a measurable per-request cost on large options classes. The configuration binder source generator (.NET 8, EnableConfigurationBindingGenerator) removes the reflection.

Example

Performance and trade-offs
IOptions costs nothing per request. IOptionsSnapshot rebinds per scope. That is fine for small classes, but measurable on hot endpoints with large option graphs; prefer IOptionsMonitor.CurrentValue there.
Architectural context
Secrets come from Key Vault through configuration, never from appsettings in the repo. Feature flags come from Azure App Configuration or Microsoft.FeatureManagement, not from hand-rolled options. The Domain never sees IConfiguration; it receives values or typed options through Application.
What breaks in production
Reading IConfiguration["Pricing:Rate"] deep in the domain scatters string keys. Missing ValidateOnStart lets the process boot and crash on the first order. Injecting IOptionsSnapshot into a singleton fails scope validation, and if validation is off it is a captive dependency.
Say this in the room
I bind a typed options class with data annotations and ValidateOnStart, so a bad setting fails the slot before swap. IOptions is fixed, IOptionsSnapshot is per request, and IOptionsMonitor is for singletons that watch changes. Secrets come from Key Vault through configuration.

2.12Result or throw

QWhen do you return a Result and when do you throw? What does an exception actually cost?

Short answerThrow for defects and for conditions the caller cannot reasonably handle: broken invariants, missing configuration, I/O failure after retries. Return a result for expected business outcomes: validation failures, insufficient stock, a duplicate idempotency key. Then map results to 4xx and unexpected exceptions to a 500 from one global handler. Exceptions are slow by design: a throw captures a stack trace and unwinds frames, costing microseconds, compared with nanoseconds for a return.

How it works

Under the hood
A throw allocates the exception, captures the stack trace (walking frames), and runs a two-pass unwind: one pass to find a matching handler (running exception filters) and one to run finally blocks. .NET 9 moved exception handling to a managed implementation that is substantially faster than before, but throwing is still orders of magnitude slower than returning, and it allocates. Using exceptions for control flow in a hot validation path is measurable at load.

Example

Architectural context
The Domain throws on invariant violations, which are defects. The Application layer returns result types for expected outcomes. The Api maps results with a switch expression and lets one IExceptionHandler produce 500s with a trace id. MassTransit consumers follow the same split: expected outcomes are handled, and exceptions trigger retry policies and, eventually, the error queue.
What breaks in production
A Result that wraps bugs hides them from telemetry and from crash alerts. An exception for "coupon does not apply" trains clients to retry a 500. Catching Exception and returning success is how a failed save becomes a 200 and a lost order.
Say this in the room
Expected business outcomes return a result and become a 4xx. Defects throw, and one IExceptionHandler turns them into a 500 with a trace id. A throw costs microseconds and a stack walk, so I do not use exceptions for validation on hot paths.

3.1The pipeline for a secured POST

QWalk me through everything that happens between Kestrel accepting a connection and your handler running for an authenticated POST /orders. Why does middleware order matter?

Short answerKestrel parses the request into an HttpContext and invokes a single RequestDelegate, which is the middleware chain you registered, composed in order. Exception handling goes outermost, then HTTPS, routing (which selects the endpoint), CORS, authentication (which builds the principal), authorization (which evaluates the endpoint's policy), rate limiting, and finally the endpoint: model binding, filters, your handler, and the result writer. Order matters because each middleware can only see what earlier ones set up, and only wraps what comes after it.

How it works

Under the hood
  • Composition: each app.Use... registers a Func<RequestDelegate, RequestDelegate>. At startup ApplicationBuilder.Build() folds them in reverse, so the first registered becomes the outermost delegate. Per request there is no list to walk: it is a chain of direct delegate calls.
  • Routing (UseRouting) matches the URL against the endpoint data source and sets HttpContext.GetEndpoint(), including its metadata ([Authorize], CORS policy, rate-limit policy). Middleware between UseRouting and the endpoint can read that metadata, which is why CORS, authorization, and rate limiting go there. WebApplication adds UseRouting and the endpoint execution automatically if you do not.
  • Authentication runs the default scheme's handler (JwtBearer: read the header, validate the signature against cached signing keys, check issuer, audience, and lifetime) and sets HttpContext.User. Failure leaves an anonymous user; it is authorization that then challenges with 401 or forbids with 403.
  • Convention-based middleware is constructed once, so it is effectively a singleton. Constructor-injected scoped services become captive. Scoped dependencies go into InvokeAsync parameters, or the middleware implements IMiddleware and is resolved per request.
  • Response has started: once headers are flushed, middleware can no longer change the status code. An exception after that point aborts the connection rather than producing ProblemDetails.

Example

Performance and trade-offs
Each middleware adds one delegate call and whatever it does. The expensive ones are body-reading middleware (logging full request bodies buffers them), response buffering, and synchronous I/O. Keep request and response body logging off by default, or sample it, and never log Authorization headers.
Architectural context
The pipeline is the chain of responsibility for cross-cutting HTTP concerns. Correlation, exception mapping, authentication, authorization, rate limiting, and timeouts are platform concerns: put them in a shared AddPlatformDefaults() / UsePlatformDefaults() extension (the .NET Aspire ServiceDefaults pattern) so every service in the estate gets the same order.
What breaks in production
Authorization before authentication returns 401 for valid tokens. An exception handler registered late misses exceptions from earlier middleware. CORS after authorization fails browser preflights while Postman works, so the team thinks the API is fine. Scoped services in a middleware constructor leak one request's state into all others.
Say this in the room
Kestrel builds the HttpContext and calls one composed delegate. Exception handling is outermost, then routing selects the endpoint, then authentication builds the user and authorization evaluates the endpoint's policy, then rate limiting and the endpoint. Convention middleware is constructed once, so scoped services go into InvokeAsync. I can draw that order before I talk about patterns.

3.2Filters versus middleware

QWhen would you write an MVC filter or a Minimal API endpoint filter instead of middleware? What order do filters run in?

Short answerMiddleware runs for every request on the pipeline and sees only the raw HttpContext. Filters run inside endpoint execution, after routing and model binding, so they see the action's arguments, model state, and result, and they can be applied per endpoint or per group. Use middleware for transport concerns and filters for endpoint concerns such as argument validation, idempotency checks, and auditing a specific command.

How it works

Under the hood
  • MVC filter pipeline: authorization filters, then resource filters (which run before model binding and can short-circuit, as caching does), then model binding, then action filters (before and after the action, with access to arguments), then the action, then exception filters (for exceptions from the action and action filters only), then result filters (around the result execution). [ApiController] adds an automatic 400 for an invalid ModelState through an action filter.
  • Endpoint filters (Minimal APIs, .NET 7+): IEndpointFilter wraps the handler invocation with access to context.Arguments, in the order added. Route groups (MapGroup) apply filters to many endpoints at once.
  • DI: attribute filters are instances. [ServiceFilter(typeof(T))] resolves from DI (register the filter), and [TypeFilter] constructs it with DI arguments. Global filters registered by type are resolved per request.

3.3Controllers or minimal APIs

QControllers or Minimal APIs for a new service? What are the runtime and team trade-offs?

Short answerBoth run on the same routing, model binding, and endpoint infrastructure. Minimal APIs have less per-request overhead and fewer allocations, support Native AOT through the Request Delegate Generator, and give strongly typed OpenAPI responses with TypedResults. Controllers bring conventions, the full MVC filter pipeline, and familiarity on a large team. Pick one per service and write the reason down.

How it works

Under the hood
A Minimal API handler is compiled at startup into a RequestDelegate by RequestDelegateFactory (or at build time by the source generator for AOT), with binding code specialized for its parameters. A controller action goes through the MVC invoker: action selection, filter pipeline, model binding through value providers, and result execution. That costs more objects per request, but brings more extensibility. From .NET 10, Minimal APIs also get built-in validation with AddValidation().

Example

Performance and trade-offs
  • Throughput: Minimal APIs are measurably lighter per request in framework benchmarks. In a real service that waits on SQL, the difference rarely shows up in p95.
  • Startup and AOT: Minimal APIs with the Request Delegate Generator work with Native AOT; MVC does not.
  • Team cost: mixing both in one service doubles the conventions to review: two places to forget a CancellationToken, two error mappings.
Architectural context
For vertical-slice architectures, each Minimal API endpoint can sit next to its handler and validator in one folder. For a large team with existing filters and conventions, controllers keep the codebase uniform. The handler and the domain are identical either way; this is an HTTP-layer choice, not an architecture.
What breaks in production
A Minimal API lambda that closes over a scoped service captured at startup is a captive dependency. A controller base class that exposes the DbContext invites queries in actions. Rewriting controllers as Minimal APIs as a goal in itself is churn with no user value.
Say this in the room
Same routing and binding underneath. Minimal APIs are lighter, AOT-capable, and typed with TypedResults. Controllers bring the MVC filter pipeline and conventions for a big team. I pick one per service; the handler is the same either way.

3.4DI lifetimes and a captive dependency

QExplain transient, scoped, and singleton. What is a captive dependency, how do you detect it, and how does DbContext pooling change the picture?

Short answerTransient is a new instance per resolution. Scoped is one per scope, and ASP.NET Core creates a scope per request. Singleton is one per root provider, which means one per process. A captive dependency is a longer-lived service holding a shorter-lived one, such as a singleton holding a scoped DbContext, so the DbContext outlives its request and gets shared across threads. ValidateScopes catches it at resolution, and ValidateOnBuild at startup. Pooled DbContexts are reset and reused, so per-tenant state must never be injected into the context's constructor.

How it works

Under the hood
  • Scopes: each request gets an IServiceScope from IServiceScopeFactory, exposed as HttpContext.RequestServices. Scoped instances are cached in the scope. Disposables created by the scope, including transients, are disposed when it ends.
  • Root resolution: resolving a scoped service from the root provider, which is what a singleton's constructor does, makes it effectively a singleton. ValidateScopes (on by default in Development) throws instead.
  • Transient disposables from root are tracked until shutdown, a leak described in Day 1.
  • AddDbContextPool keeps a pool of contexts (1024 by default). On return, the context's change tracker and state are reset. The constructor runs only once per pooled instance, so scoped constructor dependencies (a tenant accessor) are captured from whichever request created the instance.
  • IDbContextFactory<T> creates contexts on demand for singletons, Blazor Server, and parallel work.

Example

Performance and trade-offs
  • Allocations: transient services allocate per resolution, which is fine for light objects. A transient injected into a singleton is created once, which is a silent lifetime change.
  • DbContext pooling saves the context's construction cost (the internal service provider lookup and allocations), measurable at thousands of requests a second and irrelevant at fifty.
  • Thread safety: DbContext is not thread-safe. Concurrent use throws "A second operation was started on this context instance".
Architectural context
The composition root is the only place lifetimes are decided. Libraries expose AddX() extensions that choose correct lifetimes. MassTransit consumers and MediatR handlers are resolved per message or request scope, which is exactly why a DbContext is safe inside them and unsafe in a singleton that calls them.
What breaks in production
A captive DbContext fails under parallel requests or, worse, returns one tenant's tracked entities to another. A BackgroundService that constructor-injects a DbContext fails at startup with validation on, and fails in production in a worse way with it off. Pooling plus a constructor-injected tenant is a cross-tenant data leak.
Say this in the room
Transient per resolve, scoped per request, singleton per process. A singleton holding a scoped service is a captive dependency; I turn on ValidateScopes and ValidateOnBuild so it fails the deploy. Background services create a scope per unit of work. With DbContext pooling, the constructor runs once, so tenant state is set per lease, never injected.

3.5Authentication and authorization

QHow does JwtBearer validate a token, what is the difference between 401 and 403, and how do you stop tenant A reading tenant B's order?

Short answerJwtBearer reads the bearer token, validates its signature against signing keys fetched from the issuer's OpenID metadata (cached and refreshed), then checks issuer, audience, and lifetime (with a 5-minute default clock skew), and builds a ClaimsPrincipal. A policy grants coarse access, such as a role or scope. Resource-based checks in the handler, plus a tenant query filter, protect individual rows. 401 means we do not know you; 403 means we know you and you may not.

How it works

Under the hood
  • Metadata and keys: on first use the handler downloads /.well-known/openid-configuration and the JWKS from Authority, caches them (refreshing roughly daily), and refreshes early if a token arrives with an unknown key id. That is how key rotation works without a deploy.
  • Validation: signature, iss, aud, exp/nbf (with ClockSkew, 5 minutes by default), and algorithm. .NET 8 uses JsonWebTokenHandler by default, which is faster than the old handler.
  • Claim mapping: by default inbound claims such as roles may be mapped to long URI claim types. Set MapInboundClaims = false to keep the JWT names, and set RoleClaimType to match.
  • Authorization: AuthorizationMiddleware reads the endpoint's policies, evaluates requirements through IAuthorizationHandlers, and on failure calls ChallengeAsync (401, unauthenticated) or ForbidAsync (403, authenticated).

Example

Performance and trade-offs
Signature validation (RSA) costs tens of microseconds per request; keys are cached, so there is no network call per request. Avoid per-request calls to the identity provider or Graph for claims. Use token claims, or cache the lookup.
Architectural context
Three identities appear in every design: the user (Entra ID token), the process (managed identity to SQL, Key Vault, and Service Bus), and the pipeline (migrations). Service-to-service calls use client-credentials tokens with app roles, validated the same way. A gateway (APIM, YARP) can pre-validate tokens, but each service still validates its own audience.
What breaks in production
Trusting TenantId or IsAdmin from the body is over-posting. Skipping audience validation accepts tokens minted for another API. A missing [Authorize] or RequireAuthorization on one endpoint is an anonymous write. Prevent that with a fallback policy: AddAuthorizationBuilder().SetFallbackPolicy(...RequireAuthenticatedUser()).
Say this in the room
JwtBearer validates signature, issuer, audience, and lifetime against cached signing keys and builds the principal. A policy is the coarse check. The tenant comes from the token, the query filter is the safety net, and a test proves tenant A cannot read tenant B. 401 is unknown, 403 is known and refused. A fallback policy makes forgetting Authorize fail closed.

3.7Verbs, and POST /orders under retries

QA partner retries POST /orders after a timeout. How do you guarantee one order, including when two retries arrive at the same moment?

Short answerPOST is not idempotent, so the client sends an Idempotency-Key (one GUID per user action, reused across retries). The server stores the key, a hash of the request, and the response, in the same transaction as the order, protected by a unique constraint on (tenant, key). A replay with the same body returns the stored response. A reuse with a different body is 409. Two simultaneous attempts race on the unique index: the loser catches the violation and replays.

How it works

Under the hood
The check-then-insert in C# is not atomic across instances or threads; the unique index is. SQL Server takes a key-range lock on the index entry during insert, so exactly one of the concurrent transactions commits the key, and the others fail with error 2627 or 2601. The stored response makes the replay byte-for-byte identical, which is what the client's retry logic expects.

Example

Performance and trade-offs
The idempotency lookup is one indexed seek; the extra insert rides in the same batch as the order. The cost is retention: purge keys after the client's retry window (often 24 to 72 hours) with a set-based ExecuteDelete job, so the index stays small.
Architectural context
GET, PUT, and DELETE are idempotent by definition and safe to retry, so resilience pipelines may retry them automatically. POST is retried only when an idempotency key exists. Downstream calls carry the same key (payment providers support Idempotency-Key), so the whole chain is retry-safe. The idempotency key does not replace a business unique key such as one external reference per tenant.
What breaks in production
Storing the key after SaveChanges lets two retries insert two orders. Not hashing the body means a client bug that reuses a key silently replays the wrong order. A key without retention grows forever.
Say this in the room
The client sends an Idempotency-Key. I store it uniquely per tenant with a request hash and the response, in the same transaction as the order. A concurrent duplicate loses on the unique index, and I replay the winner's response. Same body replays; a different body is 409.

3.8Validation, versioning, and pagination

QWhere does validation live, how do you version the API, and how do you paginate a list that grows by millions of rows?

Short answerShape validation runs once at the edge (FluentValidation, data annotations, or .NET 10's built-in Minimal API validation) and returns 400 with field-level errors. Business rules stay in the handler. Version in the URL for an enterprise API, with an overlap window and usage metrics before you retire a version. Paginate with a keyset cursor over an index on (TenantId, CreatedUtc, Id), cap the page size, and sort from an allow-list.

Example

Performance and trade-offs
Offset pagination reads and discards every skipped row, so page 1,000 costs a thousand times page 1. Keyset seeks straight to the cursor, so every page costs the same, provided the index matches the ORDER BY including the tie-breaker. FluentValidation validators are stateless; register them as singletons, or scoped if they need the DbContext for uniqueness hints.
Architectural context
Versioning with Asp.Versioning: URL segment (/v1/) for public and partner APIs, because gateways, caches, logs, and humans can see it. Additive changes (new optional fields) do not need a version; renames and semantic changes do. Measure traffic per version before retiring one. Contract tests (Day 8) guard the shape.
What breaks in production
An ORDER BY built from a query-string column name is injection if concatenated and a table scan if any column is allowed. Offset 100,000 on a hot table reads 100,000 rows to discard them. Validation only in the UI means the partner's script bypasses it.
Say this in the room
Shape validation is one component at the edge returning field errors; business rules stay in the handler. I version in the URL with an overlap window and usage metrics. Lists are keyset-paginated with an opaque cursor, capped, and sorted from an allow-list, with an index that matches the order including the id tie-breaker.

3.9Timeouts, retries, and a slow dependency

QThe tax service gets slow. Show me the resilience configuration on the HttpClient, explain the order of the strategies, and tell me what you would never retry.

Short answerEvery outbound call has a total timeout shorter than the caller's patience, a per-attempt timeout, retries only for idempotent and transient failures (with exponential backoff and jitter), a circuit breaker that fails fast while the dependency is sick, and a concurrency limit. In .NET 8+ that is AddStandardResilienceHandler (Polly v8): rate limiter, total timeout, retry, circuit breaker, attempt timeout, from outermost to innermost. Never retry a non-idempotent POST without an idempotency key.

How it works

Under the hood
  • Strategy order matters: the total timeout wraps the retries, so retries cannot exceed the budget. The circuit breaker sits inside the retries, so each attempt is counted and an open circuit short-circuits retries immediately with BrokenCircuitException. The attempt timeout is innermost, so one slow attempt is cut off and retried.
  • Defaults of the standard handler: total timeout 30 s, 3 retries with exponential backoff and jitter on transient HTTP status codes (408, 429, 5xx) and network exceptions, circuit breaker with a 10 percent failure ratio over a 30 s sampling window and a minimum throughput of 100, attempt timeout 10 s. Tune them per dependency.
  • HttpClient.Timeout (default 100 s) wraps the entire handler pipeline. If you set it lower than the resilience total timeout, it cancels your retries. Leave it at infinite or above the total timeout when using the resilience handler.
  • Retry-After: Polly's HTTP retry honors Retry-After on 429 and 503 responses.

Example

Performance and trade-offs
  • Latency: the worst case is the total timeout; design the user's budget around it. Jitter spreads retries so instances do not synchronize their load spikes.
  • Load amplification: N retries multiply downstream load by up to N+1 during an incident. The circuit breaker and a retry budget (hedging off, low retry counts) contain it.
  • Threads: async waits hold no threads, but each in-flight call holds a connection. Add a concurrency limiter (o.RateLimiter) for dependencies with low capacity.
Architectural context
Resilience is per dependency and reviewed like code. Payment, tax, and inventory each have their own pipeline with documented numbers. EF Core uses its execution strategy (Day 4); Service Bus has its own retry options, and MassTransit has message retry and redelivery policies. When everything is exhausted, return 503 with a trace id, and make sure telemetry tags the dependency name so the dashboard points at it.
What breaks in production
A liveness probe that checks SQL turns a database failover into a restart storm. A circuit breaker with a tiny minimum throughput opens on the first blip and fails checkout. new HttpClient() per call exhausts ports; a static client without PooledConnectionLifetime ignores DNS changes.
Say this in the room
Total timeout, then retries with jitter only for idempotent transient failures, then a circuit breaker, then a per-attempt timeout. In .NET 8 that is the standard resilience handler, tuned per dependency, with HttpClient.Timeout out of the way. I never retry a POST without an idempotency key, and liveness never checks SQL.

3.10What you look for in a pull request

QReview this controller action. What do you comment on, in what order?

Short answerRead in order of blast radius: the contract (route, verb, status codes), authorization and tenant scoping, bound fields (over-posting), async and cancellation, DI lifetimes, query shape and transaction boundary, messaging consistency, logging of secrets or personal data, and the tests that would have caught the expensive failure. Leave formatting to the formatter. Each comment states a rule the author can reuse.

Example: the action, and the comments

  1. Sync I/O: SaveChanges blocks a pool thread for the round trip. Make it async and take a CancellationToken.
  2. new AppDbContext() bypasses DI: no configured options, no scope, no disposal, no pooling. Inject a handler instead.
  3. Over-posting: the body is an entity-shaped DTO. IsAdmin and Total are client-supplied authority. Price and tenant come from the server and the token.
  4. Client-chosen Id lets callers pick keys and collide. The database assigns ids; idempotency is a separate key.
  5. Dual write: Publish after SaveChanges, outside a transaction. A crash between them commits an order and loses the event. Write an outbox row in the same SaveChanges.
  6. Echoing input returns the client's claims as if they were stored truth. Return the persisted DTO with 201 and a Location header.
  7. No authorization, no idempotency, no tests. A retried POST creates a second order.
Architectural context
Turn the recurring comments into automation so that review time goes to design: analyzers (CA2007 in libraries, CA1849 for sync-over-async, the Microsoft.VisualStudio.Threading analyzers), a fallback authorization policy, architecture tests for references, and a PR template with the checklist. Then review becomes about the contract and the data, which is the expensive part.
What breaks in production
A review that only fixes names ships the data bug. A review that rewrites the PR in comments trains the team to wait for you. A review that ignores the SQL ships a list endpoint that times out on the next large tenant.
Say this in the room
I review the contract, the auth, the bound fields, the cancellation token, the transaction boundary, and the query, in that order. Each comment states a rule the author can apply next time, and the repeat offenders become analyzers. Style belongs to the formatter.

4.1The change tracker, and when you turn it off

QWhat does the change tracker actually do, what does it cost, and when do you turn it off?

Short answerA tracked query creates an entity instance, a snapshot of its original values, and an identity-map entry, so the same row returns the same instance. On SaveChanges, DetectChanges compares every tracked entity with its snapshot and generates the SQL for whatever differs. That is ideal for a short unit of work that loads a few aggregates and changes them. Read paths should use AsNoTracking or a projection to a DTO, which skips the snapshot and identity map entirely.

How it works

Under the hood
  • Identity resolution: the StateManager keys entries by primary key. Materializing a row whose key is already tracked returns the existing instance and discards the new values, which is why a long-lived context returns stale data.
  • Snapshots: for snapshot change tracking (the default), each InternalEntityEntry holds an array of original values. Memory per tracked entity is roughly the entity plus that array plus the entry, so 10,000 tracked rows cost several megabytes and a lot of GC work.
  • DetectChanges runs automatically before SaveChanges and on some APIs (Entries(), Local). It is O(tracked entities × properties). In a loop that adds thousands of entities it becomes quadratic-ish; batch the work or use a fresh context per batch.
  • States: Added, Unchanged, Modified, Deleted, Detached. Update(entity) marks every property Modified and writes all columns; attaching and setting one property writes one column.
  • AsNoTrackingWithIdentityResolution skips snapshots but keeps an identity map for the query, so a graph with repeated references is not duplicated.

Example

Performance and trade-offs
For batches, use chunks of 500 to 2,000 entities with ChangeTracker.Clear() between chunks, or bypass EF with SqlBulkCopy into a staging table and a set-based MERGE (Day 9). For read-heavy contexts, UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking) as the default, and opt in to tracking with AsTracking() in write handlers.
Architectural context
The tracker is the unit of work, so one DbContext per request (scoped) is the right scope. Repositories that call SaveChanges themselves break that, because two repositories in one handler commit separately. CQRS fits EF nicely: commands use tracked aggregates and queries use no-tracking projections, sometimes from a read replica.
What breaks in production
A singleton or long-lived DbContext keeps every row ever loaded, returns stale values due to identity resolution, and is not thread-safe, so a second concurrent operation throws "A second operation was started on this context instance". Update() on a detached DTO-mapped entity writes every column, overwriting concurrent changes.
Say this in the room
The tracker keeps an identity map and a snapshot per entity and diffs them on SaveChanges. That is right for a short write, wrong for reads and bulk work. Reads are no-tracking projections, writes load the aggregate tracked, and bulk goes around EF.

4.2Include, split queries, lazy loading, and projection

QAn order screen needs the order, its lines, and its shipments. How do you load it, and what is a cartesian explosion?

Short answerProject to the shape the screen needs; EF generates one query with only those columns. If you need entities with two collection navigations, Include both and use AsSplitQuery, because a single JOIN multiplies rows: 50 lines times 10 shipments returns 500 rows of duplicated order data. Lazy loading is off, because it turns every navigation access into a hidden round trip.

How it works

Under the hood
  • Single query (the default) translates Includes into LEFT JOINs ordered by the keys so EF can stitch the graph while streaming. Two sibling collections produce a cartesian product.
  • Split query sends one SELECT per collection, each re-applying the root filter and ordering. Rows are not multiplied, but there are more round trips, and without a transaction or snapshot isolation the parts can come from different moments in time.
  • Projection with Select into a DTO, including nested collections, is translated into SQL; nothing is tracked. EF 8+ can also project into collections in a single query using correlated subqueries or JSON (EF 8 added primitive collections and JSON column mapping).
  • Lazy loading (Microsoft.EntityFrameworkCore.Proxies) generates runtime proxy subclasses; touching a navigation runs a query synchronously on the same context. It also breaks after the context is disposed.
  • Configure the default: UseQuerySplittingBehavior(QuerySplittingBehavior.SplitQuery) globally, then AsSingleQuery() per query when consistency matters more.

Example

Performance and trade-offs
A cartesian query moves (lines × shipments) rows over the wire and allocates materialization buffers for each one; latency grows multiplicatively. Split queries cost one round trip per collection, about 1 ms each inside an Azure region. Projections usually win on both, because the wide columns (descriptions, notes, JSON) never leave the database.
Architectural context
On read models, projections are the API's query layer; they should not leak entities to controllers. On the write side, load the aggregate with Includes that match its boundary and nothing more. If a screen needs data from three aggregates, that is a read model, and a view, Dapper query, or a denormalized table is legitimate.
What breaks in production
EF logs warning MultipleCollectionIncludeWarning when a single query includes multiple collections; turn it into an error in development. Split queries combined with Skip/Take but without a unique ordering return inconsistent pages. Lazy loading in a serializer walks the whole graph and runs hundreds of queries.
Say this in the room
I project to DTOs for reads. When I need entities with two collections, I use split queries to avoid the cartesian product, and I set that as the default. Lazy loading stays off because it hides round trips.

4.3Finding an N+1 and fixing it

QThe order list endpoint takes three seconds for a large tenant. You suspect N+1. How do you prove it, and how do you fix it?

Short answerProve it by counting commands per request: EF's logging, Application Insights dependency telemetry, or the Microsoft.EntityFrameworkCore counters will show one query for the list and then one query per row. Fix it by moving the per-row work into the query: a projection that includes the related data, a single Include with a split query, or a batched WHERE Id IN (...) load followed by an in-memory join.

How it works

Under the hood
The N+1 shape appears whenever a loop calls the database: lazy loading, a repository method called per item, await inside a foreach, or a mapping profile that resolves a lookup. Each round trip costs network latency plus parse and execute, so 200 rows at 4 ms each is 800 ms before any real work. EF 8+ translates ids.Contains(x.Id) into an OPENJSON parameter for SQL Server (one plan for any list size); EF 10 adds a parameterized-list mode, and the translation is configurable.

Example

Performance and trade-offs
The fix usually cuts latency by one to two orders of magnitude and reduces connection-pool pressure, because each request holds a connection for a fraction of the time. Watch the opposite failure too: one huge query that returns 50 MB. The goal is a small, bounded number of round trips per request, each returning only what the screen shows.
Architectural context
Make the command count visible: Application Insights shows dependency calls per operation, and OpenTelemetry's SqlClient or EF instrumentation adds spans. A PR checklist item and an integration test with the interceptor above keep N+1 from returning.
What breaks in production
It does not show up in development, where the tenant has five orders and the database is local. It shows up in production with 200 rows and 3 ms network latency, and under load it exhausts the connection pool (default max pool size 100), at which point unrelated endpoints time out.
Say this in the room
I prove N+1 by counting commands per request in telemetry or the EF logs. I fix it by moving the work into one projection or a batched lookup, and I keep it fixed with a test that counts commands.

4.4Compiled queries, compiled models, and DbContext pooling

QEF Core shows up in a CPU profile on a hot endpoint. What overheads does EF add per query and per context, and what are the knobs?

Short answerEF adds three costs: building the model at startup, translating LINQ to SQL (cached by expression shape after the first call), and creating a DbContext per request. Compiled models (dotnet ef dbcontext optimize) cut startup for large models. EF.CompileAsyncQuery skips cache lookup and parameter extraction for a hot query. AddDbContextPool reuses context instances. Each gives a few percent to tens of percent on hot paths; measure first, because the round trip usually dominates.

How it works

Under the hood
  • Query cache: each LINQ execution visits the expression tree to extract parameters and compute a cache key, then looks up the compiled shaper and SQL. Constants inlined into the expression (not captured variables) produce new cache entries and plan-cache pollution in SQL Server.
  • Compiled queries do the visit once and return a delegate; calls go straight to execution. They cannot be composed further.
  • Compiled model: model building runs conventions over every entity on first use, which can take seconds for hundreds of entities. The compiled model is generated C# that constructs the model directly. EF 9+ can generate it automatically at build time, and it is required for Native AOT with precompiled queries (experimental).
  • Pooling: AddDbContextPool registers contexts as resettable. On dispose, the context's state is reset (tracker cleared, state reset) and returned to the pool (default 1024). Constructor-injected scoped services are not allowed in pooled contexts, which is why the tenant pattern in Day 3 sets a property after leasing.

Example

Performance and trade-offs
Reference numbers from the EF team's benchmarks: pooling removes roughly a microsecond-scale allocation set per request (meaningful at thousands of requests per second); compiled queries save on the order of 10 to 30 percent of EF's CPU per query for simple queries. At 50 requests per second, neither matters compared with a missing index. The compiled model matters for cold start, especially on Functions and scale-out.
Architectural context
Use them where a profiler points, not by default. The compiled model must be regenerated when the model changes; add it to the build or use EF 9's MSBuild integration so it cannot drift. Pooling plus a tenant property is a documented pattern, but EF does not reset your own properties when a context returns to the pool, so the registration that leases the context must set the tenant every time.
What breaks in production
A pooled context that caches anything in fields (tenant, user, a list) leaks it to the next request unless reset. A stale compiled model throws at runtime or silently ignores new configuration. A compiled query that captures a DbContext instance instead of taking it as a parameter is a captive dependency.
Say this in the room
EF's overheads are model building, LINQ translation, and context creation. Compiled models, compiled queries, and pooling address each one. I reach for them after a profile says EF is hot, because the database round trip is usually the real cost.

4.5Migrations locally and in production

QHow do migrations get from a developer laptop to production, and how do you rename a column without downtime?

Short answerDevelopers create migrations and review the generated SQL in the PR. The pipeline produces an idempotent script or a migration bundle, applied by a deployment step under an identity with DDL rights (not the app's identity), before the new code is swapped in. Breaking changes use expand and contract: add the new column, dual-write and backfill, switch reads, then drop the old column in a later release. The app never runs Database.Migrate() on startup in a scaled-out environment.

How it works

Under the hood
Each migration has Up and Down and a model snapshot. __EFMigrationsHistory records applied migrations. dotnet ef migrations script --idempotent wraps each migration in an IF NOT EXISTS check against that table. A bundle (dotnet ef migrations bundle) is a self-contained executable that applies pending migrations with a connection string. EF 9+ takes an application lock during Migrate to prevent concurrent runs, but that is not a reason to migrate from app startup: the app identity then needs DDL rights, and a slow migration blocks startup health checks.

Example

Performance and trade-offs
Adding a nullable column is metadata-only. Adding a NOT NULL column with a default is metadata-only in SQL Server 2012+ Enterprise and Azure SQL. Creating an index on a large table locks it unless created with ONLINE = ON (Azure SQL supports it, plus RESUMABLE = ON). Large backfills must be batched to avoid lock escalation (about 5,000 locks on one object) and log growth.
Architectural context
With deployment slots (Day 6), old and new code run against the same schema during the swap, so every migration must be compatible with both versions. That constraint is what makes expand and contract mandatory, not optional. Keep schema changes and code changes in separate, ordered releases when the change is breaking.
What breaks in production
Migrate() at startup on ten instances, a migration that drops a column the running version still reads, an index build that blocks writes during business hours, and a Down nobody tested. A generated migration that drops and recreates a column because the rename was not detected loses data; read the SQL.
Say this in the room
Migrations are reviewed as SQL, shipped as a bundle or idempotent script, and applied by the pipeline with a deployment identity before the swap. Breaking changes are expand and contract across releases, because during the swap both versions run against one schema.

4.6Two users update the same order

QTwo support agents edit the same order at the same time. What happens with EF by default, and what do you build instead?

Short answerBy default the last write wins silently. Add a rowversion concurrency token. EF then adds AND RowVersion = @original to the UPDATE, and if zero rows are affected it throws DbUpdateConcurrencyException. The API returns 409 (or 412 when the client sent If-Match with an ETag). The client reloads and reapplies the change, or the server merges when the changed fields do not overlap.

How it works

Under the hood
  • rowversion is an 8-byte, database-wide counter that SQL Server increments on every update of the row. EF maps it with [Timestamp] or IsRowVersion(), treats it as store-generated, and reads the new value back with OUTPUT INSERTED.RowVersion.
  • The check is optimistic: no locks are held between read and write. The UPDATE's WHERE clause makes the check atomic in the database.
  • Across HTTP: the client must send back the version it read; the server sets Entry(order).Property(o => o.RowVersion).OriginalValue to that value before saving. Reloading the entity at the start of the request and saving it does not detect a conflict with a change made between the GET and the PUT.
  • Resolution: ex.Entries gives the failed entries; GetDatabaseValuesAsync() returns the current row, so you can compare proposed, original, and database values.

Example

Performance and trade-offs
Optimistic concurrency costs one extra predicate and 8 bytes per row, and holds no locks. Pessimistic locking (UPDLOCK in a transaction) is right only for short, high-contention critical sections such as allocating stock, and it must never span a user's think time.
Architectural context
For a hot counter such as inventory, avoid read-modify-write altogether: ExecuteUpdateAsync(s => s.SetProperty(p => p.Stock, p => p.Stock - qty)) with WHERE Stock >= qty is atomic and needs no token. In a distributed system, consumers use the same idea: the event carries a version, and a handler ignores stale versions.
What breaks in production
Catching the concurrency exception and calling SaveChanges again with the same values is last-write-wins with extra steps. Retrying a concurrency conflict in a resilience policy hides real user conflicts. Forgetting to round-trip the token through the DTO means conflicts are only caught within one request.
Say this in the room
A rowversion token makes EF's UPDATE conditional on the version the client read. Zero rows affected becomes a concurrency exception, which I return as 409, or 412 when they sent If-Match. For hot counters I use an atomic set-based update instead.

4.7Transactions and the SQL retry strategy

QYou enabled EnableRetryOnFailure and now your explicit transaction throws. Why, and how do you write a multi-step transaction that survives a transient failure?

Short answerThe execution strategy retries an operation by re-running it, which is impossible if you opened a transaction yourself, because EF cannot know what to replay. Wrap the whole unit, including BeginTransaction, in db.Database.CreateExecutionStrategy().ExecuteAsync(...) so a retry replays everything. A single SaveChanges is already a transaction and needs nothing extra.

How it works

Under the hood
  • SqlServerRetryingExecutionStrategy recognizes transient error numbers (40613 database unavailable, 40501 service busy, 49918/49919/49920, 4060, 1205 deadlock victim, timeout -2 is not included by default) and retries with exponential backoff up to maxRetryCount (default 6) and maxRetryDelay (default 30 s).
  • User-initiated transactions are rejected: "The configured execution strategy does not support user-initiated transactions."
  • Commit ambiguity: if the connection fails during COMMIT, the transaction may or may not have committed. Replaying blindly can double-apply it. ExecuteInTransactionAsync takes a verifySucceeded delegate that checks, for example, whether the outbox row exists.
  • Replays need a clean context: entities tracked from the failed attempt are still there; clear the tracker at the start of the delegate or create the context inside it.

Example

Performance and trade-offs
Retries add latency only on failure. Transactions hold locks until commit, so keep them short: never call an HTTP API or publish to Service Bus inside one. A transaction that waits on a network call converts a slow dependency into blocking chains in SQL.
Architectural context
The transaction boundary is the aggregate plus its outbox rows. Anything outside the database (email, payment, another service) happens after commit, from the outbox, with idempotent consumers. TransactionScope across two connections can escalate to a distributed transaction, which Azure SQL supports only with elastic transactions; avoid it.
What breaks in production
A command timeout (-2) is not transient by default and should usually not be retried blindly, because the statement may still be running. Retrying a non-idempotent operation without verifySucceeded can apply it twice after an ambiguous commit.
Say this in the room
One SaveChanges is a transaction. When I need several steps, I wrap the whole thing in the execution strategy so a retry replays everything, clear the tracker inside, and give it a verifySucceeded check for the ambiguous commit. Nothing remote happens inside a transaction.

4.8Tenant isolation and soft delete

QHow do you guarantee one tenant never sees another tenant's orders, and how do you implement soft delete without bugs?

Short answerEvery tenant-owned entity has TenantId, set by the server from the token. A global query filter adds WHERE TenantId = @tenant to every query, every unique index starts with TenantId, and an isolation test proves that tenant B gets 404 for tenant A's id. Soft delete is another filter on IsDeleted, with filtered unique indexes. Defense in depth is SQL Row-Level Security using SESSION_CONTEXT.

How it works

Under the hood
  • Query filters are part of the model; the lambda references a property of the DbContext instance (TenantId), so EF parameterizes it per context and reuses the plan.
  • Filters apply to queries and Includes, including ExecuteUpdate and ExecuteDelete. They do not apply to FromSql on unrelated tables, raw ADO.NET, or Find on an entity already tracked from another tenant.
  • Before EF 10, an entity could have only one filter, so tenant and soft delete had to be combined, and IgnoreQueryFilters() removed both. EF 10 adds named filters (HasQueryFilter("SoftDelete", ...)) and IgnoreQueryFilters(["SoftDelete"]).
  • Required navigations with a filtered principal turn into INNER JOINs that silently drop dependents; EF warns about it.

Example

Performance and trade-offs
The filter adds one predicate that matches the leading index column, so it usually makes queries faster. RLS adds a function per row evaluated inline; with an index on TenantId the overhead is small, but measure it. Filtered unique indexes require the filter predicate in queries for the optimizer to use them, and parameterized queries sometimes do not match.
Architectural context
Tenancy model is a business decision with a cost curve: shared schema with TenantId (cheapest, this design), schema per tenant, or database per tenant in an elastic pool (strongest isolation, per-tenant restore, highest operational cost). Large tenants can move to their own database later if the code always routes by tenant (Day 9 Design C).
What breaks in production
IgnoreQueryFilters() in an admin endpoint before EF 10 also drops the tenant filter. A pooled context whose TenantId is not set per lease reads the previous tenant. A unique index on Number without TenantId leaks the existence of another tenant's order through a 409. Background jobs have no HTTP request, so they must set the tenant explicitly.
Say this in the room
TenantId comes from the token, a global filter adds it to every query, unique indexes start with it, and an automated test proves cross-tenant access returns 404. Soft delete is a second filter with filtered unique indexes, named separately in EF 10. Row-Level Security is the backstop.

4.9ExecuteUpdate, raw SQL, or a stored procedure

QYou need to close every order older than 90 days, recalculate a report, and run a complex upsert. Which EF tool for each?

Short answerSet-based changes without loading entities use ExecuteUpdateAsync or ExecuteDeleteAsync (EF 7+): one SQL statement, no tracking. Queries LINQ cannot express use FromSql with interpolated parameters, composed with LINQ where possible, or SqlQuery<T> for unmapped types (EF 8). Logic that needs MERGE, table-valued parameters, temp tables, or DBA ownership goes in a stored procedure, versioned in migrations and called with parameters.

How it works

Under the hood
ExecuteUpdate translates to a single UPDATE ... FROM ... WHERE with your filters (including global query filters). It bypasses the change tracker, so tracked entities in the same context are now stale, and it does not run SaveChanges interceptors, so audit or soft-delete logic implemented there is skipped. FromSql($"...") turns each interpolation hole into a DbParameter; FromSqlRaw with string concatenation does not. EF 10 lets ExecuteUpdate take a regular lambda with statements, so conditional setters no longer require building expression trees by hand.

Example

Performance and trade-offs
Closing 200,000 orders with tracked entities means 200,000 materializations and batched UPDATEs; ExecuteUpdate is one statement. A single large statement can still escalate to a table lock and fill the log, so for very large sets loop over key ranges (Where(o => o.Id > last && o.Id <= last + 5000)) and commit each batch.
Architectural context
The domain model owns invariants for single-aggregate changes; set-based operations are for maintenance, reporting, and bulk updates where the rule is simple and documented. If the rule is not simple, a stored procedure owned and tested in the repository is better than a 200-line LINQ query no one can read.
What breaks in production
ExecuteUpdate skips the audit interceptor and domain events, so a "close old orders" job never publishes OrderClosed. FromSql must return all columns of the entity type. Stored procedures edited directly in production drift from source control.
Say this in the room
ExecuteUpdate and ExecuteDelete for set-based changes, knowing they skip the tracker and interceptors. FromSql with interpolated parameters when LINQ cannot express it. A versioned stored procedure for MERGE, TVPs, or DBA-owned logic. Never string concatenation.

4.10Behaviors you warn a team about

QA team is new to EF Core. Which behaviors cause most of the production incidents you have seen?

Short answerClient evaluation and huge result sets, N+1 through loops or lazy loading, implicit conversions that kill indexes (string columns mapped as nvarchar against varchar columns), a long-lived or shared DbContext, missing CancellationToken, tests on the in-memory provider, Update() on detached graphs, and migrations generated without reading the SQL.

How it works

Under the hood
  • CONVERT_IMPLICIT: .NET strings map to nvarchar parameters by default. If the column is varchar, SQL Server converts the column (lower precedence type) for every row, and the index seek becomes a scan. Map the column with IsUnicode(false) or HasColumnType("varchar(32)") so EF sends a matching parameter type.
  • Client evaluation: since EF Core 3, untranslatable expressions in the final projection run on the client, but in WHERE they throw. A ToList() before Where silently pulls the whole table.
  • In-memory provider: no SQL translation, no transactions, no constraints, case-sensitive string comparison, and no relational behavior, so tests pass that would fail on SQL Server. Use SQLite in-memory for fast tests that need relational behavior, or Testcontainers for real SQL Server (Appendix A).
  • String length: unconfigured strings are nvarchar(max), which cannot be index keys and are stored off-row when large.

Example

Performance and trade-offs
An implicit conversion on a 5-million-row table turns a 1 ms seek into a multi-second scan with high CPU, and the plan cache holds that plan for every tenant. Look for CONVERT_IMPLICIT warnings in the actual execution plan and Query Store's top resource consumers (Day 5).
Architectural context
Codify the guidance: conventions in the model, analyzers, a PR checklist, and integration tests against real SQL Server that count commands. The team should be able to read the SQL EF generates; ToQueryString() on any IQueryable shows it.
What breaks in production
EnableSensitiveDataLogging in production logs customer data. A 30-second default command timeout hides slow queries until the pool exhausts. Mocking DbSet with Moq proves nothing about the SQL.
Say this in the room
The incidents I see are N+1, whole tables pulled to the client, nvarchar parameters against varchar columns causing scans, long-lived contexts, and tests on the in-memory provider. I prevent them with model conventions, warnings as errors in development, reading the generated SQL, and integration tests on real SQL Server.

Day 5 — SQL Server, query performance, and database roles

5.1Clustered index, nonclustered index, and key lookup

QExplain how SQL Server stores the Orders table, what a key lookup is, and how you choose the index for the hottest list query.

Short answerThe clustered index is the table: a B-tree whose leaf pages hold the full rows in key order. A nonclustered index is a separate B-tree whose leaf rows hold its key columns, any INCLUDE columns, and the clustering key as a row locator. If the query needs a column the nonclustered index lacks, SQL Server performs a key lookup into the clustered index for every row, which is a random read per row. For the hot list, build an index whose keys match the WHERE and ORDER BY, and INCLUDE the selected columns so the query is covered.

How it works

Under the hood
  • Pages: 8 KB pages grouped into 64 KB extents. A B-tree has a root, intermediate levels, and a doubly linked leaf level, so a range scan walks leaf pages in order. A seek on a few million rows is typically 3 or 4 page reads.
  • Clustering key choice: narrow, unique, static, and ever-increasing (an int or bigint identity) minimizes page splits and keeps every nonclustered index small, because each one carries the clustering key. A random uniqueidentifier key causes page splits and fragmentation; use NEWSEQUENTIALID() or a sequential GUID if you need GUIDs.
  • Key lookup cost: each lookup is a seek into the clustered index. The optimizer estimates the count; above a tipping point (often a low single-digit percentage of the table) it scans the clustered index instead.
  • Last-page insert contention: very high insert rates into an identity key contend on the last page latch; OPTIMIZE_FOR_SEQUENTIAL_KEY = ON (SQL Server 2019+, Azure SQL) mitigates it.

Example

Performance and trade-offs
Every index speeds reads and slows writes: each INSERT updates every index, and wide INCLUDE lists grow storage and buffer-pool usage. Five to eight well-chosen indexes on a hot OLTP table is usual; twenty usually means nobody removed the unused ones. sys.dm_db_index_usage_stats shows reads versus writes per index since restart.
Architectural context
The index is part of the feature. A PR that adds a list endpoint includes the filter, the index, and the plan. EF migrations can declare the index (HasIndex(...).IncludeProperties(...), IsDescending in EF 7+), so it ships with the code and exists in every environment.
What breaks in production
Missing-index suggestions in plans are per query and ignore existing indexes; adding them blindly produces overlapping indexes. A GUID clustering key on a high-insert table fragments badly. Dropping a "duplicate" index can break a plan forced in Query Store.
Say this in the room
The clustered index is the table in key order; a nonclustered index carries its keys, includes, and the clustering key. A key lookup is a per-row trip back to the table. For the hot list I index the equality column, then the sort columns, and include what the list shows, so the plan is a seek with no sort and no lookup.

5.2SARGable predicates, seeks, and scans

QWhy does WHERE YEAR(CreatedUtc) = 2026 scan, and what other predicate shapes prevent a seek?

Short answerA predicate is SARGable (Search ARGument-able) when the optimizer can turn it into a range on the index key. Wrapping the column in a function, doing arithmetic on it, implicit type conversion, a leading wildcard in LIKE, and OR across different columns all make the optimizer evaluate the expression per row, so it scans. Rewrite to compare the bare column with a range or a value of the same type.

How it works

Under the hood
Seek predicates must be expressible as start and end keys on the B-tree. YEAR(col) is not monotonic in a way the optimizer reasons about, so it becomes a residual predicate evaluated on every row. Data type precedence makes SQL Server convert the lower-precedence side: comparing a varchar column with an nvarchar parameter converts the column (CONVERT_IMPLICIT), which with some collations still allows a dynamic seek but usually scans. Comparing an int column with a string converts the string, which is harmless.

Example

Performance and trade-offs
On a 5-million-row table, a seek reads a handful of pages; a scan reads the whole index, often tens of thousands of pages, and consumes CPU on every row. Under concurrency, scans also take more locks and push useful pages out of the buffer pool.
Architectural context
EF translates o.CreatedUtc.Year == 2026 into DATEPART(year, ...), which is not SARGable; code review should catch date-part predicates in LINQ. For truly function-shaped filters, a persisted computed column with an index makes the expression seekable.
What breaks in production
The plan looks fine in development with 100 rows, because a scan of 100 rows is fast. The query regresses in production silently as the table grows. Check the actual plan for "Predicate" (residual) versus "Seek Predicates".
Say this in the room
A seek needs the bare column compared with a range of the same type. Functions, arithmetic, implicit conversions, and leading wildcards turn it into a scan. I rewrite to half-open ranges, and I watch for EF translating DateTime.Year into DATEPART.

5.3Statistics, Query Store, and a procedure that is slow for one customer

QThe order-search procedure is fast for most tenants and takes 20 seconds for one large tenant. What is happening, and what do you do?

Short answerProbably parameter sensitivity: the plan was compiled and cached for the first parameter value, a small tenant, with a nested loop and key lookups, and it is reused for the large tenant where it is disastrous. Confirm with Query Store (multiple plans, one regressed) and the actual plan's estimated versus actual rows. Fix with the right index first, then OPTION (RECOMPILE) for that statement, OPTIMIZE FOR, a forced plan in Query Store, or SQL Server 2022's parameter-sensitive plan optimization at compatibility level 160.

How it works

Under the hood
  • Statistics are a histogram of up to 200 steps on the leading column of an index or statistics object, plus density for column combinations. The optimizer uses them to estimate rows. Auto-update triggers after roughly SQRT(1000 × rows) modifications (the dynamic threshold, default at compatibility 130+). Skewed data, such as one tenant owning 40 percent of rows, is exactly what a histogram summarizes poorly.
  • Parameter sniffing: the first execution's parameter values are used to compile the plan, which is cached and reused. Usually that is good; with skew it is not.
  • Query Store persists query text, plans, and runtime stats per interval. It can force a plan and shows regressed queries. It is on by default in Azure SQL.
  • PSP optimization (SQL Server 2022, compatibility 160) builds a dispatcher with up to three plan variants for predicates whose cardinality varies a lot.

Example

Performance and trade-offs
OPTION (RECOMPILE) costs a compile per execution, usually 1 to 10 ms of CPU; fine for a search screen, wrong for a statement executed 2,000 times a second. Forced plans cost nothing at runtime but must be revisited when the schema changes. A covering index often removes the sensitivity, because both small and large tenants then get the same efficient seek.
Architectural context
EF queries are parameterized and sniffed the same way as procedures. EF has no per-query recompile hint, but an interceptor can append OPTION (RECOMPILE) for tagged queries (TagWith("recompile")). Keep Query Store on, capture mode AUTO, and add the "regressed queries" view to the incident runbook.
What breaks in production
Clearing the whole plan cache (DBCC FREEPROCCACHE) in production to "fix" one query causes a compile storm and hides the cause until the bad parameter value comes back first. WITH RECOMPILE on a whole procedure recompiles every statement in it.
Say this in the room
One slow tenant on a shared plan is parameter sensitivity on skewed data. I confirm it in Query Store and with estimated versus actual rows, fix the index first, then choose between forcing a plan, a statement-level recompile, and PSP on 2022. I do not flush the plan cache.

5.4Isolation, RCSI, and when readers block writers

QReaders are blocking writers on the Orders table. Explain why under default READ COMMITTED, what RCSI changes, and what it does not fix.

Short answerUnder locking READ COMMITTED, a reader takes shared locks that conflict with a writer's exclusive locks, so long reads and writes block each other. Read Committed Snapshot Isolation (RCSI) makes each statement read the last committed version of the row from the version store, so readers do not take shared locks and do not block or get blocked by writers. Azure SQL Database enables it by default. It does not prevent lost updates or write-write conflicts; you still need a rowversion token or an atomic UPDATE.

How it works

Under the hood
  • Lock modes: S (shared), U (update, taken when searching for rows to modify), X (exclusive), and intent locks (IS, IX) on pages and tables. X conflicts with S; U conflicts with U, which serializes the "search then update" phase.
  • Lock escalation: when one statement holds about 5,000 locks on a single object, SQL Server tries to escalate to a table lock, which then blocks everyone.
  • Row versioning: with RCSI or SNAPSHOT, updates copy the previous row version into the version store (tempdb, or the database's persistent version store with Accelerated Database Recovery) and add 14 bytes to the row.
  • SNAPSHOT isolation is transaction-level: the whole transaction sees one point in time and update conflicts raise error 3960. RCSI is statement-level.
  • Levels: READ UNCOMMITTED and NOLOCK read dirty and can skip or double-read rows during page splits. REPEATABLE READ and SERIALIZABLE hold locks to the end of the transaction, and SERIALIZABLE adds key-range locks.

Example

Performance and trade-offs
RCSI trades blocking for version-store work: each update writes a version, long-running transactions keep versions alive, and readers may walk version chains. On Azure SQL with ADR the persistent version store lives in the user database. The win in concurrency is almost always worth it for OLTP.
Architectural context
Rely on RCSI for read consistency, rowversion for user conflicts, atomic updates for counters, and short transactions everywhere. Code that reads and then writes inside one transaction and expects nothing to change in between needs UPDLOCK on the read or SNAPSHOT isolation with conflict handling.
What breaks in production
NOLOCK sprinkled to "fix blocking" returns duplicates and missing rows during page splits. A transaction left open across an HTTP call holds X locks and keeps the version store growing. Long reports on the primary under RCSI keep old versions alive; route them to a readable secondary.
Say this in the room
Under locking read committed, shared and exclusive locks block each other. RCSI lets readers see the last committed version without locks, and Azure SQL turns it on by default. It does not stop lost updates, so I still use a rowversion or an atomic, guarded UPDATE. NOLOCK is not a fix.

5.5Deadlocks

QYou see error 1205 in the logs a few times an hour. What is happening and how do you fix it rather than just retry?

Short answerA deadlock is a cycle: session A holds a lock B needs, and B holds a lock A needs. The lock monitor detects the cycle (it checks every 5 seconds, more often once deadlocks are found) and kills the cheaper transaction with error 1205. Retrying the victim is a mitigation. The fix is to read the deadlock graph and remove the cycle: access tables in a consistent order, add the index that makes the UPDATE touch fewer rows, shorten transactions, and use RCSI so readers are not part of the cycle.

How it works

Under the hood
Typical shapes: two transactions updating the same two tables in opposite order; a reader with a key lookup (S lock on the nonclustered index, then the clustered index) against a writer updating the clustered index and then the nonclustered index; and an UPDATE without a supporting index that scans and takes U locks on many rows. The deadlock graph XML lists each process, its statement, the resources (keylock, pagelock, objectlock with the index name), and the lock modes held and requested. Azure SQL captures them in the sqlserver.database_xml_deadlock_report extended event; on SQL Server they are in the system_health session.

Example

Performance and trade-offs
Each deadlock wastes the victim's work plus the rollback, and the detection delay adds up to seconds of latency. Retries under heavy contention can create more deadlocks. A deadlock rate that rises with load is a design problem, not noise.
Architectural context
Write paths that touch several aggregates in one transaction are where cycles appear. Keeping one aggregate per transaction (Day 7 outbox) and moving the rest to messages removes many cycles by design. SET DEADLOCK_PRIORITY LOW on background jobs makes them the preferred victim.
What breaks in production
Adding NOLOCK to the reader removes one class of deadlock and introduces wrong results. A retry without idempotency can apply a non-transactional side effect twice. An ORM that updates in entity-graph order can produce different lock orders for the same business operation.
Say this in the room
1205 is a lock cycle and the victim is rolled back. Retry is the seatbelt, not the fix. I read the deadlock graph, then fix lock order, add the index that stops the scan, and keep transactions short and single-aggregate.

5.6Keyset pagination versus offset

QPage 5,000 of the order list takes seconds and sometimes shows the same order twice. Why, and what do you change?

Short answerOFFSET n ROWS FETCH NEXT 50 must produce and discard n rows before returning anything, so cost grows linearly with page depth, and rows inserted or deleted between requests shift the window, causing duplicates and gaps. Keyset (seek) pagination remembers the last row's sort key and asks for rows after it, using the index to seek directly, so every page costs the same and the window does not shift. The trade: no "jump to page 4,812" and no cheap total count.

How it works

Under the hood
With an index on (TenantId, CreatedUtc DESC, Id DESC), the offset plan is an index seek on TenantId followed by reading n + 50 rows in order and a Top operator that discards the first n. The keyset predicate (CreatedUtc < @c) OR (CreatedUtc = @c AND Id < @id) becomes a seek range starting at the cursor. The unique tie-breaker (Id) is mandatory; without it, rows with the same timestamp are skipped or repeated at page boundaries. SQL Server does not support row-value comparison (a, b) < (@a, @b), so the OR form is required; the optimizer handles it as two seek ranges or a seek with a residual.

Example

Performance and trade-offs
Measured with SET STATISTICS IO ON, offset logical reads grow with the page number; keyset stays at a few pages. The total count is a separate query that scans the tenant's range; cache it, approximate it, or return "more available" instead (the extra-row trick in Day 3).
Architectural context
Offset is fine for admin screens over small, bounded sets where page numbers matter. Public and partner APIs use opaque cursors, which also lets you change the sort keys later without breaking clients. Exports and sync jobs use keyset over the clustered key.
What breaks in production
A cursor without a tie-breaker skips rows. A cursor that exposes raw values invites tampering; encode it and validate it. Sorting by a user-chosen column without a matching index makes every page a scan plus a sort.
Say this in the room
Offset discards rows and shifts under inserts, so deep pages are slow and inconsistent. Keyset seeks from the last key with a unique tie-breaker and an index that matches the order, so every page is cheap. I give up random page jumps and exact counts, and I say so.

5.7Who the application connects as

QWhat identity and permissions does the Orders API use in Azure SQL, and who is allowed to change the schema?

Short answerThe API connects as its managed identity, mapped to a contained database user that is a member of a custom runtime role with DML and EXECUTE on the orders schema only. Schema changes run from the pipeline under a separate migrator identity with DDL rights on that schema. Nobody's app runs as db_owner or sa, and there are no passwords in configuration.

How it works

Under the hood
A contained user FROM EXTERNAL PROVIDER maps a Microsoft Entra principal (user, group, managed identity, service principal) directly into the database; no server login is needed. The client obtains an access token for https://database.windows.net/; Microsoft.Data.SqlClient does it for you with Authentication=Active Directory Managed Identity or Active Directory Default. Permissions granted at schema scope apply to every current and future object in that schema, so new tables need no new grants.

Example

Performance and trade-offs
Token acquisition is cached by SqlClient and refreshed before expiry; the first connection after start pays tens of milliseconds. Connection pooling works unchanged because pools are keyed by connection string and identity.
Architectural context
Least privilege turns a SQL injection or a compromised app into a bounded incident: the runtime identity cannot drop tables, read other schemas, or grant itself rights. Reporting gets a read-only role on a readable secondary. Humans get access through Entra groups with Privileged Identity Management, not shared SQL logins. Disable SQL authentication on the server (Entra-only authentication) when every client supports it.
What breaks in production
db_owner for the app means a migration bug or an injection can drop the database. A shared SQL login across environments means a test leak is a production leak. Granting at object level means the next table fails in production with "permission denied" because nobody granted it.
Say this in the room
The API is a managed identity in a runtime role with DML and execute on its schema only. Migrations run from the pipeline as a separate identity with DDL. No passwords, no db_owner, and humans come through Entra groups.

5.8Stored procedure or EF query

QA DBA wants every data access to go through stored procedures. A developer wants everything in LINQ. Where do you land?

Short answerEF LINQ for the CRUD and query shapes it translates well, because it keeps the model, migrations, and tests in one place and parameterizes everything. Stored procedures where they earn it: set-based operations EF cannot express, MERGE and TVP bulk work, logic that must run close to the data under one transaction, and queries a DBA must tune and own. Both are versioned in the repository and deployed by migrations, and both execute under the same least-privilege role.

How it works

Under the hood
Performance is not the deciding factor in most cases: both are parameterized and cached the same way, and both are subject to parameter sniffing. The real differences are ownership, testability, and expressiveness. A procedure gives a stable contract and allows EXECUTE-only permissions; EF gives compile-time checking and composition. EF calls procedures through FromSql (mapped results, not composable when the SQL is EXEC), SqlQuery<T>, or ExecuteSql.

Example

Performance and trade-offs
Procedures save network bytes only when they replace several round trips with one. Business logic in T-SQL scales vertically with the database, the most expensive and hardest-to-scale tier; logic in C# scales out with App Service instances.
Architectural context
Decide per use case, record it in an ADR, and keep the rule simple: domain invariants in C#, set-based data movement in SQL. Integration tests cover both against a real SQL Server container (Appendix A).
What breaks in production
Procedures edited in production without source control drift between environments. MERGE without HOLDLOCK has race conditions under concurrency. A procedure that returns different result shapes per branch breaks EF mapping.
Say this in the room
LINQ for what it translates well; procedures for set-based work, TVPs, and DBA-owned tuning. Both live in the repository, ship through migrations, and run under the same runtime role. Domain rules stay in C#.

5.9What a unique constraint does that C# cannot

QThe code already checks for a duplicate order number before inserting. Why do you still insist on a unique index?

Short answerThe C# check and the insert are two separate operations, so two requests, threads, or instances can both pass the check and both insert. A unique index makes the database reject the second insert atomically, under its own locking, no matter which code path, script, or tool wrote it. Keep the C# check for a friendly message, and treat the constraint violation (2627 or 2601) as the real guarantee, mapped to 409.

How it works

Under the hood
During an insert, SQL Server locks the index key (and, under SERIALIZABLE or for some plans, the key range) in the unique index. A concurrent insert of the same key waits for the first transaction; if the first commits, the second fails with a duplicate-key error; if it rolls back, the second succeeds. Error 2627 is a violated UNIQUE or PRIMARY KEY constraint; 2601 is a unique index. A filtered unique index (WHERE IsDeleted = 0) enforces uniqueness only among live rows.

Example

Performance and trade-offs
A unique index costs the same as any index on writes and gives the optimizer a cardinality guarantee (one row), which improves plans. Pre-checking inside a SERIALIZABLE transaction to avoid the exception holds range locks and deadlocks under load.
Architectural context
Constraints are the last line of every invariant that spans rows: one active cart per user, one idempotency key, one processed message per consumer. They protect against bugs in code you have not written yet, including the migration script and the support engineer's ad-hoc SQL.
What breaks in production
A unique index that forgets TenantId either collides across tenants or leaks existence. A soft-deleted row blocking a re-create needs a filtered index. Catching every DbUpdateException as a duplicate hides foreign-key and truncation errors.
Say this in the room
Check-then-insert is a race across instances. The unique index is atomic and protects every writer, including scripts. I keep the friendly check, but the constraint is the guarantee, and the violation maps to 409.

6.1Where the code runs

QDraw where each piece of the Orders system runs in Azure and what identity it uses.

Short answerThe API runs on App Service (Linux, P1v3 or higher in production, two or more instances across availability zones) with a production and a staging slot. How it works

Under the hood

Requests arrive through the front ends (load balancers) and, by default, ARR affinity cookies pin a client to an instance; turn affinity off for a stateless API.   • Functions isolated worker runs your code in a separate .NET process from the Functions host. The host owns triggers and bindings and talks to the worker over gRPC.   • Managed identity is an Entra service principal tied to the resource. The platform exposes a local token endpoint (IDENTITY_ENDPOINT); DefaultAzureCredential and ManagedIdentityCredential call it and cache tokens.
Architectural context
The deployment unit equals the scaling unit: the API scales with HTTP load, the email Function with queue length, and they fail independently. That is the only split this system needs (Day 7). Private endpoints and VNet integration put SQL, Key Vault, and Service Bus off the public internet when the security posture requires it.
What breaks in production
One identity for everything (or a shared connection string) means the email Function can drop tables. Affinity left on pins users to an instance that is being recycled. A single instance in production has no availability during platform maintenance.
Say this in the room

6.3Deployment slots

QWalk through a release with slots. What exactly happens during a swap, and when is swap-back not safe?

Short answerDeploy to the staging slot, which has its own hostname and settings. The swap applies production's slot-specific settings to staging's workers, restarts them, warms them by hitting the warm-up path on every instance, and only then switches routing, so production never serves a cold or misconfigured instance. Swap-back is the same operation in reverse and takes a minute. It is unsafe when the new release changed the database in a way the old code cannot handle, which is why migrations follow expand and contract.

How it works

Under the hood
  • Phase 1: settings marked "deployment slot setting" (sticky) from the target slot are applied to the source slot's instances, which restart.
  • Phase 2: the platform sends requests to the application root, or to the paths in applicationInitialization, or to WEBSITE_SWAP_WARMUP_PING_PATH with WEBSITE_SWAP_WARMUP_PING_STATUSES, on every instance, and waits for success.
  • Phase 3: routing rules are switched; the old production bits are now in staging, still warm.
  • Swap with preview pauses after phase 1, so you can validate staging with production settings before completing.
  • Health check (/health/ready configured as the health check path) removes an unhealthy instance from the load balancer after repeated failures and replaces it eventually; it is separate from warm-up.

Example

Performance and trade-offs
Warm-up absorbs the JIT, DI graph build, EF model build, and connection pool fill before users arrive (Day 1 JIT: ReadyToRun and the compiled model shorten this). Without it, the first requests after a swap see seconds of latency on every instance.
Architectural context
Slots are a release mechanism, not environments: staging shares the production plan's capacity and must point to production dependencies (with sticky settings for anything that must differ, such as a feature flag that disables the staging outbox relay). Background workers in staging must not consume production queues before the swap; gate them with a sticky setting.
What breaks in production
A non-sticky connection string swaps test credentials into production. An outbox relay running in the staging slot publishes production messages from untested code. A release that renamed a column makes swap-back a second outage.
Say this in the room
Deploy to staging, migrate additively first, smoke-test, then swap so production only gets warmed instances with production settings. Swap-back is a minute, but only while the schema still suits the old code, which is why I use expand and contract.

6.4Secrets and Azure SQL without a password

6.5Cold start, and which plan you choose

6.6A Service Bus trigger, from delivery to completion

QWalk a message from the queue through the email Function to completion. What happens on an exception, a slow email provider, and a poison message?

Short answerIn peek-lock mode the broker locks the message for the lock duration (default 1 minute) and hands it to the trigger. The Function runs, and only after the work and the inbox row commit does it complete the message, which deletes it. An exception abandons it, which unlocks it immediately and increments the delivery count. Work longer than the lock relies on automatic lock renewal (up to 5 minutes by default). After MaxDeliveryCount deliveries (default 10) the broker moves it to the dead-letter queue. Delivery is at least once, so the handler dedupes on MessageId.

How it works

Under the hood
  • Auto-complete: by default the extension completes on success and abandons on exception. Setting AutoCompleteMessages = false and taking ServiceBusMessageActions gives you explicit control: dead-letter a payload that can never succeed instead of burning ten deliveries.
  • Concurrency: maxConcurrentCalls per instance (default 16 × cores) times the instance count is the parallelism downstream sees. The email provider's rate limit dictates it, not the default.
  • Lock lost: if processing exceeds the lock (and renewal fails or stops), another instance receives the same message while the first is still working. That is one more reason for idempotent handlers.
  • Retries: abandon makes the message available immediately, so ten deliveries can happen in seconds. Use the host's retry policy, scheduled re-enqueue with a delay, or dead-letter and replay for back-off.
  • Sessions (IsSessionsEnabled) give FIFO per session id, such as per order, at the cost of per-session throughput.

Example

Performance and trade-offs
Prefetch improves throughput but holds locks on messages that wait in memory, which expire if processing is slow; keep it at zero for slow handlers. Each instance's concurrency multiplies, so ten instances at 16 calls each is 160 concurrent sends against a provider that may allow 50.
Architectural context
Alert on dead-letter count above zero and on the age of the oldest active message (Azure Monitor metrics). Provide a replay tool that moves dead-lettered messages back after a fix, with the original MessageId so the inbox still dedupes. MassTransit or NServiceBus give the same settlement, retry, and outbox semantics as a library (Day 7).
What breaks in production
Auto-complete with a catch-all that swallows exceptions completes failed messages, so they vanish. A handler that sends the email and then crashes before completing sends it again on redelivery unless the provider call is idempotent. Lock duration shorter than the email provider's timeout guarantees duplicates.
Say this in the room
Peek lock, process, record in the inbox, then complete. Exceptions abandon and count deliveries; after the max it dead-letters, and I alert on the DLQ. I turn off auto-complete so a bad payload is dead-lettered immediately, and I size concurrency for the provider, not the default.

6.7What belongs in a Durable Functions orchestration

QWhen do you use Durable Functions, and what are the rules for code inside an orchestrator?

Short answerUse an orchestration when a workflow has several steps that must survive restarts, wait for external events or timers, fan out and fan in, or need compensation: the nightly file in Day 9 Design B, or an approval flow. The orchestrator must be deterministic, because it is replayed from history to rebuild state: no I/O, no DateTime.UtcNow, no random values, no threads. All side effects go in activities, which are at-least-once and therefore idempotent.

How it works

Under the hood
The Durable Task framework stores an append-only history per instance (Azure Storage by default; Netherite, MSSQL, or the Durable Task Scheduler as alternatives). When an awaited activity completes, the orchestrator function runs again from the top. Each await on an already-completed task in the history returns immediately with the recorded result, until execution reaches new work, which is scheduled, and the function unloads. That is why non-deterministic code produces a different path on replay and fails with a non-determinism error. context.CurrentUtcDateTime, context.NewGuid(), and durable timers are replay-safe.

Example

Performance and trade-offs
Every activity call is a queue message plus history writes, so per-step overhead is tens to hundreds of milliseconds. Fan out over chunks of thousands of rows, not over individual rows. Large inputs and outputs are stored in history; pass blob references, not data.
Architectural context
Durable Functions is a workflow engine; the alternatives are a saga state machine in MassTransit (Day 7), Logic Apps for integration-heavy low-code flows, or a simple queue chain when there is no join or timer. Version orchestrations carefully: changing the step order breaks in-flight instances, so deploy new orchestrator names or drain first.
What breaks in production
Changing orchestrator code with instances in flight causes non-determinism failures on replay. Huge histories from eternal orchestrations without ContinueAsNew slow every replay. Non-idempotent activities double-apply on retry.
Say this in the room
I use an orchestration when steps must survive restarts, wait, fan out, or compensate. The orchestrator is replayed, so it is deterministic: no I/O, no clock, no random. Side effects are idempotent activities, chunks are coarse, and payloads are references.

Day 7 — Microservices, as a person who has to operate them

7.1What a service is, and what a folder is

QYour team has a solution with Orders, Customers, and Pricing projects. Is that microservices?

Short answerNo. A service is independently deployable, owns its data, and is reached only through a contract (an API or messages), so another team can release it without coordinating with you. Projects in one solution that share a database and deploy together are modules of a monolith. That is often the right design: a modular monolith gives you boundaries, enforced with architecture tests, without the network, the distributed data, and the operational cost.

How it works

Under the hood
The tests for a real service boundary: can it be deployed alone, does it have its own schema or database that nobody else writes, does it have its own pipeline and on-call owner, and can it be down without taking the caller down? A module boundary is enforced by the compiler and by tests instead: internal types, one public contracts project per module, and NetArchTest rules that forbid one module referencing another's internals or its DbContext.

Example

Performance and trade-offs
An in-process call is nanoseconds and cannot fail partially; a network call is milliseconds, can time out, and needs retries, serialization, auth, and tracing. Turning a call graph of ten in-process calls into ten HTTP hops adds tens of milliseconds of latency and ten new failure modes per request.
Architectural context
Start as a modular monolith with schema-per-module, contracts, and events in-process (or through the outbox to a queue). When one module needs independent scaling, a different release cadence, or a separate team, extract it: the contracts become the API, the schema moves to its own database, and the in-process event becomes a message.
What breaks in production
A "distributed monolith": many deployables sharing one database or requiring a lockstep release. You pay the network costs and keep the coupling. Calling it microservices does not make the outage smaller.
Say this in the room
A service deploys alone, owns its data, and is reached by contract. Projects sharing a database are modules. I start with a modular monolith with enforced boundaries, and I extract a service when a team, a scale profile, or a release cadence demands it.

7.3Database per service, and the join you lost

QOrders and Customers are separate services with separate databases. The order list needs the customer name. How do you get it?

Short answerNot by connecting Orders to the Customers database. Options, in order of preference: keep a local, denormalized copy of what Orders needs (customer name and email) updated from CustomerChanged events; copy the value onto the order at creation time when it is historical data (the name at the time of purchase); call the Customers API, batched, when freshness matters and the dependency is acceptable; or build a separate read model or reporting store that joins both from events. Each trades freshness for availability.

How it works

Under the hood
The local copy is a cache with an owner: the Customers service publishes changes through its outbox; the Orders consumer upserts orders.CustomerSnapshot idempotently and ignores stale versions (an event version or UpdatedUtc comparison). Orders now reads the name locally with a normal SQL join, and Customers being down does not break the order list. The copy lags by seconds.

Example

Performance and trade-offs
A local join is sub-millisecond; a per-row API call is the N+1 of microservices. If you must call, batch (GET /customers?ids=1,2,3) and cache with a short TTL. Snapshots cost storage and a consumer, which is cheap.
Architectural context
Ownership rule: exactly one service writes a table. Others read through its API or hold a copy fed by its events. Reporting across services goes to a separate store (Synapse, Fabric, or a reporting database) fed by events or change data capture, so analysts never query production OLTP across boundaries.
What breaks in production
Event copies without versioning apply an old update after a new one. A snapshot without a backfill path is empty for existing customers; publish a "snapshot all" or seed from an export. Treating the copy as authoritative for writes creates two masters.
Say this in the room
One owner per table. Orders keeps a versioned copy of the customer fields it needs, fed by events, so it can join locally and survive Customers being down. Historical values are copied onto the order. Cross-service reporting has its own store.

7.4The outbox, and the crash between save and publish

QYou save the order, then publish OrderPlaced. The process crashes between the two. What happens, and how does the outbox fix it?

Short answerWithout an outbox, the order is committed and the event is lost forever (or, if you publish first, the event announces an order that never committed). The transactional outbox writes the event as a row in the same database transaction as the order, so both commit or neither does. A relay reads unsent rows and publishes them, marking them sent after the broker acknowledges. A crash after publish but before marking causes a duplicate, so delivery is at least once and consumers dedupe with an inbox.

How it works

Under the hood
  • Atomicity comes from the single local SQL transaction; no distributed transaction across SQL and Service Bus is needed or available.
  • Relay: a polling loop claims rows (READPAST, UPDLOCK), publishes, and marks them. MassTransit's bus outbox does this with a delivery service per instance, using a lock row so only one instance delivers in order.
  • Ordering is per outbox (in insertion order) but not guaranteed across instances unless one relay delivers; use Service Bus sessions keyed by aggregate id if consumers need order per aggregate.
  • Inbox: the consumer records (Consumer, MessageId) in its database in the same transaction as its own changes; a duplicate fails the unique key or is skipped by a lookup.

Example

Performance and trade-offs
The outbox adds one insert per message to the business transaction and a polling query per second per relay. Latency from commit to broker is the polling delay plus publish, typically under two seconds; the email-within-a-minute target leaves plenty of room. Purge sent rows on a schedule to keep the table small.
Architectural context
Every service that publishes integration events uses an outbox; every consumer with side effects uses an inbox or an idempotent upsert. Alert on outbox age (the oldest unsent row) as a key health signal: it catches a broken relay, broker auth failures, and throttling. If MassTransit licensing does not fit, the hand-rolled outbox in Day 6 is about 150 lines and well understood.
What breaks in production
Publishing inside the transaction (before commit) announces orders that may roll back. Calling publish.Publish on a non-outbox bus sends immediately, which is the dual write again; check the registration. An outbox without an inbox just moves the duplicate problem downstream.
Say this in the room
The event is a row in the same transaction as the order, and a relay publishes it after commit. That makes it at least once, so consumers keep an inbox keyed by message id. I alert on outbox age.

7.5A saga for order, payment, and inventory

QPlacing an order must reserve stock and capture payment, owned by different services. Design the flow, including the failure cases.

Short answerThere is no distributed transaction, so use a saga: a sequence of local transactions, each publishing an event, with a compensating action for each step that can be undone. Orchestrated, a state machine in the Orders service sends ReserveStock, then ChargePayment, then confirms; on failure it sends ReleaseStock or RefundPayment and cancels the order. Every step and compensation is idempotent, the saga state is persisted with a concurrency token, and timeouts move stuck sagas to a decision instead of waiting forever.

How it works

Under the hood
  • Orchestration versus choreography: an orchestrator (a state machine) knows the whole flow and is easy to reason about and monitor; choreography (services reacting to each other's events) has no central owner and becomes hard to follow beyond three steps.
  • Saga state is a row keyed by a correlation id with the current state and data, updated in the same transaction as the outgoing messages (outbox). Optimistic concurrency stops two events for the same saga from both transitioning it.
  • Compensation is a semantic undo, not a rollback: a refund, not a deleted payment. Some steps cannot be compensated (a shipped parcel), so put them last.
  • Pivot step: the step after which the saga only moves forward (payment captured). Steps after it must be retried until they succeed.

Example

Performance and trade-offs
Each step is a message hop (tens of milliseconds plus processing), so the saga takes about a second end to end; the API returns 202 or 201 with status Pending and the client polls or receives a notification. Saga rows are small and short-lived; archive finalized ones.
Architectural context
Ask whether you need a saga at all: if stock and payment live in the same database (a modular monolith), one local transaction does the job. Sagas are for real service boundaries. Durable Functions or a workflow engine are alternatives to a MassTransit state machine; the design questions (idempotency, compensation, timeouts, observability) are the same.
What breaks in production
A compensation that is not idempotent refunds twice. A saga without timeouts waits forever on a lost reply. Treating a payment timeout as a failure and releasing stock when the charge actually succeeded loses money; the provider's idempotency key and a status query resolve the ambiguity.
Say this in the room
A saga is local transactions plus compensations. I orchestrate it as a state machine with persisted, versioned state, idempotent steps, a timeout on every wait, and the uncompensatable step last. A payment timeout is "unknown", so I query by idempotency key before deciding.

7.6Idempotent consumption in SQL

QShow me exactly how a consumer guarantees it applies a message once, even under concurrent redelivery.

Short answerIn one SQL transaction: insert (Consumer, MessageId) into an inbox table with a unique key, then apply the business change, then commit, then complete the message. A duplicate delivery fails the inbox insert (or finds the row), so the transaction rolls back and the consumer completes the message without doing the work again. When the change is naturally idempotent (an upsert with a version check), the inbox is optional.

How it works

Under the hood
Two concurrent deliveries of the same message both try to insert the same inbox key; the unique index lets one commit and makes the other wait, then fail with 2627. Because the business change is in the same transaction, the loser's change rolls back too. Side effects outside the database (email, HTTP) cannot be in that transaction, so they either carry an idempotency key to the external system or are themselves driven by an outbox row created in the transaction.

Example

Performance and trade-offs
One extra narrow insert per message. Retention matters: purge inbox rows older than the broker's maximum redelivery window (MassTransit's DuplicateDetectionWindow), or the table grows without bound. Service Bus duplicate detection (by MessageId within a window) helps on the send side but does not replace the inbox.
Architectural context
Idempotency is layered: the producer sets a deterministic MessageId (for example derived from the outbox row id), the broker may dedupe sends, and the consumer dedupes processing. State-based guards (WHERE Status = 'Pending') make handlers robust even without an inbox.
What breaks in production
Checking the inbox in one transaction and writing the change in another reopens the race. Using a random MessageId generated on each publish retry defeats dedupe. Completing the message before committing the transaction loses the work on a crash.
Say this in the room
Inbox insert and business change in one transaction, unique on consumer and message id, then complete. A duplicate fails the key and rolls back, so the change happens once. External side effects carry their own idempotency key.

7.7Versioning an event

QThree consumers read OrderPlaced. You need to add a field and rename another. How do you change it without breaking anyone?

Short answerAdditive changes are safe if consumers are tolerant readers: add optional fields with defaults, never remove or retype a field that is in use, and keep the event name and meaning. A rename is a breaking change, so publish both (old field and new field, or OrderPlaced and OrderPlacedV2) until every consumer has moved, then remove the old one. The contract lives in one shared contracts package or schema, and consumer-driven contract tests tell you who would break.

How it works

Under the hood
System.Text.Json ignores unknown properties by default, which is what makes additive changes safe; JsonUnmappedMemberHandling.Disallow on a consumer turns every additive change into a failure, so do not use it on integration events. Missing properties deserialize to default unless marked required, so new fields must have meaningful defaults for old messages still in the queue. A message type header (MassTransit uses URNs such as urn:message:Orders.Contracts:OrderPlaced; CloudEvents uses type) routes versions to the right handler.

Example

Performance and trade-offs
Dual publishing doubles message volume for that event during the window, which is usually negligible. Messages already in queues and dead-letter queues are old versions; consumers must handle them until the queues drain.
Architectural context
Events are public APIs: owned, documented, versioned, and deprecated with a date. Track which consumers subscribe (Service Bus subscriptions are visible; ask owners) and remove the old version only when its subscription count reaches zero. Prefer thin events (ids plus what changed) to fat events that expose the whole aggregate and break on every model change.
What breaks in production
Renaming a C# record's namespace changes the MassTransit message URN and silently stops routing. A required new field breaks old messages in the dead-letter queue on replay. Sharing the domain entity as the event couples every consumer to internal refactoring.
Say this in the room
Additive changes with defaults, tolerant readers, and no removal. A breaking change becomes a new version published in parallel until every consumer has moved, measured by subscriptions, not by hope. Events are thin, owned, and versioned like APIs.

7.8Logs, metrics, and traces across services

QA customer says they never got their confirmation email for order 4411. How does your telemetry let you find out why in five minutes?

Short answerEvery hop carries W3C trace context (traceparent): HTTP headers between services and the Diagnostic-Id / application properties on Service Bus messages. OpenTelemetry instruments ASP.NET Core, HttpClient, SqlClient, and the messaging library, so one trace shows POST /orders, the SQL insert, the outbox publish, the queue wait, and the Function's email call. Structured logs include the trace id and business keys (OrderId, TenantId), so searching for order 4411 gives the trace. Metrics (rates, durations, queue age, DLQ depth) tell you something is wrong before the customer does.

How it works

Under the hood
  • Activities: .NET's System.Diagnostics.Activity is the OpenTelemetry span. ActivitySource.StartActivity returns null when no listener samples it, so instrumentation is nearly free when off.
  • Propagation: the default propagator injects traceparent and tracestate into outgoing HTTP requests and extracts them on the server. Azure SDK clients and MassTransit propagate through message headers, so the consumer's span becomes a child (or a link) of the producer's.
  • Metrics: System.Diagnostics.Metrics.Meter instruments (Counter, Histogram, ObservableGauge) are aggregated in-process and exported periodically, so they are cheap at any request rate. ASP.NET Core 8 emits http.server.request.duration and Kestrel, routing, and rate-limiting metrics natively.
  • Logs: ILogger scopes and the OpenTelemetry logging provider attach the current trace and span ids to every record.
  • Sampling: head sampling at a fixed rate keeps cost bounded; Application Insights adds rate-limited sampling. Keep errors and slow requests by sampling at ingestion or tail-sampling in a collector.

Example

Performance and trade-offs
Traces cost ingestion money, not CPU: a few microseconds per span. Control cost with sampling, by not logging request bodies, by filtering health checks, and with high-cardinality tags kept off metrics (an order id on a metric dimension creates a time series per order). Logs at Information level for each step in a hot loop are the usual cost explosion.
Architectural context
Standardize on OpenTelemetry semantics so the backend can change (Application Insights, Grafana, Datadog) without code changes. Every service exports the same resource attributes, the same business tags, and a small set of SLO metrics. Dashboards are per user journey (place order, receive email), not per service.
What breaks in production
A Function that starts a new trace instead of continuing the producer's breaks the story at the queue. Logging personal data (email addresses, addresses) in traces creates a compliance problem. Metrics with tenant id as a dimension are fine at 50 tenants and expensive at 50,000.
Say this in the room
W3C trace context crosses HTTP and Service Bus, OpenTelemetry instruments every hop, and logs carry the trace id plus OrderId and TenantId. I find the order in logs, open the trace, and see the hop that failed. Metrics on outbox age and DLQ depth alert before the customer calls.

7.9A downstream service is down

QThe Pricing service is down. What does the Orders API do, and what does the customer see?

Short answerIt depends on whether the dependency is required for a correct answer. Decide in advance, per dependency: fail fast with 503 and a clear message (the circuit breaker stops wasting time), degrade with a cached or last-known value if the business accepts it, or accept the work asynchronously (store the order as PendingPrice and finish when Pricing returns). In every case, a bounded timeout protects the API's threads and connections, and an alert names the dependency.

Example

What breaks in production

Say this in the room
Per dependency I decide in advance: fail fast, degrade with a bounded stale value, or accept asynchronously. Timeouts and a breaker protect the API, a bulkhead keeps one dependency from eating the pool, and the customer sees either a normal result or an honest 503.

Day 8 — .NET Framework to modern .NET

Day 8 is a plan a manager can fund. You do not rewrite the system in a branch for nine months. You inventory the blockers, put a facade in front of the surface that must stay stable, move one vertical slice to .NET 10, run both, and delete the old slice only when the new one has the same logs, the same auth, and a rollback. The goal is an empty Framework footprint on a date, not a heroic cutover weekend.

8.1What actually changes

QWhat is different between .NET Framework 4.8 and .NET 10 beyond "it is cross-platform"? Which differences change behavior silently?

Short answerThe project system (SDK-style, PackageReference), the host (generic host, Kestrel, middleware instead of System.Web and IIS modules), configuration (options instead of ConfigurationManager), DI built in, no SynchronizationContext in ASP.NET Core, Server GC and tiered JIT by default, ICU globalization, System.Text.Json instead of Newtonsoft by default, BinaryFormatter removed (.NET 9), and EF Core instead of EF6. The analyzer finds missing APIs; it does not find the behavioral changes, which are the ones that cause incidents.

How it works

Under the hood
  • Hosting: Framework ASP.NET runs inside IIS's integrated pipeline with HttpApplication events and modules. ASP.NET Core is a console app that hosts Kestrel; IIS, if used, is a reverse proxy through the ASP.NET Core Module (in-process or out-of-process).
  • Request context: HttpContext.Current relied on the ASP.NET SynchronizationContext flowing the request. ASP.NET Core has neither; the context is passed in, or read through IHttpContextAccessor (an AsyncLocal), sparingly.
  • Globalization: .NET 5+ uses ICU on all platforms, so culture-sensitive IndexOf, StartsWith, and sorting can return different results than NLS on Windows. Use ordinal comparisons for identifiers.
  • Serialization: System.Text.Json is case-sensitive by default outside ASP.NET Core's web defaults, does not serialize fields, writes enums as numbers, and throws on reference cycles unless configured. A partner contract that depended on Newtonsoft's behavior changes shape.
  • Performance defaults: tiered compilation, Dynamic PGO (.NET 8), and Server GC in ASP.NET Core typically give large throughput gains, but Server GC uses more memory per core (DATAS in .NET 9+ reduces it).

Example

Performance and trade-offs
Moving from Framework 4.8 to .NET 10 commonly yields substantial throughput and latency gains for the same code, from the JIT, GC, Kestrel, and library improvements. Measure it on the first slice; it is part of the business case, along with the support date.
Architectural context
.NET Framework 4.8 is supported as part of Windows, but it gets no new features, and the ecosystem (Azure SDKs, EF Core, OpenTelemetry, modern auth libraries) targets modern .NET. The business case is security support, hiring, hosting options (Linux, containers, Functions isolated), and performance, not novelty.
What breaks in production
A multi-target library with no end date becomes a permanent compatibility swamp. A green analyzer report misses changed JSON shapes, ICU comparisons, and EF query translation. Promising a WCF binding you have not checked becomes the date slip.
Say this in the room
Different host, pipeline, configuration, serializer, globalization, and data layer. The analyzer finds missing APIs; I look for behavioral changes, especially JSON shape, culture comparisons, and EF translation, and I keep the wire contract stable on purpose.

8.2The migration plan

QYou have an 80-project .NET Framework solution with a Web API that partners call. Give me the plan.

Short answerWeek zero is an inventory and a blocker list. Pick .NET 10 as the target, freeze new Framework-only dependencies, and add characterization tests around the slice you will move. Put YARP in front of the existing host. Move pure libraries first (multi-targeted), then one vertical slice, POST and GET /orders, to a new ASP.NET Core host behind the same URL. Shift traffic gradually, keep rollback as a route change, and repeat slice by slice. Report the percentage of traffic on the new runtime, not the percentage of projects converted.

How it works

Under the hood
The strangler fig works because the facade owns the URL space. YARP (Yet Another Reverse Proxy, a library hosted in ASP.NET Core) routes by path, method, or header to clusters; changing a route is a configuration change that reloads without restart. Microsoft's System.Web adapters (Microsoft.AspNetCore.SystemWebAdapters) give the new host a System.Web.HttpContext-shaped API for shared libraries and support remote session and remote authentication against the Framework app during the overlap, so a user's session or cookie works on both sides.

Example

Performance and trade-offs
The proxy adds a hop of about a millisecond inside a region and some CPU; it is negligible compared with the safety it buys. Run it on the same plan or as a Container App; keep it stateless and instrumented, since it becomes the place you see which runtime served each request.
Architectural context
The plan is a sequence of independently shippable slices, each with its own rollback, which makes it fundable in increments. In Azure, Front Door or Application Gateway path routing can play the facade role; YARP gives more control and runs in code you test. The new host is a modular monolith from day one (Day 7), not a set of microservices.
What breaks in production
A status deck that counts projects hides that the revenue path is still on Framework. A feature freeze that is not real means new Framework-only code lands every sprint. A first slice that is "the whole solution" teaches you nothing until month nine.
Say this in the room
Inventory, a facade on the current URL, one vertical slice to .NET 10 with characterization tests, both runtimes live, and rollback as a route change. I report traffic percentage, and I estimate the rest after the first slice is in production.

8.3What usually blocks a Web API

QWhich parts of a Framework Web API do not move by recompiling, and what do they become?

Short answerHTTP modules and handlers (they quietly do auth, logging, tenant resolution) become middleware. Global.asax events become startup code and middleware. ConfigurationManager and web.config transforms become options and environment configuration. HttpContext.Current becomes an injected HttpContext. WCF clients need regenerated proxies or a new contract. App-pool identity becomes a managed identity. Synchronous I/O that was tolerable on IIS starves the thread pool under Kestrel load. Packages without modern builds must be replaced, wrapped, or block the slice.

How it works

Under the hood
An IIS module runs for every request in the integrated pipeline, in event order (BeginRequest, AuthenticateRequest, AuthorizeRequest, and so on), whether or not the code author remembered it. ASP.NET Core middleware only runs if you register it, in the order you register it. So a missed module does not fail the build; it silently removes a control. Kestrel disallows synchronous I/O on the request and response streams by default (AllowSynchronousIO = false), which surfaces sync reads as exceptions instead of starvation.

Example

Performance and trade-offs
Sync-over-async code that "worked" on IIS (where the request thread was dedicated and the pool was tuned) becomes thread-pool starvation under Kestrel at a fraction of the load. Search for .Result, .Wait(), GetAwaiter().GetResult(), and synchronous ADO.NET in the slice before load testing.
Architectural context
Make the inventory of modules part of week zero: read web.config's system.webServer/modules and system.web/httpModules, and Global.asax. Each module gets a middleware equivalent with a test, or a documented decision that it is no longer needed.
What breaks in production
Porting [Authorize] and assuming the module still ran is how an endpoint ships anonymous or cross-tenant. Copying HttpContext.Current into a static helper captures the wrong request. A package without a modern build blocks the slice; pretending otherwise blocks the program.
Say this in the room
Modules become middleware with tests that fail closed; configuration becomes options; app-pool identity becomes a managed identity; sync I/O gets fixed before load testing. I publish the blocker list with an owner and a decision for each.

8.5EF6 to EF Core without a production surprise

QThe slice uses EF6 with an EDMX. How do you move it to EF Core without changing the database or the query behavior by accident?

Short answerTreat it as a new data layer. Write the EF Core model in code to match the existing schema exactly (tables, schemas, keys, column types, delete behaviors, concurrency tokens), and verify by generating a migration against a baselined snapshot: it must be empty. Port the hot queries and compare their SQL and plans on realistic data, because translation differs. One side owns migrations. Lazy loading is off. Test transactions and concurrency, not only CRUD.

How it works

Under the hood
  • Translation differences: EF6 could silently evaluate parts of a query in memory in some cases; EF Core throws for untranslatable WHERE clauses. EF Core uses different SQL shapes for Includes (JOINs or split queries), GroupBy, and Contains (OPENJSON in EF 8+).
  • Behavior differences: cascade delete conventions, required versus optional relationships, the default for decimal precision, owned types instead of complex types (EF 8 adds complex types back), and many-to-many without a join entity.
  • Baseline: create an initial migration from the hand-written model, then mark it applied (insert its id into __EFMigrationsHistory) on existing databases; generating a second migration should then produce nothing.

Example

Performance and trade-offs
The same LINQ can produce a different plan: a JOIN shape instead of a subquery, a parameterized IN as OPENJSON. Run the top queries against a production-sized copy with Query Store on, and compare duration and reads with the EF6 version before moving traffic.
Architectural context
During the strangler, EF6 stays in the old process and EF Core in the new one, against the same database. Rules: one migration history owner (the new side, applied by the pipeline), the old app never creates tables (Database.SetInitializer<T>(null)), and schema changes are expand and contract so both models remain valid.
What breaks in production
Two migration histories on one database drop a column the other app reads. A property rename that EF Core sees as drop-and-add loses data. Lazy loading that filled a grid in EF6 becomes an N+1 or an empty collection in EF Core. The in-memory provider catches none of it.
Say this in the room
I rebuild the model in code to match the live schema and prove it with an empty migration. Hot queries are compared as SQL and as plans on realistic data. One side owns migrations, and both sides stay compatible through expand and contract.

8.6Authentication, cut over without an anonymous hour

QThe Framework API uses Windows authentication for internal users and an OWIN JWT middleware for partners. How do you move auth to the new host without an outage or a hole?

Short answerWrite down every audience and mechanism first. The new host accepts the target scheme (Entra ID bearer tokens) and, during the overlap, the legacy scheme too, with a policy scheme that selects the handler per request and logs which one succeeded. Authorization policies reproduce today's roles. A fallback policy requires authentication everywhere. Tests prove 401, 403, and cross-tenant 404 on every moved route. Impersonation down to SQL is replaced by the app's managed identity plus authorization in the API.

How it works

Under the hood
A policy scheme (AddPolicyScheme) is a virtual scheme whose ForwardDefaultSelector inspects the request and forwards to a real handler, so endpoints keep one policy while two token types are accepted. JwtBearer validates issuer, audience, lifetime, and signature against keys from the authority's metadata (cached and refreshed). Windows authentication (Negotiate) works on Kestrel and in IIS, but Azure App Service on Linux does not support it, which is often what forces the move to Entra ID.

Example

Performance and trade-offs
Token validation is a signature check with cached keys, microseconds per request. The policy scheme adds a header inspection. The metadata fetch happens at startup and on key rollover; make sure the host can reach the authority from its network.
Architectural context
Users are authenticated by Entra ID; the API authorizes; the app connects to SQL as itself (managed identity, Day 5). Per-user data access rules move into the API's authorization and query filters, which are testable, instead of SQL permissions per Windows account, which were not. Close the legacy scheme when its log count reaches zero for an agreed period.
What breaks in production
A route you forgot to protect ships open unless the fallback policy exists. Impersonation to SQL silently stops working, or the new app connects with a powerful account copied into a connection string. A certificate or client secret with no expiry alert fails on a Saturday.
Say this in the room
I map every audience, accept both schemes only during the overlap through a policy scheme, and log which one authenticated. A fallback policy makes everything require auth. 401, 403, and cross-tenant cases are tests. The user token authorizes; the managed identity connects to SQL.

8.7What you test when the old system has few tests

QThe legacy solution has almost no tests. What do you test before moving a slice, and what do you deliberately not test?

Short answerCharacterize the HTTP contract of the slice from the old host: status codes, important headers, and the JSON for the main success and failure cases, captured as approved snapshots and replayed against the new host. Add golden tests for money calculations and anything that caused an incident, an integration test against real SQL for the migrated queries, proxy routing tests, and a load test on the slice. Do not stop to unit-test the whole legacy estate.

How it works

Under the hood
A characterization test records what the system does today, right or wrong, so the migration preserves behavior and any intentional change is visible in review. Snapshot libraries (Verify) store the approved output next to the test and fail with a diff when it changes. Running the same suite against both hosts (by switching the base URL) is the strongest equivalence check you can get cheaply.

Example

Performance and trade-offs
The load test is where sync-over-async, missing indexes, and connection-pool limits show up. Run it against the new host with production-like data before the first percentage of traffic moves, and again after the move with real traffic as the comparison.
Architectural context
The contract suite becomes the regression suite of the new host, so the migration leaves the system better tested than it found it, focused on what matters. Keep the snapshots in source control; changes to them are reviewed like code.
What breaks in production
A green suite of new unit tests that never saw the old JSON lets a renamed field break every partner. Skipping the proxy test sends /payments to a host that does not own it yet. Leaving load testing until launch hides the blocking call.
Say this in the room
I characterize the HTTP contract of the slice on the old host and replay it on the new one, add golden tests for money, auth tests on every route, a real SQL test for the hot queries, and a load test. I test payment before I test a dropdown.

Example

Architectural context
Present the estimate as a decision with options: faster with more people on parallel slices once the pattern is proven; cheaper by leaving low-value modules on a supported Framework host longer; riskier by skipping characterization tests. 8.9Rollback six weeks into a strangler

QSix weeks after moving /orders to .NET 10, a serious bug appears. How do you roll back, and what makes rollback impossible?

Short answerRollback is a route change in the facade that sends /orders back to the Framework host. It works only if the old host can still read and write the current schema and the data the new host wrote. That is guaranteed by expand and contract: add nullable columns, never rename or drop in the same release as the route change, and keep the old code tolerant of new data. A feature flag can disable a new behavior without moving the route. Rehearse it on staging and write it on the release ticket.

How it works

Under the hood
Two code versions share one database, so the schema must be valid for both at every point. "Expand" changes (new nullable columns, new tables, new indexes) are invisible to the old code. "Contract" changes (drops, renames, NOT NULL without defaults) are applied only after the old code is gone for good. Data compatibility matters too: if the new host writes an enum value or a status the old host does not know, the old host fails after rollback even though the schema is fine.

Example

Architectural context
Rollback design is part of the slice's definition of done: the route change, the schema compatibility check, the data compatibility check, and a rehearsal. If you cannot describe the rollback in three lines, the slice is too big.
What breaks in production
A drop or rename in the same release as the route change removes the old host as a rollback. Data written in a shape the old host rejects is stuck even if the route goes back. An unrehearsed proxy change at midnight is a guess.
Say this in the room
Rollback is a route change plus a schema and data the old code can still use. I expand first and contract much later, add kill switches for new behavior, and rehearse the route change. If I cannot describe the rollback, the slice is too big.

9.1The design spine

QDesign a backend for X. Where do you start, and how do you keep twenty minutes from turning into a tour of Azure products?

Short answerWrite the spine on the board in the first three minutes and fill it in order: users and numbers, API, data, consistency, failure, operation, and the trade-off you refused. State assumed numbers and invite correction, because the design changes when the number changes. Do back-of-envelope math out loud so the scale claims are earned.

  1. Clarify the user, the success metric, the scale you are assuming, and what is out of scope. State the assumption and let them correct you.
  2. Name the API: resources, verbs, sync versus async, status codes.
  3. Name the data: the aggregate, the key, the constraint, the index that matches the hot query.
  4. Name consistency: what is in one SQL transaction, what is a message, what may lag.
  5. Name failure: timeout, retry, duplicate, poison message, and what the user sees.
  6. Name operation: logs, the one dashboard, deploy and rollback, identities and SQL roles.
  7. Name the trade-off you refused, and the first slice you would ship.

How it works: the arithmetic that earns the design

Under the hood
  • Throughput: 2 million orders a year is about 5,500 a day, or 0.06 per second on average. With a 10× daily peak and reads at 20× writes, about 50 requests per second at peak is generous.
  • Concurrency (Little's law): in-flight requests = arrival rate × latency = 50 × 0.1 s = 5. Two App Service instances with a few dozen threads each are idle most of the time; the SQL connection pool needs single digits per instance.
  • Storage: 2 million orders × about 2 KB with lines and indexes is about 4 GB a year. One Azure SQL database holds a decade without partitioning.
  • Messages: one OrderPlaced per order is far below a Standard Service Bus namespace's limits.
  • Conclusion said out loud: one database, one API, one Function. The interesting problems are correctness (idempotency, lost updates, duplicates), not scale.

Example of the opening ninety seconds

What breaks in production
Designing for a million events a second without being asked overbuilds and runs out of time before the failure modes, which is where the points are. Naming products before the numbers makes every later choice look arbitrary.
Say this in the room
I state the user, the number, and the out-of-scope box before I name a product, and I show the arithmetic. Then I take correction. The rest of the design hangs off that number.

9.2Design A — the Order API, worked

QDesign the backend for creating an order, viewing it, and emailing a confirmation. Partners retry. Two customers must not lose updates. You are the tech lead.

Short answerThis combines Days 3 through 7 in one design, spoken in spine order. Idempotent POST with a stored response; server-side pricing; one SQL transaction for the order, the idempotency key, and the outbox; rowversion for updates; keyset lists; email via Service Bus and an idempotent Function; App Service with slots; three identities; and a dashboard with outbox age and DLQ depth. The first slice is a synchronous create, the outbox, and the email consumer.

API

Data and consistency

Failure, operation, and the slice

  • Tax, if synchronous and required: a total timeout inside the request budget, a small jittered retry only because the tax call is safe to repeat, a breaker, then 503. If the business would rather accept PendingTax, say that and store the state; label it a product choice.
  • Duplicate email: the consumer dedupes on the message id. That unique key is in the first increment, not a follow-up story.
  • Two writers: the rowversion WHERE clause changes zero rows, EF throws, the API returns 412 (or 409 without If-Match). No blind retry.
  • Host: App Service, slots, Always On, affinity off. Isolated-worker Function for email. Three identities: user token, API managed identity in app_orders_runtime, pipeline migrator.
  • Dashboard: request p95 by operation, SQL dependency duration, outbox age, dead-letter depth, thread-pool queue length. Rollback is a swap, only while the schema is compatible.
  • First slice: synchronous create, the outbox, and the email consumer. Pricing stays a module behind IPriceService.
Performance and trade-offs
Latency budget for POST at p95 300 ms: auth and validation about 1 ms, idempotency lookup one seek (2 ms), tax call up to 150 ms with timeout, one SQL transaction with four inserts (5 to 10 ms), serialization under 1 ms. The tax call dominates, which is why its timeout and breaker are the design's main lever.
What breaks in production
Accepting Total from the client lets the partner set the price. Publishing inside the transaction holds locks and announces orders that may roll back. A microservice split in the first twenty minutes spends the clock on boxes and never reaches the duplicate or the 412.
Say this in the room
One transaction for the order, the idempotency row, and the outbox. Email after commit, deduped. 412 on a lost update. App Service and a Function, three identities, and a dashboard with outbox age. Pricing stays a module until a second team needs it. The week-one risk is a duplicate email, so the inbox ships first.

9.3Design B — a nightly file of a million rows, worked

QA partner drops a CSV with a million rows in storage every night. Validate, load, and report failures, while the HTTP API stays responsive.

Short answerThe blob trigger only records the file and enqueues a control message. A splitter (or a Durable orchestration) plans chunks; workers stream each chunk, validate rows, bulk-copy valid rows into a staging table with SqlBulkCopy, and merge set-based into the real table in one short transaction per chunk, idempotent on (FileId, ChunkNo). Bad rows go to an error table the partner can download. The file moves through explicit states, and an alert fires if it is not terminal by the deadline.

Flow

Why not EF per row

Performance and trade-offs
A million SaveChanges calls are a million round trips and transactions, hours at 5 ms each, and they hold the API's database busy. SqlBulkCopy loads tens of thousands of rows per second per connection; the MERGE per chunk of 10,000 rows is one short transaction. Chunks bound memory and retry cost. Watch the Azure SQL log rate limit (LOG_RATE_GOVERNOR) and schedule large loads off-peak or scale the tier temporarily.
Architectural context
Identities: the worker's managed identity reads the container and writes the staging schema; it cannot ALTER, and it is not the API's identity. A Durable Functions fan-out (Day 6) is the orchestrated version of the same flow, with the file state as its custom status. Prove chunk retry on a small file before talking about scale.
What breaks in production
One invocation that reads the whole file dies at the function timeout and retries from byte zero. A chunk retry without a range key double-inserts. A poison chunk that stops the whole orchestration leaves 99 chunks unprocessed and the file looking idle. Byte-range splitting must align to line boundaries (and quoted newlines in CSV); a splitter that counts lines first is simpler.
Say this in the room
The trigger only records the file. Workers own idempotent chunks: stream, validate, bulk copy to staging, set-based merge. Bad rows are queryable and downloadable, the API only reads status, and an alert fires if the file is not done by the deadline.

9.4Design C — multi-tenant, if they ask

QMake the Order API multi-tenant. One database or many?

Short answerDefault to one database with TenantId on every tenant-owned row, a global query filter, unique indexes that start with TenantId, the tenant from the token only, and a test that crosses tenants. Row-Level Security is the backstop. A noisy or regulated tenant can move to its own database in an elastic pool, which the app resolves per tenant through a catalog, at the cost of running every migration once per database. Do not start with a database per tenant for hundreds of small customers.

How it works

Under the hood
Tenant resolution happens once per request in middleware (Day 8) and is stored in a scoped ITenant. For database-per-tenant, a tenant catalog maps TenantId to a connection string or database name, and the DbContext registration builds options per tenant (with pooling, via a factory keyed by tenant). Elastic pools share vCores across databases so many small tenants cost little; elastic jobs or a pipeline loop apply migrations to every database and record the version per tenant.

Example

Shared database, TenantIdLogical (filters, RLS)LowestOne migration, one database

Database per tenant (elastic pool)Physical; per-tenant restore and keysMediumMigrations × N, catalog, drift detection

What breaks in production
Trusting tenant id from the body is a cross-tenant write. A unique index on Number alone collides across tenants or leaks that a number exists. A database per small tenant multiplies every operational mistake by the tenant count, and a missed database during migrations is a drift incident.
Say this in the room
One database, TenantId from the token, a filter, unique indexes that include the tenant, RLS as a backstop, and a test that crosses tenants. A separate database is a named exception for a regulated or noisy tenant, with the migration cost stated first.

9.5How a lead story is shaped

QTell me about a time you led through a production incident, a disagreement, or growing someone.

Short answerUse situation, task, action, result, and a last line: what the team does now. Keep it under two minutes. "I" is for your decision; "we" is for the work the team did. Panels score whether you actually decided something, the number that proves the result, and the rule that outlived the event. The three stories below are scaffolds, annotated so you can hear what does the work. Then you throw the facts away and write yours.

Scaffold — production incident

Situation: a release went out at 11:00 and by 11:20 the order GET p95 was above four seconds. Task: you were the tech lead on call and had to choose rollback or fix-forward. Action: you checked the deploy marker against the latency chart, saw SQL dependency time jump, and swapped back within fifteen minutes because the migration had only added a nullable column. Then you looked at Query Store. A new screen was scanning Orders. The team added a covering index in a reviewed script and shipped it that afternoon. Result: latency returned to about 200 milliseconds after the swap, and the index kept the new screen. The team rule now is that a list-endpoint PR includes the filter, the index, and a sample plan, and rollback is pre-written on the release ticket.

  • The decision is the swap, and the minute you chose it. Without the minute, it is a war story.
  • The number is the p95 before and after. A panel can score a number. It cannot score "it was slow".
  • The safety condition is the nullable column. That is why swap-back was allowed. Say it.
  • The lasting line is the PR rule. A lead changes the next review, not only tonight's graph.

Scaffold — disagreement

Situation: a senior developer wanted a generic repository and a new microservice for pricing before a release. Task: you needed a data-access approach the team could review, and a date you could hit. Action: you asked what change you were protecting. You had one query shape and one team. You proposed pricing as a module behind IPriceService, and no generic repository, so the SQL stayed visible. You wrote a one-page note and asked them to own the module boundary. Result: you shipped on time, the query stayed tunable, and they kept real ownership. You would split pricing later if a second team needed to release it.

  • You disagreed with a person, not with "the business". Name the proposal.
  • The question "what change are we protecting?" is the technique. Use it on your own story.
  • The relationship cost is in the story: they kept ownership. A lead who only wins the argument sounds expensive to work with.
  • The consequence is a date you hit and a SQL statement you could still see.

Scaffold — growing someone

Situation: a developer with two years of experience was copying controllers and calling SaveChanges from actions. Task: the next feature had to land in a shape the team could maintain. Action: you paired on one endpoint, moved the use case into a handler, and left them a checklist: cancellation token, a projection for the read, a test for the failure path, and a status code. You reviewed the rule, not the formatting. Result: they owned the returns API two months later and caught an over-posting bug in someone else's PR. The checklist is in the repository.

  • The action is a checklist another person can apply. Heroic pairing with no artifact does not scale.
  • The result is what they own now, plus a bug they caught without you.
  • I reviewed the rule. We shipped the endpoint. Keep those pronouns honest.
What breaks in production
Memorizing these scaffolds as your career fails on the first follow-up ("which index, on which table?"). Replace every fact. If you do not have a p95, use the number you did have: error count, tickets, minutes to swap.
Say this in the room
My story has a decision, a number, and a rule the team still follows. "I" is the decision. The sample in the guide is the shape. The facts are mine.

9.7Technical debt

QHow do you decide which technical debt to pay down, and how do you get it funded?

Short answerName the debt in user or operator language (this list endpoint will time out at the next tenant's volume; this host is out of support in November 2026), attach the cost of leaving it and the cost of fixing it, and put a slice of the fix into an increment that already opens that code. Spend a reserved capacity (often 15 to 20 percent) on the item with the nearest incident, not on the rewrite you find interesting. Delete debt too: a pattern you no longer need is a ticket with an owner.

Example

Architectural context
Make debt visible with the same telemetry you use for incidents: SLO burn, Query Store regressions, dependency versions approaching end of support, and flaky-test counts. A debt register with evidence and cost is something a manager can trade against features; "clean code" is not.
Say this in the room
I name the incident the debt implies, show the evidence, and propose the smallest fix attached to work that is already open. I do not spend the reserve on the rewrite I find interesting.

9.8Review without becoming the bottleneck

QYou are the most senior engineer. How do you keep quality high without every PR waiting for you?

Short answerPublish the rules so people can apply them without you: cancellation, authorization, SQL shape, secrets, tests for the money path, migration safety. Automate what can be automated (formatters, analyzers, architecture tests, CODEOWNERS for auth and schema). Review the contract and the risk, not the braces. Ask for a design walk-through before a thousand-line PR exists. Pair on a junior's first reviews so comments teach. Grow a second reviewer for each risky area, and measure PR wait time.

Example

What breaks in production
If every PR waits for you, the review system has failed, and your absence becomes an outage of delivery. Style comments crowd out the one comment about the missing tenant filter.
Say this in the room
I publish the rule, automate what I can, review the contract and the risk, and make sure a second person can approve the ordinary PR. I watch PR wait time; if everything waits for me, I have failed.

9.9Disagreeing with your manager's technical direction

QYour manager wants a direction you think is wrong. What do you do?

Short answerRestate their goal until they agree you understood it. Put your alternative in writing with the risk, the date, and the operational cost. Distinguish a reversible choice from a one-way door. On a reversible choice, disagree, commit, and watch the metric you named. On a one-way door (a shared database across a boundary you cannot undo, a production login as db_owner), say so clearly and offer a smaller experiment. Do not relitigate in the team channel after the decision. If the decision is unsafe for customers or staff, escalate with the risk written down.

Example

What breaks in production
Calling every disagreement a one-way door makes the phrase useless. Relitigating a reversible choice in public after committing trains the team to ignore decisions. Staying silent on db_owner because the date is close is how the login survives for years.
Say this in the room
I restate the goal, write the risk, and separate a reversible choice from a one-way door. I use that language once, on a real example, and then I commit or escalate.

10.2Rapid fire, each with a miniature

Read the miniature, cover it, and say the one-sentence answer. The pointer is where the full treatment lives if you miss.

401 versus 403

401 means we do not know you; 403 means we know you and you may not do this. Another tenant's resource is 404, so existence does not leak. Full treatment: Day 3.

PUT versus PATCH versus POST

PUT replaces the resource and is idempotent. PATCH changes part of it. POST creates or starts work, and a retry needs an idempotency key. Full treatment: Day 3.

Transient, scoped, singleton

Per resolve, per scope (request), per container. DbContext is scoped. A singleton must not capture a scoped service; ValidateScopes catches it in development, and a hosted service creates a scope per unit of work. Full treatment: Day 3.

Why not .Result

It blocks a pool thread while the I/O completes, so under load the pool starves and every endpoint slows; with a SynchronizationContext it can deadlock. Await and pass a CancellationToken. Full treatment: Day 1.

Async state machine

The compiler rewrites an async method into a struct state machine; on the first incomplete await it is boxed to the heap, and the continuation is scheduled when the awaited task completes. No thread waits during the I/O. Full treatment: Day 1.

ValueTask versus Task

ValueTask avoids an allocation when the result is usually synchronous (a cache hit). Await it exactly once and never store it; Task is the default for everything else. Full treatment: Day 1.

ConfigureAwait(false)

Library code that may run under a UI or classic ASP.NET context should not resume on it. ASP.NET Core has no SynchronizationContext, so application code just awaits. Blocking still hurts either way. Full treatment: Day 1.

Thread-pool starvation

Blocking calls hold workers; the pool injects new threads slowly (about one per second past the minimum), so queue length climbs while CPU stays low. Fix the blocking, not the minimum. Full treatment: Day 1 and Day 6.

GC generations

New objects go to Gen0; survivors are promoted to Gen1 then Gen2. Most objects die young, so Gen0 collections are cheap and frequent; Gen2 collections are expensive and should be rare. Full treatment: Day 1.

LOH and POH

Objects of 85,000 bytes or more go to the Large Object Heap, collected with Gen2 and not compacted by default, so big temporary buffers cause Gen2 GCs and fragmentation. The Pinned Object Heap holds long-lived pinned buffers. Rent big buffers from ArrayPool. Full treatment: Day 1.

Server versus Workstation GC

Server GC has a heap and a GC thread per core for throughput and is the ASP.NET Core default; Workstation GC uses less memory. DATAS (default in .NET 9+ with Server GC) adapts heap count to load, which matters in containers. Full treatment: Day 1.

Span<T>

A ref struct view over contiguous memory (array, stack, native) with no allocation; it cannot be boxed, captured, or live across await. Memory<T> is the heap-storable version for async code. Full treatment: Day 1.

Boxing

Converting a value type to object or an interface allocates a heap copy. It hides in non-generic collections, string.Format with value types, and interface calls on structs. Full treatment: Day 1.

Tiered JIT and ReadyToRun

Methods start at Tier0 (fast to compile, unoptimized) and are recompiled at Tier1 with Dynamic PGO after about 30 calls; ReadyToRun ships precompiled code to cut startup. Native AOT removes the JIT entirely at the cost of reflection limits. Full treatment: Day 1.

Channels

An async producer-consumer queue. A bounded channel applies backpressure: writers wait when it is full, so a fast producer cannot exhaust memory. Full treatment: Day 1.

lock and await

lock is thread-affine and the compiler forbids await inside it; use SemaphoreSlim(1, 1) with WaitAsync for async critical sections, and remember either only protects one process. Full treatment: Day 1.

Captive middleware

Convention-based middleware is constructed once, so a scoped service in its constructor is captured for the app's lifetime. Take scoped services as InvokeAsync parameters, or use IMiddleware registered as scoped. Full treatment: Day 3.

IEnumerable versus IQueryable

IEnumerable runs in memory; IQueryable is an expression tree a provider turns into SQL. Once you cross into IEnumerable, every later operator runs on the client. Full treatment: Day 1.

AsNoTracking

On reads, skip the snapshot and identity map; better, project to a DTO so only the needed columns are selected. Full treatment: Day 4.

N+1

One query for the parents and one per child, from a loop or a lazy load. Replace it with one projection or a controlled include, and count commands in a test. Full treatment: Day 4.

rowversion

A concurrency token: the UPDATE matches the version the client read. Zero rows means a concurrency exception, returned as 412 with If-Match or 409 without, never a silent overwrite. Full treatment: Day 4.

Clustered versus nonclustered

The clustered index is the table in key order. A nonclustered index is a separate B-tree carrying the clustering key; include the selected columns to avoid key lookups. Full treatment: Day 5.

SARGable

The bare column compared with a value of the same type lets the index seek. Functions, arithmetic, and implicit conversions on the column force a scan. Full treatment: Day 5.

Deadlock 1205

Two transactions each hold a lock the other needs; SQL Server kills one. Retry is the seatbelt; the fix is consistent access order, a supporting index, and short transactions. Full treatment: Day 5.

RCSI

Readers see the last committed row version and take no shared locks, so they do not block writers. It costs version-store work and does not prevent lost updates. Full treatment: Day 5.

db_owner for the app

No. A runtime role with DML and EXECUTE on its schema, and a separate migrator identity used only by the pipeline. Full treatment: Day 5.

Idempotency key

A client key stored uniquely with a request hash and the first response, in the same transaction, so a retried POST replays instead of creating a second order. Full treatment: Day 3 and Design A.

Outbox

The business row and the message row commit together; a relay publishes after commit; consumers dedupe with an inbox. Delivery is at least once. Full treatment: Day 7.

Peek lock

Service Bus locks the message while you process it; complete deletes it, abandon or lock expiry redelivers it, and after MaxDeliveryCount it is dead-lettered. Full treatment: Day 6.

Cold start

A new or scaled-to-zero instance pays host start, JIT, and DI before the first request. Fine for email; for a user waiting, buy warm capacity (always-ready, Premium) or keep it in the API. Full treatment: Day 6.

Deployment slot

Deploy to staging, apply production settings, warm every instance, then switch routing; swap-back is the same operation, valid only while the schema suits both versions. Full treatment: Day 6 and Day 4.

Managed identity

The Azure resource gets an Entra identity and tokens from the platform, so no password exists; grant it narrow RBAC roles and a contained SQL user. Full treatment: Day 6.

Strangler fig

A facade owns the URL; one slice at a time routes to the new host; delete the old slice when traffic, logs, and rollback are proven. Full treatment: Day 8.

Generic repository

DbContext is already a unit of work and DbSet a repository. Prefer a focused store per aggregate, or none, so the SQL shape stays visible. Full treatment: Day 2.

Mediator

A dispatcher from a request to one handler, worth it when pipeline behaviors (validation, transactions, logging) earn it. Handlers do not send other requests. Note MediatR's commercial license from 2025. Full treatment: Day 2.

Circuit breaker

After a failure ratio over a sampling window, fail fast for a break duration, then probe. Inside the retry, outside the attempt timeout. Full treatment: Day 3.

Sync versus async integration

Synchronous when the user needs the answer now and you accept the availability coupling; asynchronous when the work can finish after the response. Full treatment: Day 7.

Database per service

The service owns its writes; cross-service joins become an API call, a versioned local copy fed by events, or a reporting store. Full treatment: Day 7.

Startup Migrate

Unsafe with many instances and it needs DDL rights on the app identity. Apply a reviewed bundle or idempotent script from the pipeline before the swap. Full treatment: Day 4.

Record versus class

A record for value-shaped data (DTOs, events, value objects) with generated equality and with; a class for an entity with identity that EF tracks. Full treatment: Day 1.

ProblemDetails

RFC 9457 error body with type, title, status, detail, and a trace id; validation adds an errors dictionary. One shape everywhere through AddProblemDetails. Full treatment: Day 3.

Keyset versus offset

Keyset seeks from the last key with a unique tie-breaker, so every page costs the same; offset reads and discards skipped rows and shifts under inserts. Full treatment: Day 5.

.NET support

.NET 10 is the LTS to target, supported until November 2028. .NET 8 (LTS) and .NET 9 (STS) both reach end of support on 10 November 2026, as does the in-process Functions model. Full treatment: Day 8.

Appendix A — Testing and diagnostics

The roadmap's days refer here whenever an answer ends with "and I would prove it". A lead is expected to say how a claim is tested before merge and how a problem is diagnosed in production without guessing.

A.1Unit testing that survives refactoring

QWhat makes a unit test valuable rather than a maintenance cost? Show a good one and a bad one.

Short answerTest behavior through the public surface of a unit (a domain object, a handler, a pure function), with real collaborators where they are cheap and fakes only at the process boundary (clock, network, message bus). Name tests by behavior, arrange with builders, assert on outcomes rather than interactions, and control time with TimeProvider and FakeTimeProvider. Do not mock DbContext or DbSet: test data access with a real database (next section).

How it works

Under the hood
  • xUnit creates a new instance of the test class per test, so constructor setup is per test and state does not leak. IClassFixture<T> shares expensive setup within a class; ICollectionFixture<T> shares it across classes and disables parallelism between them. Test classes in different collections run in parallel by default. xUnit v3 (2024+) runs tests as standalone executables and adds TestContext.Current.CancellationToken.
  • Mocks versus fakes: a mock verifies calls (Verify(x => x.Save(...))), coupling the test to the implementation. A fake is a working lightweight implementation (in-memory store, fake clock) and lets the test assert on state. Interaction assertions are right only when the interaction is the behavior (a message was published).
  • FakeTimeProvider (Microsoft.Extensions.TimeProvider.Testing) implements GetUtcNow, timers, and Task.Delay through TimeProvider, so tests advance time instantly with Advance.

Example

Performance and trade-offs
Unit tests should run in milliseconds each, so the whole suite runs on every save. Slow unit tests are usually hidden I/O or a real Task.Delay; FakeTimeProvider removes the latter.
Architectural context
Push logic into the domain and pure functions so most rules are unit-testable without infrastructure; keep handlers thin and cover them with integration tests. The testing pyramid for this system: many domain tests, a solid layer of API integration tests against real SQL, a few end-to-end smoke tests after deploy.
What breaks in production
Tests that mirror the implementation break on every refactor and catch no bugs. DateTime.Now in code under test creates tests that fail at midnight, at month end, or in another time zone. Shared static state between tests makes them order-dependent once parallelism is on.
Say this in the room
I test behavior through public surfaces, with fakes only at process boundaries, builders for arrangement, and FakeTimeProvider for time. I assert outcomes, not calls. Data access is tested against a real database, never a mocked DbSet.

A.2Integration tests with WebApplicationFactory, Testcontainers, and Respawn

QHow do you test the API end to end, including SQL, auth, and the outbox, quickly enough to run on every PR?

Short answerHost the real app in memory with WebApplicationFactory<Program>, point it at a real SQL Server in a Docker container started once per test run with Testcontainers, apply migrations once, and reset data between tests with Respawn (which deletes rows in dependency order, much faster than recreating the database). Replace only true externals: a test authentication handler that issues claims per persona, a fake email sender, and an in-memory or test-harness bus.

How it works

Under the hood
WebApplicationFactory builds the host from your Program with a TestServer, so requests go through the real middleware, routing, model binding, filters, and DI, without sockets. ConfigureWebHost lets you override configuration and services after the app's registrations. Testcontainers starts the container through the Docker API and gives you a connection string with a random port. Respawn reads the schema's foreign keys once, then issues ordered DELETE statements for the tables that have data, skipping tables you exclude such as __EFMigrationsHistory.

Example

Performance and trade-offs
A SQL Server container takes 10 to 20 seconds to start; do it once per run with a collection fixture. Respawn resets in tens of milliseconds. Tests in one collection run sequentially; split independent areas into separate collections with separate databases (one container, several databases) for parallelism. CI agents need Docker; hosted Linux agents on GitHub Actions and Azure Pipelines have it.
Architectural context
These tests are the safety net for the claims made throughout the guide: idempotency under concurrent retries, 401/403/404 per persona, tenant isolation, rowversion 412s, N+1 command counts (Day 4 interceptor), and migrations applying cleanly from zero. Contract snapshots (Day 8) run in the same harness.
What breaks in production
The EF in-memory provider passes tests that fail on SQL Server: no transactions, no constraints, no SQL translation. SQLite differs in types, collation, and concurrency. A shared database without reset makes tests order-dependent. Testing against a shared dev database in Azure makes CI flaky and slow.
Say this in the room
WebApplicationFactory hosts the real pipeline, Testcontainers gives a real SQL Server per run, migrations run once, Respawn resets between tests, and only true externals are faked. That is where I prove idempotency, tenant isolation, and concurrency, on every PR.

A.3BenchmarkDotNet: measuring instead of guessing

QA developer says their change makes parsing 30 percent faster. How do you verify it?

Short answerA BenchmarkDotNet benchmark in a Release build, comparing the old and new implementations with one marked as the baseline, with [MemoryDiagnoser] to show allocations per operation, realistic inputs as parameters, and results consumed (returned) so the JIT cannot eliminate the work. Look at the mean, the error and standard deviation, the ratio to baseline, and allocated bytes. Then confirm the effect in the real system with counters or a trace, because a micro-benchmark proves the method, not the endpoint.

How it works

Under the hood
BenchmarkDotNet generates and builds a separate project per runtime and configuration, runs it in a new process, performs pilot runs to choose an invocation count, warms up until steady state (so Tier1 and Dynamic PGO code is measured, not Tier0), then runs many iterations and computes statistics with outlier removal. MemoryDiagnoser reads allocated bytes per thread from the GC API; DisassemblyDiagnoser shows the JIT's machine code. Running from a Debug build or under a debugger is refused, because the numbers would be meaningless.

Example

Performance and trade-offs
Allocation reduction often matters more than the nanoseconds: fewer Gen0 collections and less promotion to Gen2 under load improve tail latency for the whole process. Report both. A 10 ns gain on a method called once per request is irrelevant next to a 5 ms SQL query.
Architectural context
Keep benchmarks in a benchmarks/ project in the repository for hot paths (serialization, parsing, pricing), run them on demand or nightly on a dedicated agent, and require them in PRs that claim performance. Compare runtimes (net8.0 versus net10.0) as part of the migration's business case.
What breaks in production
Benchmarks on a laptop on battery, with a browser open, vary by tens of percent. Inputs that fit in L1 cache flatter the result. A benchmark that tests a different code path than production (a warm cache, a tiny payload) proves nothing about production.
Say this in the room
BenchmarkDotNet in Release with a baseline, realistic parameters, MemoryDiagnoser, and returned results. I read mean, error, ratio, and allocated bytes, then I confirm the endpoint moved with counters or a trace.

A.4dotnet-counters: the first look at a live process

QThe API is slow in production. Before taking a dump or a trace, what do you look at on the process itself?

Short answerdotnet-counters attaches to a running process through the diagnostics port (EventPipe) with near-zero overhead and shows live runtime metrics: CPU, working set, GC heap size and collection counts per generation, time in GC, allocation rate, thread-pool thread count and queue length, lock contention, exception count, and ASP.NET Core request rates. Thirty seconds of counters tells you which family the problem belongs to: CPU-bound, GC-bound, starved, or waiting on something outside.

A.5dotnet-trace: where the time and allocations go

QCPU is at 90 percent on every instance after a release. How do you find the method responsible?

Short answerCollect a 30-second CPU sampling trace with dotnet-trace from one busy instance, open it in a flame-graph viewer (Speedscope, PerfView, or Visual Studio), and look for the widest stacks in your code. For allocation problems, collect GC events with allocation sampling and look at the types and call stacks allocating the most. Compare with a trace from the previous release if you have one.

How it works

Under the hood
dotnet-trace enables EventPipe providers in the target process: Microsoft-DotNETCore-SampleProfiler captures managed stacks of every thread about every millisecond; Microsoft-Windows-DotNETRuntime with GC keywords emits GC start/end, heap stats, and GCAllocationTick events roughly every 100 KB of allocation with the type and stack. The output is a .nettrace file. It works on Linux and Windows without kernel tools, though it sees only managed code; PerfView (ETW) or perf on Linux see native frames too.

Example

Performance and trade-offs
CPU sampling overhead is a few percent; gc-verbose with allocation ticks is higher on allocation-heavy apps. Keep traces short (30 to 60 seconds) and on one instance. Traces include method names and possibly string payloads from events, so treat them as sensitive data.
Architectural context
dotnet-monitor runs as a sidecar or a tool and exposes an HTTP API to collect traces, dumps, and gcdumps on demand or on triggers (CPU above X for Y seconds), which is how you capture evidence in containers at 03:00 without a human attaching. Application Insights Profiler gives sampled production traces on App Service with no tooling on the instance.
What breaks in production
Profiling a Debug build or a cold process measures Tier0 code and startup. A trace from a healthy instance shows nothing; take it from the instance with the symptom while the symptom is happening.
Say this in the room
A 30-second cpu-sampling trace from the busy instance, viewed as a flame graph, shows the widest stack. For GC pressure, gc-verbose shows which types and call sites allocate. In containers, dotnet-monitor collects on a trigger.

A.6dotnet-dump and dotnet-gcdump: hangs, starvation, and leaks

QMemory grows until the instance restarts every two days, and sometimes requests hang. How do you find the cause?

Short answerFor a leak, take two gcdumps an hour apart with dotnet-gcdump and compare object counts and sizes by type; the type that keeps growing, plus its retention path (gcroot), names the leak. For a hang or starvation, take a full dump with dotnet-dump during the symptom and analyze it with SOS: threadpool for queue length, clrstack -all or parallelstacks for what threads are blocked on, dumpasync for awaiting state machines, and syncblk for lock owners.

How it works

Under the hood
A gcdump is a heap graph (types, counts, sizes, references) collected via EventPipe by triggering a Gen2 GC; it is small and contains no field values, so it is relatively safe to share. A full dump is the process's entire memory (gigabytes, contains secrets and personal data) and supports the full SOS command set. gcroot walks from an object back to a root (a static field, a thread stack, a GC handle, the finalizer queue), which is how you see that a singleton's event subscription or a static dictionary keeps the objects alive.

Example

Performance and trade-offs
A full dump pauses the process while memory is written (seconds for large heaps), so on a live instance, take it from one instance and route traffic away if possible. Gcdump triggers a full blocking GC, which is also a pause. Neither belongs in an automatic loop.
Architectural context
Configure automatic dumps on crash (DOTNET_DbgEnableMiniDump=1, DOTNET_DbgMiniDumpType=2, a writable path) so crashes leave evidence. Store dumps in a restricted location with retention, because they contain tokens, connection strings, and customer data. App Service's "Diagnose and solve problems" can collect memory dumps and run the analysis for you.
What breaks in production
Sharing a full dump in a chat channel leaks secrets. Analyzing a dump taken after the hang cleared shows a healthy process. Comparing a single gcdump to intuition ("strings look big") without a second snapshot misidentifies normal caches as leaks.
Say this in the room
Leaks: two gcdumps, compare growth by type, gcroot the growing type to its root. Hangs: a full dump during the symptom, then threadpool, parallelstacks, dumpasync, and syncblk. Dumps are sensitive data and get handled like production secrets.
